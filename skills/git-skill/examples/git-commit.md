## 场景三:Git 代码提交

### 提交代码流程

**【重要】推送前必须先确认当前分支名称，严禁硬编码 master 或任何固定分支名！**

#### 单号获取优先级策略

在执行 `git commit` 前，必须按照以下优先级顺序获取 Jira 单号：

**优先级 1：查看当前工程最近一周内的提交记录**

```cmd
::: 获取最近一周内所有提交记录，提取最新的单号
git log --since="1 week ago" --pretty=format:"%s" | findstr /R "RDC:[A-Z]*-[0-9]*"
```

- 从返回结果中提取第一个匹配的单号（如 `RNIA-1687846`）
- 如果找到单号，则复用该单号作为本次提交的单号
- 如果未找到任何提交记录或无匹配单号，进入优先级 2

**优先级 2：弹框要求用户输入新单号**

- 调用弹框工具
- 标题：`"Jira 单号输入"`
- 提示文本：`"未找到最近的提交单号，请输入新的 Jira 单号 (格式如：RNIA-123456)："`
- 等待用户输入并验证格式是否符合 `[A-Z]+-\d+` 模式
- 若用户取消输入，终止提交流程并提示"无法继续执行代码提交，请准备好 Jira 单号后重试"

```cmd
::: 第一步：获取当前分支名称（必须执行）
git rev-parse --abbrev-ref HEAD
::: 返回值示例：ngi-master、master、feature-xxx 等

::: 第二步：根据当前分支执行 add 和 commit
::: 【重要】请严格按照用户要求添加文件，谨慎使用 git add ./ 全量添加
::: 如需精确添加指定文件，请使用 git add <文件路径>
git add ./
::: 必须按照指定格式编写提交说明，单号需通过上述优先级策略获取
git commit -m "RDC:RNIA-1687846 提交说明"

::: 第三步：使用第一步获取的当前分支名进行推送（将 <branch_name> 替换为实际分支名）
git push origin HEAD:refs/for/<branch_name>
::: 正确示例（假设当前分支是 ngi-master）：git push origin HEAD:refs/for/ngi-master
::: 错误示例（禁止硬编码）：git push origin HEAD:refs/for/master
```

### git add 注意事项

**严格按照用户要求执行 add 操作**:
- 如果用户明确指定了要添加的文件或目录,必须精确添加用户要求的内容,不得擅自添加其他文件
- **谨慎使用 `git add ./`** 全量添加:仅在用户明确要求全量添加时使用,或者在确认工作区所有变更都属于本次提交范围时方可使用
- 执行 `git add` 前,务必通过 `git status` 或 `git diff` 确认即将添加的文件是否符合用户要求
- 如有疑问,应先向用户确认后再执行 add 操作

### 提交说明格式要求

#### 提交说明格式规范

```
RDC:<单号> <变更类型>: <简洁描述>
```

**格式要求**：
- 必须以 `RDC:` 开头，后跟 Jira 单号（如 `RNIA-123456`、`RNC-789012`）
- 单号后应紧跟空格，然后是变更类型关键词
- 变更类型后用冒号 `:` 分隔，冒号后是具体描述
- 描述应简洁明了，一行内完成（建议不超过 50 个字符）

**正确示例**：
```
RDC:RNIA-1614601 修复:/pcg/detail/line查询空指针异常(关联过滤)
RDC:RNIA-1687846 新增:无线网络孪生-优化方案任务详情页
RDC:RNC-1523456 优化:统计查询SQL性能
RDC:RNIA-1590123 调整:任务状态流转逻辑
```

**错误示例**：
```
错误：RDC:RNIA-1614601  修改了代码（太笼统）
错误：RDC:1614601 修复xxx（缺少项目前缀）
错误：RDC:RNIA-1614601  这个功能修改了很多地方（冗余）
```

#### 智能提交说明生成流程

**【核心目标】** 通过 Git 命令获取修改的代码细节，自动编写真实合理的提交说明，避免机械套用模板或编造内容。

##### 第一步：识别 Git 状态场景

根据 `git status` 的输出，AI 应识别以下三种典型场景：

| 场景 | Git 状态特征 | 说明 |
|------|-------------|------|
| **场景 A：未 add** | `Changes not staged for commit` | 代码已修改但未添加到暂存区 |
| **场景 B：已 add** | `Changes to be committed` | 部分或全部代码已添加到暂存区 |
| **场景 C：已 push（待修改）** | `Your branch is ahead of 'origin/xxx' by N commit` | 代码已推送到远程，需通过 `commit --amend` 修改描述 |

> **注意**：对于场景 C（已 push 到远程），由于涉及交互模式，无法通过命令直接修改提交说明，AI 应输出清晰的文字指引供用户手动执行。

##### 第二步：获取代码变更详情

根据识别到的场景，执行相应的命令获取变更内容：

**场景 A（未 add）或场景 B（已 add）**：

```cmd
::: 查看工作区状态，确认变更范围
git --no-pager status

::: 获取未暂存的变更详情（场景 A 必选）
git --no-pager diff

::: 获取已暂存的变更详情（场景 B 必选）
git --no-pager diff --cached

::: 获取变更文件的统计信息（了解改动范围）
git --no-pager diff --stat
git --no-pager diff --cached --stat
```

**场景 C（已 push，需 amend）**：

```cmd
::: 查看最近一次提交的完整信息
git --no-pager log -1 --format="%B"

::: 查看最近一次提交的代码变更
git --no-pager show HEAD --format="" -p -- <具体文件路径>
```

##### 第三步：分析变更内容并生成提交说明

AI 应基于获取到的代码变更内容，进行以下分析：

1. **确定变更类型**：功能新增、Bug 修复、代码优化、重构、接口调整等
2. **提取关键信息**：
   - 修改了哪些文件
   - 变更的核心逻辑是什么
   - 解决什么问题或实现什么功能
3. **生成结构化提交说明**：

```
RDC:<单号> <变更类型>: <简洁描述>
```

##### 第四步：场景处理细则

**场景 A（未 add）- 代码刚修改还未 add**

适用于：代码已修改但未添加到暂存区

处理流程：执行 `git status` 和 `git diff` 查看变更 → 分析变更内容 → 生成提交说明并告知用户 → 用户确认后执行 add、commit、push

**场景 B（已 add 一部分，其他不需关注）**

适用于：部分或全部代码已添加到暂存区

处理流程：执行 `git status` 查看已暂存和未暂存的变更 → 重点分析已暂存的变更 → 生成提交说明 → 告知用户"已暂存的变更将进入本次提交" → 用户确认后执行 commit、push

**场景 C（已 push，需通过 amend 修改描述）**

处理流程：
1. 执行 `git log -1 --format="%B"` 查看当前提交说明
2. 告知用户当前提交说明的内容
3. 通过 `git show HEAD -p` 或指定文件查看提交的具体变更
4. 基于变更内容生成新的提交说明
5. 输出文字指引（不执行命令）

> **注意**：`--force-with-lease` 是安全的强制推送方式，当远程分支在你上次 fetch 后有其他人提交时会拒绝推送，避免覆盖他人代码。
