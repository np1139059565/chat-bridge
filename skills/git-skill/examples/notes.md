## 注意事项

- **Cookie 使用方式**:把完整 Cookie 字符串直接写进每条 curl 的 `-H "Cookie: ..."`(详见 `auth-cookie.md`)。**严禁使用 `set` 环境变量方案**(`set` 具有延迟性,与后续命令用 `&`/`&&` 连接必然失败;且每条命令独立 shell,变量必然丢失)。
- **Gerrit 与本地 Git 的分工(重要)**:
  - **Gerrit API 为主,本地 Git 为辅。** Gerrit API 获取的才是"已推送到 Gerrit 的变更",是权威来源;本地 `git log` 仅能看到本地/已拉取分支,且可能滞后或遗漏未推送/其他分支的提交。
  - **以下场景必须先调 Gerrit API、严禁用本地 Git 替代**:用户要求"添加评审人 / 走查代码 / 对某个变更做操作"时,必须先获取变更列表拿到准确的 `CHANGE_NUMBER`。
  - **以下场景允许使用本地 Git 作为补充**:当 Gerrit 返回信息不足以完成任务时(例如 commit message 过简、需要看真实代码 diff、撰写工作/述职报告等),可切换到本地代码库用 `git log` / `git show` 补充细节。**但获取"我有哪些变更"时仍应以 Gerrit API 为准,本地 Git 仅用于细化内容。**
- **严禁在用户没有明确要求的时候使用 Git 操作/推送本地代码**
- **当用户要求添加评审人或走查代码时,必须阅读'智能补充评审人'章节,自行添加缺失的评审人,严禁再询问需要添加哪些人**
- 所有 Git 操作应在代码仓库根目录下执行
- 提交前请确认修改内容无误(`git diff` / `git status`)
- 推送前请先拉取最新代码(`git pull --rebase`),避免冲突
- 若需要交互式操作(如解决冲突),请在终端中手动处理,不要通过自动化命令
- **使用 curl 调用 Gerrit API 时**:
  - **响应前缀**:所有 API 响应均以 `)]}'\n` 这 5 个字符作为前缀(不是合法 JSON)。**落地处理**:把响应写入文件后用 read_file 读取时,需手动忽略开头 `)]}'` 这一行,从下一行起的 JSON 才是有效内容;若用脚本解析,需 `substr`/跳过前 5 个字符。**切勿把带前缀的内容直接当 JSON 解析。**
  - **URL 编码**:文件路径中的 `/` 需替换为 `%2F`,空格替换为 `%20`。CMD 中可使用 `set VAR=%VAR:/=%%2F%` 进行替换(注意百分号转义)
  - **变更号**:`CHANGE_NUMBER` 是纯数字(如 `25832328`),而非完整的 `project~branch~id` 格式
  - **权限**:添加评审人、发表评论、打分等操作需要当前用户具有对应权限（如成为变更的评审人或项目 Maintainer）
- **评审人补充策略**:每次提交代码后,应主动检查评审人列表是否满足"至少一位主评审人 + 至少一位领域评审人"的要求,若不满足则自动调用添加评审人 API 进行补充。主评审人优先添加"祝晶",领域评审人根据代码变更类型(后端/前端/测试)从预定义列表中选择。
