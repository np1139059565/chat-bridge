## 二、M1：图谱「0 节点 / 269 边」

### 现象
访问记忆图谱页，统计栏显示 `0 节点 / 269 边`，画布无任何图形。

### 根因
`routes/memory_graph.py` 的 `/memory/graph` 接口，节点与边取数范围不一致：

- 节点：`memory_nodes.list_by_conv(conv_id, site_key)` —— **按会话过滤**。
- 边：`memory_edges.all_edges()` —— **返回全库所有边**。

当 `conv_id` 为空（或该会话没有节点）时，节点查出 0 条、边却是全库的 269 条，于是出现「0 节点 / 269 边」，且没有节点可绘制。

### 修复方向
1. 让节点与边同口径：边也按 `conv_id` 关联的节点集合过滤；或
2. 明确约定「留空即全库」：不传 `conv_id` 时节点也返回全库。

推荐方案 1（按会话过滤），与页面输入框「会话 id（留空看全部）」的语义保持一致：留空时才两边都返回全库。

## 三、M2：前端抽屉未接入记忆图谱

### 现象
抽屉内没有进入记忆图谱的入口，也无任何图谱渲染。

### 证据
- 在 `extend/` 全目录搜索 `memory-graph` / `graph_export` / `radialTree` / `forceSimulation` / `d3.`，**零命中**。
- 前端对记忆接口仅有 3 处调用：
  - `/memory/conversation`（读写会话，见 `04_sessions.js`、`05h_memory_bridge.js`）
  - `/memory/conversations`（会话列表）
  - `/memory/conversation/delete`（删除会话）
- 图谱仅有一个后端独立页面 `flask_server/static/memory_graph.html`，需手动访问 `/memory-graph` 才能打开。

### 与设计的差距
设计文档《记忆机制改进方案》第八节要求前端 D3 力导向图 + 径向树。当前实现为后端原生 Canvas 页面，且前端无入口。

### 修复方向
1. 最低成本：抽屉加一个按钮，跳转/内嵌 `/memory-graph`。
2. 完整实现：在抽屉内实现图谱视图，调用 `/memory/graph` 取数渲染。

## 四、M3：「记忆告警提示」无实现

### 现象
用户反馈「记忆告警提示被去掉了」。

### 证据
- 前端搜索「告警」，仅命中**质量告警**：`05e_quality.js`（检查 AI 回复质量）、`05g_cards.js`（告警落点决策），与「记忆」无关。
- 无任何「记忆告警」相关代码。
- 设计文档《记忆机制改进方案》未定义「记忆告警」功能。

### 结论
当前代码中不存在「记忆告警」的任何痕迹：要么是改造前更早移除，要么改造后从未实现。需确认该功能的原始定义，再决定是否重建。

## 五、M4：蒸馏（自动写记忆）疑似不触发

### 链路现状（理论已接通）
前端保存会话 → `POST /memory/conversation` → `memory_conversations.save_conversation()` → `routes/memory_graph.py` 的 `_distill_new()` → `memory_distill.distill_async()`。

边已成功写入（269 条为证），说明保存链路在跑。

### 疑点
`_distill_new()` 的逻辑为：

```
nodes = memory_nodes.list_by_conv(conv_id, site_key or None)
pending = [n["id"] for n in nodes if not n.get("essence")]
if pending:
    memory_distill.distill_async(pending)
```

- `list_by_conv` 要求 `conv_id` 与 `site_key` **同时匹配**。
- 若前端上送的 `site_key` 与写库时不一致，则查出 0 个节点，`pending` 为空，蒸馏永不触发，节点 `essence` 永远为空 —— 表现为「AI 从来不写记忆」。

### 验证方法（待执行）
比对数据库中 `nodes.conv_id` / `nodes.site_key` 的实际取值，与前端 `memSaveConv` 上送值是否一致。

### 修复方向
统一前后端 `site_key` 约定；或在 `_distill_new` 中放宽匹配（例如按 `conv_id` 单独取待蒸馏节点）。

## 六、V1：语音播放卡死约十秒

### 日志证据
`data/logs/app-2026-10-06.log` 中 watchdog 两次抓到「卡死现场」（03:56:47、04:02:05），堆栈指向同一处：

```
edge_tts/communicate.py:613 in save
    async for message in self.stream()        ← 卡在这里，等待 websocket 数据
remote_bridge/voice_tts.py:118 in text_to_voice
    fut.result(timeout=SYNTH_TIMEOUT + 10)    ← 阻塞等待
web_bridge/web_mirror.py:84 in synthesize_voice
    ← 由 _auto_synth 调用
```

### 机制分析
`remote_bridge/voice_tts.py` 的设计：
- 所有合成请求共用**同一个长期事件循环线程**（`_loop_thread_main`，循环只建一次、永不销毁）。
- 单次合成用 `asyncio.wait_for(comm.save(...), timeout=SYNTH_TIMEOUT)` 做超时（`SYNTH_TIMEOUT = 20`）。
- 外层 `fut.result(timeout=SYNTH_TIMEOUT + 10)` 阻塞等待。

问题在于：`edge_tts` 的 `save` 底层是 websocket 收流，`wait_for` 超时后**未必能真正取消该协程**。堆栈显示协程仍挂在 `stream()` 上，说明取消未生效，事件循环被这个死协程占住。由于循环只有一条，后续合成全部排队，叠加信号量 `MAX_CONCURRENT_SYNTH=3` 与外层超时，表现为服务端卡住约十秒。

### 补充
- 点播接口 `/api/web/voice-ensure` 与后台 `_auto_synth` 均为**开线程异步执行**，本身不阻塞请求线程。
- 卡顿源自被占住的共享事件循环，而非接口同步等待。

### 修复方向（择一或组合）
1. 每次合成使用独立事件循环/独立线程，避免单个死协程拖垮全部合成。
2. 为共享循环加看门狗：检测到长时间无响应则重建循环。
3. 在协程内部对 `stream()` 设置更底层的超时与强制关闭（如显式关闭 websocket 连接）。

## 七、修复优先级建议

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | M1 | 改动小、见效快，直接修复用户可见的图谱异常 |
| P0 | V1 | 影响服务可用性，卡死会拖累其它功能 |
| P1 | M4 | 决定「AI 是否写记忆」，需先做数据比对坐实 |
| P2 | M2 | 功能补全，工作量取决于是否前端化 |
| P2 | M3 | 需先确认功能原始定义 |
