# 多通道重构进度（3c）

## 目标

把 QQ / 微信 / 企业微信三条通道的重复实现收敛到公共层，
每个通道只保留「连接与协议差异」的少量适配代码。

## 现状盘点

`remote_bridge/` 原有 41 个文件、约 1 万行，三通道各有一套实现：

| 职责 | QQ | 微信 | 企业微信 |
|---|---|---|---|
| 客户端 | qq_client.py | weixin_client.py | wecom_client.py |
| 网关 | qq_gateway.py | weixin_gateway.py | wecom_gateway.py |
| 推送分发 | message_router.py | weixin_router.py | wecom_router.py |
| 协议 | qq_event_parse.py | weixin_proto.py | wecom_proto.py |
| 媒体 | qq_media.py | （复用 weixin_client） | wecom_media.py |
| 文件 | qq_files.py | — | wecom_media_collect.py |

## 重复点清单

1. **最近用户兜底**：各通道各写一份，都要持久化。
2. **已推集合去重**：命名空间不同，但「读集合 → 差集 → 写回」流程一样。
3. **推送串行锁**：QQ 按会话分锁，微信用全局 RLock，企微无锁。
4. **配额窗口**：QQ 是 60 分钟被动回复窗口，微信是「每条用户消息一个约 10 条回复池」，企微无限制。
5. **媒体上传**：各通道自己的上传格式与重试。

## 目标架构

```
remote_bridge/
├── channel/                 # 公共层
│   ├── adapter.py           # 通道适配器协议
│   ├── push_pipeline.py     # 推送管线：去重 → 组装 → 发送 → 记账
│   ├── dedupe.py            # 已推集合（按通道命名空间）
│   ├── quota.py             # 配额策略
│   └── target.py            # 最近用户兜底与持久化
├── adapters/                # 各通道适配器
│   ├── qq.py
│   ├── weixin.py
│   └── wecom.py
└── （其余既有模块保持不动，逐步改为调用公共层）
```

## 本轮附带修复（非 3c 范围，但已提交）

1. **卡片刷新后退回待执行**
   代码块 id 是内容指纹，网页重新渲染后同一调用得到新 id，
   新卡片匹配不到旧状态而重置为 pending。
   改用「消息指纹 + 工具名 + 参数」组成执行签名，建卡时据此恢复。
   **待验证**：刷新页面后卡片是否保持已执行态。

2. **纯媒体批次被整批丢弃**
   管线在合并文本为空时直接 return，若这批全是图片 / 语音则全部发不出去。
   改为仍走一次媒体发送。已用纯图片批次验证通过。

3. **外部指令定向到当前页面**
   外部指令下发时未传 page_url，命令变成「公开命令」，多标签时可能被
   后台标签取走。已补 open_pages() 查询并定向。
   **未验证**：`/dc` 是否恢复。

## 下次继续时的验证清单

按优先级排列，逐项确认后再进入阶段六清理：

| 编号 | 验证项 | 预期 | 失败时排查方向 |
|---|---|---|---|
| V1 | 刷新页面后工具卡片状态 | 保持已执行，不退回待执行 | 已通过：签名库随存档落盘并在读档时恢复，重启后仍能命中 |
| V2 | 企业微信收 AI 文本回复 | 正常收到，格式与改造前一致 | 检查 use_pipeline 开关与适配器日志 |
| V3 | 企业微信收图片 | 图片能显示 | push_media 是否被调用、req_id 消费 |
| V4 | 企业微信收语音 | 语音能播放 | TTS 引擎是否就绪、synth_pending 返回 |
| V5 | QQ 收消息（文本 / 图片 / 语音） | 与改造前一致 | 窗口是否有效、去重 key 是否冲突 |
| V6 | 单独发一次 /dc（抽屉打开） | 抽屉关闭，日志出现「取走本页面命令」 | 若仍「逸散取走」则目标页登记有问题 |
| V7 | bridge.use_pipeline 设为 false 后重启 | 退回旧链路，推送恢复 | 用于新链路出问题时的紧急回退 |

**回退方法**：在 `flask_server/config/runtime.yaml` 的 `bridge:` 分区下加一行 `use_pipeline: false`（当前该分区未配置此项，缺省即走新管线），重启服务即可。

## 验收标准

- 三条通道的推送行为与改造前一致（V2–V5 全通过）
- remote_bridge 文件数下降（阶段六完成后）
- 新增一个通道只需实现适配器协议，不改公共层

## 风险

- 推送链路涉及真实账号，回归须谨慎
- 配额与窗口语义各通道不同，抽象时不能抹平差异，只能把差异收敛到策略对象
- 当前处于双轨并行状态：新管线在跑，旧 router 仍在仓库中，代码量暂时比改造前多
