## 一、原始需求（用户提案，原样保留）

1. 拆分「网页 AI 站点配置」：不再统一渲染全部配置，根据访问 URL 动态展示对应站点的配置内容，实现按站点隔离。
2. 公共配置增加浏览器持久缓存机制：
   - 用户修改配置时，变更优先写入浏览器缓存（刷新页面不丢失本地修改），不直接写入后端配置文件；
   - 用户点击【覆盖】按钮（新增），才将当前配置提交后端，覆盖服务端配置文件，遵循**新配置覆盖旧配置**原则；
   - 页面每次刷新时，主动拉取后端最新配置；依靠配置自带的时间戳做版本比对，遵循**新配置覆盖旧配置**原则；
   - 补充约束：所有配置项都需要增加时间戳字段，用于版本判断。

## 三、漏洞清单

### P0：不解决就会丢数据 / 功能不成立 / 越界

**V1 · 两条需求语义互相矛盾（最核心）**
「刷新不丢本地修改」要求本地草稿优先；「刷新拉后端、新覆盖旧」要求新版本优先。二者放进同一套时间戳比较时：本地未覆盖草稿的时间戳永远新于后端基线，后端更新永远进不来；一旦另一台机器/标签页点了【覆盖】使后端时间戳反超，刷新又会静默吞掉本机未覆盖的修改。
**本质**：草稿是「待提交态」，服务端是「已提交态」，语义不同，不能靠时间戳定胜负。
**影响**：多页面共享名存实亡，用户丢改动且无任何提示。

**V2 · 整集覆盖的 last-write-wins**
`POST /config` 的 `profiles` 是整集替换。A 页面改 `glm`、B 页面改 `deepseek`，各自缓存各自点【覆盖】，后提交者用自己那份整集快照把前者冲掉；时间戳若只加在整集粒度，判不出单站点冲突。
**影响**：并发编辑必丢一方，且无冲突提示。

**V3 · 时间戳字段会被后端直接丢弃**
`sanitize_profiles` 只收 `str / bool / list[str]`，`applyProfiles` 同样只校验这三种类型。时间戳若为数字（epoch ms）→ 写盘与下发时被丢；若为 ISO 字符串 → 能留下，但会被 `PROFILE_FIELD_META` 当成未知自定义字段渲染成可编辑输入框、被 `serializeProfilesDraft` 当业务值提交、可能被用户误改；若用嵌套 `{value, ts}` → 嵌套对象一律丢弃。
**影响**：「所有配置项都带时间戳」在现链路上根本不成立，需连锁改后端规整、前端应用、字段元表、序列化四处。

**V4 · 「所有配置项」范围爆炸 + 凭证进缓存**
`GET /config` 还含 `flask` / `limits` / `default_profile` / `tools` / `tool_config` / `system_config` / `site_profiles`，其中运行时配置文件（gitignore）承载凭证、推送开关、端口，且 `site_profiles` 是派生字段。若「公共配置」不划白名单就整体缓存，等于把不入库的密钥写进 `chrome.storage.local`（明文可读），并给派生字段也盖时间戳造成双真源。
**影响**：安全边界 + 配置漂移。

### P1：体验 / 一致性 / 竞态

**V5 · 客户端时钟不可信**：浏览器 `Date.now()` 可回拨、跨机器不一致；快 1 小时的机器旧改动会被判成「新」，永久压住他人新改动。建议由服务端盖单调递增 `revision`，本地 `mtime` 只用于展示与冲突提示，不参与胜负判定。

**V6 · 按 URL 渲染的五个边界**：① `request_page` 是异步的，配置先到、URL 未到时会渲染 0 个站点或白屏，需 fallback；② 未登记站点实际兜底 `glm`（历史事故见待办清单「千问被按 GLM 解析」），应显示**实际生效档案 id** 而非 URL 字面量，并显式提示「未登记」；③ 只显示当前站点后，跨站点「新增/管理」入口会消失，需保留独立管理模式；④ `hosts` 多域名（如 `www.kimi.com` 与 `kimi.com`）归一化口径要与 `guessProfile` 的 `endsWith('.'+host)` 对齐；⑤ 同一标签页 SPA 切站时 `page_url` 变化，草稿须按站点分键存，不能串。

**V7 · 【覆盖】按钮语义歧义**：按钮名叫「覆盖」，却又要求「遵循新配置覆盖旧」——若服务端此刻更新（他人已提交），按钮到底覆盖不覆盖？并发、网络失败、冲突时草稿能否保留（否则「刷新不丢」被破坏）都未定义。建议按钮语义改为「提交草稿」，携带 `base_revision`，服务端不一致时返回冲突并展示差异，由用户决定强制覆盖；「新覆盖旧」只用于**自动拉取**场景。

**V8 · 草稿态与运行时档案的关系未定义**：现状改完立即 `profiles_refresh` 热更新，用户改选择器马上能验证；改成只写缓存后，点【覆盖】前内容脚本仍用旧档案，用户会以为「改了没生效」。`testProfileField` 本就用当前编辑值试运行，不受影响。需明确：草稿只影响设置页预览与试运行，**运行时档案仍以后端 `/profiles` 为唯一权威**，并在 UI 上给出「未覆盖」可见状态。

**V9 · 时间戳粒度与存储形状**：字段级（`container_ts` 旁挂）、档案级（`_meta`）、整集 envelope（`{profiles, rev}`）三种方案的改动量差一个量级；字段级会污染字段元表，档案级需改 `sanitize` 放行，整集 envelope 改动最小但判不出单站点冲突。需先定粒度再动代码。

### P2：工程提醒

**V10 · 别拆掉既有保护**：`01_backend.js` 的 `_siteProfLoaded` 守卫已经在防「刷新冲掉编辑中草稿」。新方案应沿用「刷新只更新服务端基线快照、草稿独立保留」的语义，而不是把刷新实现成覆盖草稿。

**V11 · 文档门禁**：`doc-sync` 会扫 `docs/` 下全部 Markdown 的路径引用，且当前 HEAD 已自带 2 项运行时配置路径未收录的欠账（上一轮提交实测）。新文档措辞避免新增带目录前缀的运行时配置路径串；提交时按既有归因豁免处理，不要为过闸去改无关文档。

## 四、建议方向（v2，已作废，仅保留推理历史）

> **作废说明（2026-11-09）**：本节「三层模型 + 服务端单调 revision」已被第八节方案 v3 取代。
> v3 不再引入时间戳 / 版本号 / 时钟，改由「刷新并排标差异 + 【还原】/【覆盖】人工确认」解决冲突。

1. **分三层**，不再让草稿与权威同台比时间戳：
   - 服务端基线（权威）：带服务端 `revision`，刷新时拉取；
   - 本地草稿（编辑态）：按站点分键存 `chrome.storage.local`，带 `mtime`，仅用于展示与「有未覆盖修改」提示；
   - 运行时档案（内容脚本）：只认后端 `/profiles`，不读浏览器缓存。
2. **两个动作分开**：自动拉取用「新覆盖旧」；用户点按钮是「提交草稿 + base_revision 冲突检测」，冲突显式化，失败保留草稿。
3. **版本用服务端单调 revision**，时间戳退为展示/审计字段，避免客户端时钟决定胜负。
4. **缓存白名单**：只缓存入库的定义分区（站点档案、体积上限、默认档案），运行时配置（含凭证、端口、工具开关）与派生字段不进缓存。
5. **时间戳粒度**：先做整集/档案级 envelope，字段级 LWW 列为可选增强并单列成本。
6. **按 URL 隔离**用 `guessProfile` 的实际结果选渲染目标，保留「管理全部站点」入口，URL 未到时给明确 fallback。

## 八、方案 v3：差异可视化 + 人工确认（当前候选，待拍板）

> 用户于 2026-11-09 提出，用于**取代**第四节 / 第五节的 v2 版本号思路。
> 本节仍属评审记录，代码零改动；实施前需拍板 N1 与 D1–D3。

### 8.1 方案原文

1. 后端只保留一份母版。前端刷新时先拉取后端当前配置，与本地缓存按项对比（每个 AI 页面存一份，「网页 AI 站点配置」只显示适配的即可）；与本地不一致的项标颜色区分，旁边附【还原】按钮，可按服务端配置还原。
2. 点【覆盖】时先弹提示，明确影响范围并**分开提示**：公共配置会覆盖所有页面；「网页 AI 站点配置」各页面独立，不存在覆盖其它页面的说法，只可能覆盖**其它电脑同一个页面**的配置。确认后才写后端。

### 8.2 本质：把「自动裁决」换成「人眼裁决」

不再比时间戳 / 流水号 / 时钟，谁也不自动盖谁：刷新只做「拉后端 + 并排标差异」，两边数据都不动；用户要么点【还原】用服务端值覆盖本地，要么点【覆盖】用本地值写后端。冲突不再由程序判定，而是摆出来由人确认。
比喻：柜台只留一本母本；桌上按店分页夹着便签；每天早上领一份复印件与便签并排摊开，不一样的行画荧光；旁边两个方向相反的按钮——【还原】按柜台擦便签，【覆盖】把便签誊抄进柜台（先递条子分两栏写清影响范围）。没有章。

### 8.3 关闭 / 残留对照

| V3 时间戳被 sanitize 丢弃 | 关闭 | 不加时间戳；连带后端放行 / applyProfiles 白名单 / 字段元表排除 / 序列化排除四处连锁改动全部取消 |
| V5 客户端时钟不可信 | 关闭 | 无时钟 |
| V2 整集覆盖冲掉他人修改 | 基本关闭，前提是 D2 | 覆盖须按站点分区提交，不能再整集替换 |
| V4 凭证进缓存 | 待 D3 划白名单 | 用户已区分「公共配置 / 站点配置」，但缓存边界未点名 |
| V9 版本粒度与存储形状 | 大幅简化 | 无需版本表与版本字段 |

### 8.4 必须补的前置 N1：本地要留一张「没动过的旧复印件」

本地缓存若只有一份（即被改过的草稿），拿它直接跟后端比，用户自己改的每一行都会被标成「不一致」：分不清「我改的」与「别人也改了」，点【还原】会把未提交改动一起冲掉，真正的两边都改也显示成同一种色。
补法只多一张纸：本地再存一份 `base`（上次与服务端对齐时、未改动的原样快照），三张纸一起按「配置键路径」逐项比：

| draft | base | backend | 含义 | 标色 |
|---|---|---|---|---|
| 改了 | 原样 | 原样 | 只有我改了（未提交） | 本地修改 |
| 原样 | 原样 | 变了 | 只有服务端变了，可放心还原 | 服务端更新 |
| 改了 | 原样 | 也变了且三者不同 | 两边都动，真冲突 | 冲突，必须人选 |

**关键细节**：`base` 不得随刷新更新为 backend，它只在【还原】或【覆盖】成功后重置为当时的服务端值；刷新只更新 `backend`。否则「服务端刚变过」的信息当场被抹平，第二类判不出来。这恰好复活了 `01_backend.js` 中 `_siteProfLoaded` 的既有语义（刷新只更新快照、不覆盖草稿），只是把快照明确成锚点。
实现二选一，均远轻于版本号：(a) 存整份 `base` 快照（配置量小，推荐）；(b) 只记被改动键的原值（更省，逻辑稍绕）。
