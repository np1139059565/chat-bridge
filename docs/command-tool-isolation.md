# 指令与工具的隔离铁律（chat-bridge）

> 状态：强制规范。改动任何涉及「指令」「工具」「卡片回传」的代码前，先读本文。
> 目的：指令与工具**严禁任何形式的互相入侵**。此坑已多次复现，根因是缺乏权威文档，
> 每换一处代码就重新踩一遍。本文即防再犯的权威依据。

---

## 一、两个概念，两个归属

| | 指令（command） | 工具（tool） |
|---|---|---|
| **谁用** | 用户（通过 QQ / 网页机器人） | AI（模型调用） |
| **声明位置** | `tool.json` 的 `commands` | `tool.json` 的 `tools` |
| **执行端** | `command_actions` 数组 | `tools` 数组（同一批） |
| **下发通道** | 卡片总线 `drawer-command` | 卡片总线 `external-call` |
| **回执去向** | QQ / 网页收件箱 | 网页 AI（作为工具结果） |
| **能否进 AI 工具目录 / System Prompt** | **否，绝对禁止** | 是 |
| **能否流向 AI** | **否，任何情况都禁止** | 是（这是它的用途） |

一句话：**指令归用户，工具归 AI。指令的任何东西都不得流向 AI。**

---

## 二、铁律（违反即为严重缺陷）

R1. **指令不得出现在任何「给 AI 看的」清单里**：`/tools`、System Prompt、
    未知工具提示的 `available` 列表、`get_tool_params` 的可用清单。
R2. **指令执行产生的任何东西不得流向 AI**：包括执行结果、执行失败、错误堆栈、
    网络异常（如 `Failed to fetch`）、中间状态。这些只能推给 QQ / 网页机器人。
R3. **指令与工具不得混放在同一数据数组**：源头分开——`tools` 只放 AI 工具，
    `command_actions` 放指令执行端，`commands` 放指令声明。三者各司其职。
R4. **不得用标记字段区分指令与工具**：曾用 `command_only: true` 标记，
    靠视图层过滤，极易漏过滤。改为源头分开（按所在数组自动标注来源身份）。
R5. **指令执行端与 AI 工具共用执行通道，但不得共用展示通道**：
    执行通道共用（避免重复实现），展示/回传通道必须分开。

---

## 三、隔离机制（现状如何实现）

1. **声明层**：`tool.json` 三数组并列——`tools`（AI 工具）/ `command_actions`
   （指令执行端）/ `commands`（指令声明）。
2. **加载层**：`custom_tools/loader.py` 的 `parse_skill` 按条目所在数组自动标注
   `kind`（`tool` / `command_action`），前端与后端据此天然分流。
3. **视图层**：所有「给 AI 看的」视图（`meta.all_meta`、`external_tools.provider_tools`、
   `prompt_sections`）只取 `kind=tool`。设置页视图只取 `kind=tool`，指令执行端不进设置页。
4. **执行层**：指令执行端仍注册进 provider hub（`find_tool` 能找到），
   但 `provider_tools()`（给 AI 的目录）过滤掉它——执行通道共用，展示通道分开。

## 四、所有「指令可能流向 AI」的路径（改动必查）

以下每一处都是历史上的泄露点，改动相关代码时必须逐一核对：

| # | 路径 | 文件 | 防护 |
|---|---|---|---|
| 1 | 工具目录 `/tools` | `routes/tools.py` | 只取 `kind=tool` |
| 2 | System Prompt 技能清单 | `core/prompt_sections.py` | 只取 `kind=tool` |
| 3 | 未知工具可用清单 | `routes/tools.py`、`tools_impl.py` | 只取 `kind=tool` |
| 4 | 设置页工具列表 | `routes/custom_tools.py` → `meta.all_meta_full` | 只取 `kind=tool` |
| 5 | 指令卡片漏消费 | `dialog/parts/01_backend.js` | `drawer-command` 黑名单拦截 |
| 6 | 指令结果 / 失败回传 | 见下「回传通道」 | 指令回执走 `/api/bridge/result`，不进 AI |

---

## 五、回传通道：指令与工具的分界

**工具回传**（合法，进 AI）：
- AI 调用工具 → 工具卡片 → 执行结果/失败 → 经 `postCardResult` 回传网页 AI。
- 失败分两类：AI 能改的（参数错、工具代码缺陷）回传；环境/网络类（服务未起、
  连接中断）**不**回传，因为 AI 改不了、只会污染上下文。

**指令回执**（禁止进 AI）：
- 用户发指令 → `drawer-command` 卡片 → 前端执行本地动作 → 回执经
  `/api/bridge/result` → QQ / 网页收件箱。
- **绝不**经 `/tool`、绝不产生工具卡片、绝不调用 `postCardResult`。

**判别口诀**：这条东西是「AI 主动调用的」还是「用户发指令触发的」？
- AI 主动调用 → 可以回传 AI。
- 用户发指令触发 → 只能回用户（QQ / 网页），**任何情况都不进 AI**。

## 六、新增功能时的自查清单

改动涉及指令或工具时，逐条核对：

- [ ] 新增的工具是指令执行端还是 AI 工具？放对数组了吗？
- [ ] 新的「给 AI 看的」清单，过滤了 `kind != tool` 吗？
- [ ] 新的回传逻辑，来源是指令还是工具？指令来源绝不进 AI。
- [ ] 指令执行失败时，错误会不会被包装成工具结果回传？
- [ ] 有没有用「标记字段 + 过滤」的旧写法？应改为源头分开。

## 七、历史事故（引以为戒）

1. `open_drawer` 等 5 个抽屉控制工具混进 `/tools` 与 System Prompt（指令入侵工具目录）。
2. 指令执行端出现在设置页工具列表（用户报「指令入侵工具列表」）。
3. 指令执行产生的网络错误（`Failed to fetch`）回传给了 AI（指令流向 AI）。

共同根因：缺一份权威的隔离规范，改动时无据可依。本文即为此而写。
