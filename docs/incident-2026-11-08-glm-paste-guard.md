# 事故记录：2026-11-08 GLM 回传粘贴卡死（生成态误判 + 冲刷死代码）

## 现象与影响

自动执行单 ef5791c 验证轮次：GLM 页面只粘贴了文本、没有回车，消息未发出，文本滞留输入框。日志链：

    发送队列入列: auto_send 待发=1
    收到消息 type=auto_send
    [生成态] 翻转 false → true          ← 粘贴文本后「生成态」误判出现
    回传中: AI 生成中，回传挂起; 文本回传（回车前拦截）   ← enter_only 挂起
    风控恢复: 未识别到停止状态（…均不成立）
    多次重试未命中停止状态; 放弃本轮      ← 只识别不恢复，卡死无人解

## 根因（两层叠加）

**① 生成态判据假阳性（根子）**：GLM 判据 .enter.is-main-chat.m-three-row 本意「多行输出=生成中」，但输入框被写入多行文本时输入区同样变高、m-three-row 同样出现。ef5791c 之前无条件回车，消息发出→输入框清空→类名消失，假阳性被旧逻辑掩盖；守卫上线后暴露：粘贴多行文本→误判生成中→守卫二挂起补回车→文本滞留→类名持续命中→**死锁闭环**（页面实际空闲）。

**② 冲刷函数死代码（帮凶）**：_flushPendingPaste 的 30s 超时清收放在 if (A.state.isGenerating) return 门**之后**。生成态一旦误判卡死，每秒轮询全在门口返回，超时分支永远执行不到，enter_only 条目无限搁浅。

## 修复

| 文件 | 改动 |
|---|---|
| extend/content/03b_paste.js（自 03_bridge.js 拆出） | 超时清收前移到生成态门之前（到期条目无论状态先如实放弃上报，卡片可重新执行补救）；挂起上限 30s→120s（正常生成常超 30s，原值会误杀合法挂起） |
| extend/content/00_state.js | GLM profile 新增 generatingRequireEmptyInput: true |
| extend/content/04_observer.js | 选择器命中后校验输入框为空（生成中输入框必为空——文本已随发送清空）；命中但有内容→判空闲 |
| extend/content/05_index.js | BUILD_TAG → 2026-11-08-genstate-fix-v13 |

**取舍说明**：生成期间用户手动输入会使判定翻回空闲（假阴性），此时粘贴不挂起；GLM 生成中本就允许输入排队发送，假阴性危害远小于死锁，可接受。

## 教训

1. 用 UI 状态类名做生成态判据，必须确认类名的**唯一性**（仅生成中出现）；m-three-row 这类随内容变化的布局类不满足。
2. 超时/放弃等保底路径不得放在可能**永久不翻转**的状态门之后——否则保底即死代码。
3. 挂起上限必须大于正常业务时长（生成长达数分钟≠故障），误杀会制造假失败。
4. 文档内容含三反引号会顶破桥接卡片的外层围栏（本次两次「格式错误」的真正原因）：经桥接通道写文档，代码引用一律用缩进块。

## 补充观察：清空会话后重解析卡片触发 quality_report 连环报（2026-11-08 晚）

现象：GLM 页清空会话内容后，对已执行卡片点「重新解析」，quality_report（voice_missing）连报 4-5 次；每次 msg_id 均为新值（属新建消息而非重放缓存），且每条报告自身会终止当次回音（「本次回音已被终止」），被重解析的卡片命令始终没有机会执行。

机理推测：重解析会让质量门对历史回复重新体检，凡缺 bridge-voice 块的历史回复各生成一条新报告——清空前缺语音的回复有几条就连环报几条；报告又终止回音，重解析动作本身因此也总是被掐断。

规避：
1. 含 run_command 卡片的回复必须同时携带 bridge-voice 块（源头杜绝 voice_missing，历史也因此对重解析安全）；
2. 清空会话后不要直接重解析旧卡片，改为重新发起同内容请求；
3. 连环 quality_report 属桥接产品侧行为，已在 docs/pending-tasks.md 登记跟进。
