# 多通道通用化清单

## 一、判定原则

三条通道（QQ / 微信 / 企业微信）的能力差异应当只出现在「接发瞬间的协议编码」。
凡是不涉及协议本身、却写死走某一条通道的实现，都属待通用化项。

需要区分三类情况，避免把合理的适配层当成缺陷：

| 类别 | 特征 | 处理 |
|---|---|---|
| 真正的通道专属 | 硬编码调用某通道的客户端、窗口机制、用户标识来源 | **必须通用化** |
| 签名兼容适配层 | 各通道实现同名方法（如 `send_c2c`）以适配统一调用点 | 保留，属设计所需 |
| 通道固有差异 | 窗口机制、配额、帧格式 | 收敛到适配器策略，不改公共流程 |

## 二、已发现缺陷

### D1 文件推送工具只支持网页与 QQ

- **位置**：`tools/push_file_impl.py`
- **现象**：仅判断 `active_channel.is_web()`，非网页一律走 QQ 分支，
  使用 `message_router.get_last_client()` 与 `get_last_openid()` 取发送句柄与目标。
- **影响**：从企业微信发起时，文件被推到 QQ，企业微信收不到；
  且发送目标取决于「QQ 侧是否有人刚说过话」，与发起通道无关。
- **验证**：从企业微信调用，返回 `target: QQ`，文件未出现在企业微信。

### D2 指令回执依赖 QQ 的序号分配器

- **位置**：`remote_bridge/command_dispatch.py` → `_reply()`
- **现象**：以 `client.needs_window` 区分通道。QQ 走 `message_router.next_seq()`
  取窗口与序号；其它通道走不带窗口参数的发送。
- **影响**：当前行为正确（企业微信 `needs_window = False`，走无窗口分支），
  但通道判断依赖客户端实例上的一个布尔属性，新增通道时容易漏设而退化为走 QQ 分支。
- **性质**：隐患，非现症。

### D3 推送目标存在两套来源

- **位置**：`remote_bridge/message_router` 的 `_last_client` / `_last_openid`（QQ 专属）
  与 `remote_bridge/channel/target.py` 的 `TargetStore`（三通道通用）
- **现象**：同一语义「最近跟谁说话」有两套存储。新代码用后者，旧代码用前者。
- **影响**：调用方若取错来源，会把消息发给另一条通道的用户。

### D4 企业微信多轮收不到文字回复 —— 已修复

**根因**：`flask_server/remote_bridge/adapters/wecom.py` 调用了 `log()`，
但既未定义也未导入，媒体发送的失败分支一进入就抛 `NameError`，
整个推送流程被异常中断。日志里累计 33 条 `name 'log' is not defined`。

**为何长期未发现**：`_send_media` 的失败分支从未被任何测试覆盖，
78 个用例只走成功路径，而 `log()` 恰好只在失败路径上被调用。

**修复**：补上 `bridge_log` 导入与 `log()` 函数；管线日志加通道名与接收方，
使后续能直接看出是哪条通道发给了谁。

**验证**：日志出现 `[wecom] 合并推送成功 3 条 recipient=...`，用户确认收到。

### D5 卡片结果无限重放 —— 已修复

**现象**：同一条工具调用结果被反复回传，累计出现 6 次，且频率上升。

**根因**：前端 `consumeOneCard` 中，本地已存在同 id 卡片时直接 `return false`，
**未调用 `confirmCardDelivered`**。后端设计为「未确认的卡片可被反复取走」，
于是确认失败一次之后，该卡片永远停在未确认状态：每轮轮询都被取走，
每次都被去重分支挡回，形成无限重放。

**修复**：去重分支补上回执——本地已有该卡恰说明它已展示过，正是应当确认的时刻。

### D6 文件推送的通道分派 —— 已修复

**原状**：`flask_server/tools/push_file_impl.py` 只判断 `is_web()`，
非网页一律走 QQ 分支，从企业微信调用时文件被推到 QQ。

**修复**：改为按活跃通道名分派——web 走下载目录，wecom 走主动推送
（目标取 `flask_server/remote_bridge/channel/target.py` 的最近用户），
weixin 明确返回「暂不支持」，不再跨通道代发。

**同时补充测试**：新增 5 个用例覆盖企微成功 / 失败 / 未连接 / 无会话，
以及微信通道明确拒绝。此前该分支零覆盖。

### D4 原始排查记录（保留备查）

- **现象**：用户从企业微信连续发送多条消息，入向正常（日志有「收到消息」「已投递卡片」），
  但出向文字一条都收不到。
- **已观察线索**：
  1. `active_channel` 取值长期停留在 `qq`，用户从企业微信发消息后未更新为 `wecom`。
  2. 同期日志中出现大量 `[bridge][router] 窗口已关闭，暂不推送`——这是 QQ 旧链路的失败记录。
  3. 14:20 之后没有任何管线特征日志（合并推送成功 / 配额用尽 / 推送异常等）。
  4. 去重状态文件里有大量 `@wecom` 命名空间的记录。
- **初步判断**：消息可能被去重集合判为「已推过」而跳过；或广播逻辑未按预期对两条通道各发一份。
- **待排查方向**：
  1. 核对 `active_channel.note()` 在企业微信网关里是否被调用，为何值未变。
  2. 核对广播开关在运行期是否真的读到 `True`（配置已落盘，但进程可能仍是旧值）。
  3. 核对管线里 `_wants(target, channel, broadcast)` 的实际入参。
  4. 核对去重集合的会话键：抽屉上报的 `conversationId` 与 `@wecom` 后缀拼接是否稳定。

### D6b 图文混排被拆成多张卡片 —— 已修复

**现象**：企业微信发一条「多图 + 多文字」消息，扩展面板里出现 1 张文字卡 + N 张图片卡，
全部独立待执行，图文归属丢失、贴图顺序错乱。

**根因有两层**：
1. 入口处 `if not text:` 先判文字——而平台在 mixed 消息顶层也带文字，
   于是直接走文本分支，**整条消息里的图片被跳过**。
2. 即使进了 mixed 分支，也是给每张图单独调 `_handle_media`，
   每次投一张独立卡片，4 张图 = 4 张卡。

**修复**：
1. `msgtype == "mixed"` 时**优先**处理，不再先看有没有文字；顶层文字与子项文字合并。
2. 图片先全部下载落盘，再与文字一起投成**一张**卡片（`data_urls` 数组，前端一次贴多张）。

**验证**（20:16:45 实测）：
```
mixed 子项：count=4 detail=[('image',...), ('text',...), ('image',...), ('text',...)]
图文消息已投递 文字长度=17 图片数=2
[delivery] 已投递图片卡片 00963621 张数=2
```
一次投递、两张图、文字随行。用户确认前端显示为一张卡片。

### D6c 卡片投递各自实现 —— 部分修复

**问题**：三份网关各写一套 `_deliver_as_card` / `_deliver_image_card`，
能力不一致。企业微信漏了多图支持，正是 D6b 的成因之一。

**已完成**：新增 `flask_server/remote_bridge/channel/delivery.py`，
提供 `deliver_images` / `deliver_file` / `deliver_text` 三个公共函数。
图片投递已迁完三条通道（QQ / 企业微信 / 网页版）。

**仍未迁移**：
- 文本卡片：`qq_gateway` / `weixin_gateway` / `wecom_gateway` / `web_bridge` 各一份；
- 文件卡片：`qq_files.py` 一份、`wecom_gateway` 一份。
公共层的对应函数已就绪，只差替换调用点。

### D7 企业微信缺少 Markdown 渲染 —— 待修复

**现象**：同一条 AI 回复，QQ 与企业微信收到的内容形态差异明显，QQ 侧更优质。
企业微信收到的文本没有 Markdown 格式（加粗、列表、代码块均不渲染）。

**待查方向**：
1. 企业微信的 markdown 消息类型是否有独立格式要求（如 `msgtype: markdown` 与
   普通 `text` 的差异、是否只支持子集语法）。
2. 当前发送用的是 `send_markdown`，但内容可能被平台按纯文本处理，
   需确认帧里 `msgtype` 的实际取值与平台文档是否一致。
3. 表格类内容已被转为纯文本列表（见 D 系列修复），但其它 Markdown 语法
   （标题、粗体、代码围栏）是否同样需要降级，需按平台能力逐项确认。

### D8 消息块的组织顺序与折叠要求 —— 待实现

**目标结构**（按消息类型分别规定）：

AI 消息：
1. 思考内容（默认折叠）
2. 文本消息
3. 工具调用（折叠）
4. 语音块

工具消息：
1. 媒体文件
2. JSON 内容（折叠）

用户消息：
1. 媒体文件
2. 文本

**补充约定**：用户消息本身没有 JSON 外层结构（那是外部卡片信封的形态）。
若开启了广播、同一条用户消息要同步到其它通道，发送前需**剥离信封外层**，
只保留「媒体 + 文本」的实质内容，避免别的通道收到嵌套 JSON。

**现状差距**：当前推送是「按块平铺拼接」，没有折叠概念，也没有规定的块顺序。
需要引入「块序 + 可折叠标记」的表达，再按各通道能力渲染
（QQ 有折叠能力、企业微信是否有待确认）。

### D9 企业微信消息顺序疑似乱序 —— 待确认

**现象**：QQ 侧消息顺序严格，企业微信侧明显偏乱，疑似未按时序发送。

**待查方向**：
1. 合并推送时是否按消息的 `created_at` / 到达顺序排序；
   `merge_batch` 目前按传入的 `items` 顺序拼接，而 `items` 的顺序来自抽屉切片，
   切片顺序是否与真实时序一致需验证。
2. 媒体是在文本之后单独发送的（`push_media` 在 `send_text` 之后调用），
   若一批里既有文本又有图片，用户看到的顺序是「先文后图」，
   与 QQ 的「按消息逐条」不同，这是不是「乱」的主因。
3. 语音是在锁外合成后补推的（`after_push`），时序天然晚于正文，
   是否应改为「语音就位后再一并发出」。

### D10 刷新页面后已执行卡片退回待执行 —— 待修复

**现象**：刷新浏览器页面后，此前已执行完成的工具卡片又变回「待执行」状态。

**可疑方向**：
1. 已执行状态是否只存在内存、未随存档落盘；刷新后重新采集时匹配不到。
2. 执行签名的组成（消息指纹 + 工具名 + 参数）在页面重渲染后是否稳定；
   若消息指纹随 DOM 变化而变，签名就对不上，卡片被当成新卡片。
3. `channel-refactor-progress.md` 里记过同类问题（V1 已通过，但该文提到
   「非末条消息的卡片被执行」仍能复发），可能同源。

**现象 B（该执行却不执行）**：最新卡片从未执行过，面板里也没有执行按钮。
控制台日志实测（2026-11-03）：
```
[AI-Mirror][dialog] ingestMessages 收到 3 条 (来源=generate)
[AI-Mirror][dialog] 质量诊断: lastIsAssistant=true isFreshReply=true 末条role=assistant
[AI-Mirror][dialog] 自动执行决策: 无候选，不执行
[AI-Mirror][dialog] 本轮处理完成: 消息=3, 可见=3, 分支=73, 自动候选=0
```

**B 方向根因已定位**（读码确认）：前端 `extend/dialog/parts/05g_cards.js` 的候选入池条件为
`mi === incoming.length - 1 && state.isFreshReply`。
日志显示 `isFreshReply=true` 却 `自动候选=0`，说明卡片所在消息**不是切片末条**。
工具调用块之后还跟着语音块与 `bridge_copy_md`、`click` 等消息，把卡片挤出了末位，
于是既不自动执行、也不生成执行按钮。

**修法方向**：把「必须是切片末条」放宽为「属于本轮新增消息集合中的最后一张工具卡片」。
这与 A 方向（防止历史卡片被重新认领）不冲突——「新增集合」本身就排除了历史消息。
两个方向应一并修改并联合验证。

**现象 C（卡片被判幽灵卡、拒绝执行）**：候选找到了、卡片也建了，执行时被拦截。
控制台实测（2026-11-03）：
```
[AI-Mirror][dialog] 卡片执行开始：id=c19knvv6 工具=run_command 方式=自动
[AI-Mirror][dialog] 卡片执行拦截：id=c19knvv6 原因=不在镜像中（幽灵卡片）
```

**判定机制**（`extend/dialog/parts/06_execute.js` 的 `cardInMirror`）：
要求 `card.id` 必须能在 `this.messages`（镜像可见切片）的代码块里找到同 id 的块，
找不到即判为「幽灵卡片」并拒绝执行、退回 pending。

**可疑原因**：代码块 id 是内容指纹。当一条 AI 回复持续追加内容时
（实测该轮依次出现 `bridge_copy_md`、`click`、`click_result` 等块），
网页会重渲染，块 id 随内容变化而变，而卡片的 id 仍是被建卡时的旧值，
于是立刻成了「孤儿」——卡片在界面上看得见，却匹配不到镜像里的块。

**与 A / B 的关系**：三者同属「卡片 id 与消息块 id 的一致性」问题。
A 是刷新后 id 变了导致状态丢失，B 是采集条件过严导致漏采，
C 是执行时二次校验时 id 已过期。**应统一按「消息指纹 + 工具名 + 参数」
的执行签名来判身份**，而不是依赖易变的内容指纹 id。

### D11 企业微信推送出现重复消息 —— 待修复

**现象**：推送到企业微信的消息存在重复，同一条内容收到多次。

**可疑方向**：
1. 广播开启后，每条通道各自记账；若某次推送成功但确认环节失败，
   下一轮上报会重推同一条（去重集合已记录则不会，需确认记账时机）。
2. 抽屉上报是「全量切片」，去重集合按会话键隔离；
   若会话键不稳定（如 `conversationId` 变化），同一批消息会被当成新的。
3. 媒体在文本之后单独发送，若文本已成功、媒体失败，下一轮会把整批重推，
   导致文本重复。

## 三、改造原则

1. **推送目标单一来源**：统一从 `flask_server/remote_bridge/channel/target.py` 取「最近用户」，
   QQ 的 `_last_client` 仅用于取客户端句柄，不再作为目标来源。
2. **通道判定集中化**：不在各工具内散写 `is_web()` 之类的判断，
   改为向公共层要「当前活跃通道名」，再按名分派。
3. **能力缺失显式声明**：某通道不支持某操作时，返回明确的「不支持」而不是走别的通道。
4. **适配器协议优先**：新增下发能力时，先在 `flask_server/remote_bridge/channel/adapter.py` 定义方法，
   各通道按需实现，工具层只调协议方法。

## 四、逐项方案

### D1 文件推送通用化

在 `t_push_file` 中按活跃通道分派：

| 活跃通道 | 投递方式 |
|---|---|
| web | 落网页下载目录，投收件箱条目（现状保留） |
| qq | 走被动回复窗口（现状保留） |
| wecom | 用 `bridge.wecom_client` 走 `send_file`（三步上传拿 media_id） |
| weixin | 该通道不支持发文件，返回明确的不支持说明 |

目标用户统一取 `channel.target.<通道>.get()`。

### D2 通道能力声明集中化

把「是否需要被动回复窗口」从客户端实例属性提升为通道元数据，
在 `flask_server/remote_bridge/channel/adapter.py` 中声明，指令层查表而非读实例属性。

### D3 目标来源收敛

逐处排查 `get_last_openid()` 的调用点，改为从 `flask_server/remote_bridge/channel/target.py` 取。
`_last_client` 保留但仅用于 QQ 客户端句柄。

## 五、验收标准

- 从任意通道调用文件推送，文件回到发起通道。
- 通道不支持某能力时，返回明确说明，不跨通道代发。
- 新增一条通道时，无需改动任何工具层代码。
