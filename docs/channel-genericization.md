# 多通道通用化清单

## 一、判定原则

三条通道（QQ / 微信 / 企业微信）的能力差异应当只出现在「接发瞬间的协议编码」。
凡是不涉及协议本身、却写死走某一条通道的实现，都属待通用化项。

需要区分三类情况，避免把合理的适配层当成缺陷：

| 类别 | 特征 | 处理 |
|---|---|---|
| 真正的通道专属 | 硬编码调用某通道的客户端、窗口机制、用户标识来源 | **必须通用化** |
| 签名兼容适配层 | 各通道实现同名方法（如 `send_c2c`）以适配统一调用点 | 保留，属设计所需 |
| 通道固有差异 | 窗口机制、配额、帧格式 | 收敛到适配器策略，不改公共流程 |

## 二、已发现缺陷

### D1 文件推送工具只支持网页与 QQ

- **位置**：`tools/push_file_impl.py`
- **现象**：仅判断 `active_channel.is_web()`，非网页一律走 QQ 分支，
  使用 `message_router.get_last_client()` 与 `get_last_openid()` 取发送句柄与目标。
- **影响**：从企业微信发起时，文件被推到 QQ，企业微信收不到；
  且发送目标取决于「QQ 侧是否有人刚说过话」，与发起通道无关。
- **验证**：从企业微信调用，返回 `target: QQ`，文件未出现在企业微信。

### D2 指令回执依赖 QQ 的序号分配器

- **位置**：`remote_bridge/command_dispatch.py` → `_reply()`
- **现象**：以 `client.needs_window` 区分通道。QQ 走 `message_router.next_seq()`
  取窗口与序号；其它通道走不带窗口参数的发送。
- **影响**：当前行为正确（企业微信 `needs_window = False`，走无窗口分支），
  但通道判断依赖客户端实例上的一个布尔属性，新增通道时容易漏设而退化为走 QQ 分支。
- **性质**：隐患，非现症。

### D3 推送目标存在两套来源

- **位置**：`remote_bridge/message_router` 的 `_last_client` / `_last_openid`（QQ 专属）
  与 `remote_bridge/channel/target.py` 的 `TargetStore`（三通道通用）
- **现象**：同一语义「最近跟谁说话」有两套存储。新代码用后者，旧代码用前者。
- **影响**：调用方若取错来源，会把消息发给另一条通道的用户。

### D4 企业微信多轮收不到文字回复 —— 已修复

**根因**：`flask_server/remote_bridge/adapters/wecom.py` 调用了 `log()`，
但既未定义也未导入，媒体发送的失败分支一进入就抛 `NameError`，
整个推送流程被异常中断。日志里累计 33 条 `name 'log' is not defined`。

**为何长期未发现**：`_send_media` 的失败分支从未被任何测试覆盖，
78 个用例只走成功路径，而 `log()` 恰好只在失败路径上被调用。

**修复**：补上 `bridge_log` 导入与 `log()` 函数；管线日志加通道名与接收方，
使后续能直接看出是哪条通道发给了谁。

**验证**：日志出现 `[wecom] 合并推送成功 3 条 recipient=...`，用户确认收到。

### D5 卡片结果无限重放 —— 已修复

**现象**：同一条工具调用结果被反复回传，累计出现 6 次，且频率上升。

**根因**：前端 `consumeOneCard` 中，本地已存在同 id 卡片时直接 `return false`，
**未调用 `confirmCardDelivered`**。后端设计为「未确认的卡片可被反复取走」，
于是确认失败一次之后，该卡片永远停在未确认状态：每轮轮询都被取走，
每次都被去重分支挡回，形成无限重放。

**修复**：去重分支补上回执——本地已有该卡恰说明它已展示过，正是应当确认的时刻。

### D6 文件推送的通道分派 —— 已修复

**原状**：`flask_server/tools/push_file_impl.py` 只判断 `is_web()`，
非网页一律走 QQ 分支，从企业微信调用时文件被推到 QQ。

**修复**：改为按活跃通道名分派——web 走下载目录，wecom 走主动推送
（目标取 `flask_server/remote_bridge/channel/target.py` 的最近用户），
weixin 明确返回「暂不支持」，不再跨通道代发。

**同时补充测试**：新增 5 个用例覆盖企微成功 / 失败 / 未连接 / 无会话，
以及微信通道明确拒绝。此前该分支零覆盖。

### D4 原始排查记录（保留备查）

- **现象**：用户从企业微信连续发送多条消息，入向正常（日志有「收到消息」「已投递卡片」），
  但出向文字一条都收不到。
- **已观察线索**：
  1. `active_channel` 取值长期停留在 `qq`，用户从企业微信发消息后未更新为 `wecom`。
  2. 同期日志中出现大量 `[bridge][router] 窗口已关闭，暂不推送`——这是 QQ 旧链路的失败记录。
  3. 14:20 之后没有任何管线特征日志（合并推送成功 / 配额用尽 / 推送异常等）。
  4. 去重状态文件里有大量 `@wecom` 命名空间的记录。
- **初步判断**：消息可能被去重集合判为「已推过」而跳过；或广播逻辑未按预期对两条通道各发一份。
- **待排查方向**：
  1. 核对 `active_channel.note()` 在企业微信网关里是否被调用，为何值未变。
  2. 核对广播开关在运行期是否真的读到 `True`（配置已落盘，但进程可能仍是旧值）。
  3. 核对管线里 `_wants(target, channel, broadcast)` 的实际入参。
  4. 核对去重集合的会话键：抽屉上报的 `conversationId` 与 `@wecom` 后缀拼接是否稳定。

## 三、改造原则

1. **推送目标单一来源**：统一从 `flask_server/remote_bridge/channel/target.py` 取「最近用户」，
   QQ 的 `_last_client` 仅用于取客户端句柄，不再作为目标来源。
2. **通道判定集中化**：不在各工具内散写 `is_web()` 之类的判断，
   改为向公共层要「当前活跃通道名」，再按名分派。
3. **能力缺失显式声明**：某通道不支持某操作时，返回明确的「不支持」而不是走别的通道。
4. **适配器协议优先**：新增下发能力时，先在 `flask_server/remote_bridge/channel/adapter.py` 定义方法，
   各通道按需实现，工具层只调协议方法。

## 四、逐项方案

### D1 文件推送通用化

在 `t_push_file` 中按活跃通道分派：

| 活跃通道 | 投递方式 |
|---|---|
| web | 落网页下载目录，投收件箱条目（现状保留） |
| qq | 走被动回复窗口（现状保留） |
| wecom | 用 `bridge.wecom_client` 走 `send_file`（三步上传拿 media_id） |
| weixin | 该通道不支持发文件，返回明确的不支持说明 |

目标用户统一取 `channel.target.<通道>.get()`。

### D2 通道能力声明集中化

把「是否需要被动回复窗口」从客户端实例属性提升为通道元数据，
在 `flask_server/remote_bridge/channel/adapter.py` 中声明，指令层查表而非读实例属性。

### D3 目标来源收敛

逐处排查 `get_last_openid()` 的调用点，改为从 `flask_server/remote_bridge/channel/target.py` 取。
`_last_client` 保留但仅用于 QQ 客户端句柄。

## 五、验收标准

- 从任意通道调用文件推送，文件回到发起通道。
- 通道不支持某能力时，返回明确说明，不跨通道代发。
- 新增一条通道时，无需改动任何工具层代码。
