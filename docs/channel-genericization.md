# 多通道通用化清单

> 2026-11-04 整理：本文经多轮追加后，同一缺陷出现 2–3 次、编号重复。
> 本次按「状态」重组，每个缺陷只保留一处，被证伪的中间假设移入附录 A。

## 一、判定原则

三条通道（QQ / 微信 / 企业微信）的能力差异应当只出现在「接发瞬间的协议编码」。
凡是不涉及协议本身、却写死走某一条通道的实现，都属待通用化项。

需要区分三类情况，避免把合理的适配层当成缺陷：

| 类别 | 特征 | 处理 |
|---|---|---|
| 真正的通道专属 | 硬编码调用某通道的客户端、窗口机制、用户标识来源 | **必须通用化** |
| 签名兼容适配层 | 各通道实现同名方法（如 `send_c2c`）以适配统一调用点 | 保留，属设计所需 |
| 通道固有差异 | 窗口机制、配额、帧格式 | 收敛到适配器策略，不改公共流程 |

## 三、已完成的修复

### G1 文件推送的通道分派

**原状**：`flask_server/tools/push_file_impl.py` 只判断 `is_web()`，
非网页一律走 QQ 分支——从企业微信调用时文件被推到 QQ，
且发送目标取决于「QQ 侧是否有人刚说过话」，与发起通道无关。

**修复**：按活跃通道名分派——web 走下载目录；wecom 走主动推送
（目标取 `flask_server/remote_bridge/channel/target.py` 的最近用户）；
weixin 明确返回「暂不支持」，不跨通道代发。

**测试**：新增 5 个用例覆盖企微成功 / 失败 / 未连接 / 无会话，
以及微信通道明确拒绝。该分支此前零覆盖。

### G3 推送目标来源收敛

**原状**：「最近跟谁说话」有两套存储——`message_router._last_openid`（QQ 专属、纯内存）
与 `flask_server/remote_bridge/channel/target.py` 的 `TargetStore`（三通道通用、落盘）。
前者随重启归零，后者可续用，取错来源会把消息发给另一条通道的用户。

**修复**：`get_last_openid` 先取内存值，为空时回退到 `TargetStore.qq` 的落盘记录。
`_last_client` 保留，仅用于取 QQ 客户端句柄。

### G4 企业微信多轮收不到文字回复

**根因**：`flask_server/remote_bridge/adapters/wecom.py` 调用了 `log()`，
但既未定义也未导入。媒体发送的失败分支一进入就抛 `NameError`，
整个推送流程被异常中断。日志里累计 33 条 `name 'log' is not defined`。

**为何长期未发现**：`_send_media` 的失败分支从未被任何测试覆盖，
78 个用例只走成功路径，而 `log()` 恰好只在失败路径上被调用。

**修复**：补上 `bridge_log` 导入与 `log()` 函数；管线日志加通道名与接收方，
使后续能直接看出是哪条通道发给了谁。

**验证**：日志出现 `[wecom] 合并推送成功 3 条 recipient=...`，用户确认收到。

### G5 卡片结果无限重放

**根因**：前端 `consumeOneCard` 中，本地已存在同 id 卡片时直接 `return false`，
**未调用 `confirmCardDelivered`**。后端设计为「未确认的卡片可被反复取走」，
于是确认失败一次之后，该卡片永远停在未确认状态：每轮轮询都被取走、
每次都被去重分支挡回，形成无限重放。

**修复**：去重分支补上回执——本地已有该卡恰说明它已展示过，正是应当确认的时刻。

### G6 图文混排被拆成多张卡片

**根因有两层**：
1. 入口处 `if not text:` 先判文字——平台在 mixed 消息顶层也带文字，
   于是直接走文本分支，**整条消息里的图片被跳过**。
2. 即使进了 mixed 分支，也是给每张图单独调 `_handle_media`，
   每次投一张独立卡片，4 张图 = 4 张卡。

**修复**：
1. `msgtype == "mixed"` 时**优先**处理，不再先看有没有文字；顶层文字与子项文字合并。
2. 图片先全部下载落盘，再与文字一起投成**一张**卡片（`data_urls` 数组，前端一次贴多张）。

**验证**：
```
mixed 子项：count=4 detail=[('image',...), ('text',...), ('image',...), ('text',...)]
图文消息已投递 文字长度=17 图片数=2
[delivery] 已投递图片卡片 xxxx 张数=2
```
一次投递、两张图、文字随行，前端显示为一张卡片。

### G7 卡片投递与正文组装抽到公共层

**原状**：三份网关各写一套 `_deliver_as_card` / `_deliver_image_card`，
能力不一致——企业微信漏了多图支持，正是 G6 的成因之一。
正文拼装亦然：企微与微信两份实现逐字相同。

**已建立的两个公共模块**：

| 模块 | 提供 | 迁移状态 |
|---|---|---|
| `flask_server/remote_bridge/channel/delivery.py` | `deliver_images` / `deliver_file` / `deliver_text` | 三通道均已迁完 |
| `flask_server/remote_bridge/channel/text.py` | `truncate` / `is_own_source` / `extract_text` / `body_of` | 企微与微信已迁完 |

通道差异通过参数表达：微信截断上限 1800、企微 3500；
微信不重复检查来源（由管线在上游过滤）。

**测试**：新增 `tests/test_channel_delivery.py`（7 例）与
`tests/test_channel_text.py`（12 例），直接守公共层契约，不再按通道各写一份。

### G8 企业微信缺 Markdown 渲染

**排查结论：不是平台限制，是取正文的路径不同。**

| 通道 | 取正文方式 | 结果 |
|---|---|---|
| QQ | `outbound.build_body`，优先用 `md` 原文 | `## 标题\n正文**加粗**` |
| 企业微信 | `text.extract_text`，从 blocks 拼纯文本 | `标题\n正文加粗` |

同一份上报数据，两条通道取了不同来源，格式差异由此而来。
前端早已记录标题的 `level` 与引用的 `quote` 类型，是后端把结构丢了。

**修复**：`flask_server/remote_bridge/channel/text.py` 的 `extract_text` / `body_of` 增加 `use_md` 参数。
支持 Markdown 的通道传 `True`（企微），不支持的不传（微信，避免露出裸语法）。
QQ 走自己的 `build_body`，本就优先用 md，无需改动。

**通道能力现状**：

| 通道 | 支持 Markdown | 依据 |
|---|---|---|
| QQ | 是 | `msg_type=2`，正文放 `markdown.content` |
| 企业微信 | 是 | `msgtype=markdown`，正文放 `markdown.content` |
| 微信 | 否 | `send_text` 忽略 markdown 参数 |
| 网页 | 否 | 收件箱按纯文本渲染 |

**待确认**：企微 markdown 实际支持的语法子集（表格已知不支持，已转为纯文本列表）。
本次解决的是「有格式却没用上」，语法子集问题若仍存在需单独处理。

## 四、待处理

### G2 指令回执依赖客户端实例的布尔属性 —— 已修复

**位置**：`flask_server/remote_bridge/command_dispatch.py` → `_reply()`

**原状**：以 `client.needs_window` 区分通道。QQ 走 `message_router.next_seq()`
取窗口与序号；其它通道走不带窗口参数的发送。QQ 客户端本身没声明该属性，
靠读取时的默认值兜底——新增通道若漏声明，会默认按 QQ 处理。

**修复**：
1. `QQClient` 显式声明 `needs_window = True`，使「哪些通道需要窗口」
   成为可查的契约，而非依赖默认值推断；
2. 判定处对属性缺失告警，并按「需要窗口」走保守分支——
   宁可多走一次窗口检查，也不让新通道误入无窗口路径。

**三通道现状**：QQ `True`、微信 `False`、企微 `False`。

### G9 消息块的组织顺序与折叠 —— 顺序已实现

**目标结构**：

AI 消息：思考内容（折叠）→ 文本 → 工具调用（折叠）→ 语音块

工具消息：媒体文件 → JSON 内容（折叠）

用户消息：媒体文件 → 文本

**关于折叠的现实约束**：QQ 与企微的 Markdown 都不支持 `<details>` 一类折叠语法。
故折叠只能靠**代码块**降级实现——代码块视觉上独立、弱化注意力，等效于折叠。

**已实现**（`flask_server/remote_bridge/channel/text.py` 的 `_assemble_ordered`）：

| 块类别 | 判定 | 输出位置 | 处理 |
|---|---|---|---|
| 思考 | `type=thinking` | 最前 | 代码块包裹，受「思考」开关控制 |
| 正文 | 段落 / 标题 / 列表 / 引用 / 表格 | 居中 | 原样输出 |
| 工具调用 | `bridge-chat-call` | 靠后 | 代码块包裹，**只报工具名，不带参数** |
| 语音 | `bridge-voice` | 最后 | 输出朗读文本 |

顺序按类别固定，与块在 DOM 里的先后无关——AI 回复的块顺序可能是
「正文 → 工具调用 → 思考」这类乱序，直接拼接会让读者先看到工具调用。

**保留的两条原设计**：
1. 纯工具调用消息不产出正文（没有可读内容，推出去是一屏花括号）；
2. 工具参数不进正文（用户需要知道调了什么工具，不需要看具体入参）。

**未实现**：用户消息的「剥离信封外层」——广播时同步给其它通道的场景，
目前各通道按自己的方式处理卡片信封，尚未统一剥离。

### G10 消息顺序疑似乱序

**现象**：QQ 侧消息顺序严格，企业微信侧明显偏乱。

**状态**：缺日志证据，待复现时截图确认。

**未验证的猜测（不作为修复依据）**：
1. 合并推送按 `items` 顺序拼接，而 `items` 来自抽屉切片，
   切片顺序是否等于真实时序未验证；
2. 媒体在文本之后单独发送（`push_media` 在 `send_text` 后调用），
   一批里既有文本又有图时，用户看到「先文后图」；
3. 语音在锁外合成后补推（`after_push`），时序天然晚于正文。

### G11 卡片执行状态异常

**已改两版，两版都未确认真机生效。**

**版本一（已废弃）**：签名用「消息指纹 + 工具名 + 参数」。
失效原因：消息指纹由 `extend/lib/dom-utils.js` 的 `messageFingerprint` 计算，
它把消息里所有块的内容拼起来做哈希，AI 追加内容时必然改变——
与代码块 id 同样不稳定，兜底判据因此形同虚设。

**版本二（当前）**：判据只用「工具名 + 参数」，不含任何内容哈希。
参数通常含具体路径、命令等，重复概率低。
即便误判为「存在」，后果也只是这张待执行卡片被执行——本就是该做的动作，
远好过误判为「不存在」导致卡片永远无法执行。

**另外两处已改**：
1. 候选入池判据从「切片末条」改为「本轮最后一条助手消息」——
   工具调用块之后常跟着语音块、`bridge_copy_md`、`click` 等消息，
   它们到达后把 AI 回复挤出末位，卡片再也不被收集。
2. 状态文件写入改原子操作（临时文件 + `os.replace`）——
   重启走 `os._exit(0)` 强制退出、不做清理，直接覆盖可能写坏文件，
   导致去重集合归零、整批重推。

**下次复现时先确认两件事**：
1. 扩展是否已重新加载（旧版扩展的代码与磁盘不一致）；
2. 控制台是否出现「签名匹配失败」诊断（该日志打出两侧指纹对比）。

### G12 企业微信推送出现重复

**已定位线索**：重复一般出现在 `/rall` 重启后的**第一条**消息。

`/rall` 是组合指令：`/rf`（刷新页面）→ `/sa on` → `/dc` → `/rs`（重启服务）。
线索把范围收窄到「重启后的状态恢复」。

**已排除**：
- 新链路日志里同一秒重复记录为 0 处；
- 去重集合会话键稳定（UUID，非随机）；
- 待推缓存是纯内存，不影响去重判定。

**已做的修复**：状态文件写入改原子操作（见 G11 第 2 条）。
原因：`os._exit(0)` 强制退出时若正在覆盖原文件，文件会被截断成半截 JSON，
下次启动解析失败即回退空结构，去重集合归零，第一条上报把整个切片当新的全量重推。

**待验证**：重启一次，看第一条消息是否仍重复。

## 五、改造原则

1. **推送目标单一来源**：统一从 `flask_server/remote_bridge/channel/target.py` 取「最近用户」，
   QQ 的 `_last_client` 仅用于取客户端句柄。
2. **通道判定集中化**：不在各工具内散写 `is_web()` 之类的判断，
   改为向公共层要「当前活跃通道名」，再按名分派。
3. **能力缺失显式声明**：某通道不支持某操作时，返回明确的「不支持」而不是走别的通道。
4. **适配器协议优先**：新增下发能力时，先在 `flask_server/remote_bridge/channel/adapter.py` 定义方法，
   各通道按需实现，工具层只调协议方法。
5. **测试守公共层契约**：能力收归公共层后，测试也应守在这一层，
   不按通道各写一份——否则改坏公共层，各通道的测试可能照样全绿。

## 六、验收标准

- 从任意通道调用文件推送，文件回到发起通道。
- 通道不支持某能力时，返回明确说明，不跨通道代发。
- 新增一条通道时，无需改动任何工具层代码。

## 附录 A：排查过程中被证伪的假设

保留这些是为了避免后来人重复走同样的弯路。

| 当时的假设 | 实际情况 |
|---|---|
| 企微丢文字是因为「两条通道互相压制」 | 是适配器调用了未定义的 `log()`，异常中断了推送 |
| 企微缺 Markdown 是平台限制 | 是两条通道取正文来源不同，我们没把格式发出去 |
| 卡片重放是缓存问题 | 是「取走未确认」的卡片被反复投递，确认分支缺失 |
| 幽灵卡是因为代码块 id 变化 | 判断对了一半——消息指纹同样基于内容，也会变 |
| 清理旧代码按「函数名白名单」删即可 | 漏掉外部引用，两次误删，靠版本控制还原 |

**清理死代码的正确方法**（可复用）：从「被外部引用的函数」出发算**保留闭包**，
闭包之外才是死代码。每步都实际调用验证，而非只看能否导入。
