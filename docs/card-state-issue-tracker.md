# 卡片状态故障追踪

> 本文档记录「卡片状态异常」的排查进度，防止改了又改回来。
> 规则：每尝试一个方案，先在此登记假设与预期，验证后再标记结论。

## 一、故障现象

| 编号 | 现象 | 严重程度 |
|---|---|---|
| S1 | 刷新页面（含 `/rall` 重启）后，已执行卡片全部退回待执行 | 严重 |
| S2 | 非末条消息里的卡片抢占自动执行权 | 严重 |
| S3 | 偶发「幽灵卡片」：执行时被判不在镜像中而拒绝 | 中 |

## 二、已确认的事实

### 事实 1：记忆开关阻断了整个数据库（根因）

`flask_server/core/memory_db.py` 的 `get_conn()` 首行即检查记忆开关：

```python
def get_conn():
    if not is_enabled():
        raise MemoryDisabled("记忆系统已关闭（设置页未开启记忆检查）")
```

**后果**：记忆检查关闭时，任何会话读写都失败。
前端的 `persistConv` 发起保存 → 后端投入异步队列并返回 `accepted: true`
→ 后台线程真正写库时抛 `MemoryDisabled` → 异常被队列吞掉 → 一条数据都没落库
→ 加载时返回「后端无此会话」→ 签名库为空 → 卡片全部退回待执行。

**证据**（2026-11-04 实测）：
```
[AI-Mirror][dialog] loadConversation: 后端与本地均无会话 cid:48d77399-...
[AI-Mirror][dialog] persistConv 写入后端：会话=..., 节点=6, 外部卡片=0, 签名=0
```

**性质**：架构缺陷。会话持久化属基础存储，必须始终可用；
记忆蒸馏 / 检索 / 事件聚类属可选分析，才该受开关控制。两者被混在同一道开关后。

### 事实 2：消息指纹是设计所需，不是缺陷

执行签名含消息指纹（`msgId`），用于区分「同工具同参数但分属不同消息」的两次调用。
**去掉它会导致两个相同参数的调用无法各自执行**，这是更严重的故障。

此前一度删掉它，已回退（提交 `ede8a67`）。

## 三、已排除的假设

| 假设 | 排除依据 |
|---|---|
| 签名含消息指纹导致刷新后对不上 | 去掉指纹后故障依旧；且指纹是区分重复调用的基础 |
| 代码块 id 变化导致卡片匹配失败 | 改了幽灵卡校验，故障依旧 |
| 签名只按「工具名 + 参数」即可 | 会让两次相同调用互相压制 |
| 后端字段白名单漏了签名 | 补了字段，仍失败——因为整张表都写不进去 |

## 四、已知的回归

### R1：自动执行判据被放宽（待回退）

`extend/dialog/parts/05g_cards.js` 的候选入池判据：

- **原设计**：`mi === incoming.length - 1`（必须是切片末条）
- **被改为**：`mi === state.lastAssistantIdx`（最后一条助手消息）

两者在正常时序下等价，但切片为 `[user, assistant, user]` 这类形态时会分叉：
助手消息不是末条，却会被判为可执行 → 正是现象 S2。

**结论**：应回退到「切片末条」判据。

## 五、待决策

| 编号 | 事项 | 选项 |
|---|---|---|
| D1 | 记忆开关阻断数据库 | A. 拆开：会话存储不受开关控制，开关只管蒸馏/检索；B. 保持现状，要求用户始终开启记忆检查 |
| D2 | R1 判据回归 | A. 回退到切片末条；B. 保留现状 |
| D3 | 历史卡片无签名记录 | 修复只对修复后新执行的卡片有效；历史卡片无法追溯，需接受 |

## 六、验证方法（修复后执行）

1. 确认 `get_conn()` 在记忆开关关闭时仍可用；
2. 执行一张新卡片，观察日志 `persistConv ... 签名=N`，N 应大于 0；
3. 刷新页面，观察日志 `loadConversation 签名恢复：后端=N`，N 应一致；
4. 确认该卡片仍显示「已执行」；
5. 确认非末条消息里的卡片不自动执行。

## 七、教训

1. **先验证数据能否持久化，再怀疑算法**。本次故障的根因在存储层，
   而前三次修改都在算法层打转。
2. **不凭读代码推断就改**。必须先用日志拿到证据。
3. **改动前登记假设与预期**，验证后再标记结论，避免反复。
