> 规则：每项结论必须附可复现的证据来源；无证据的推断不写入本文档。

## 四、S1 根因（已查明）

签名存取本身没有问题，问题在前端时序：

1. 页面刷新后，消息渲染建卡与「从后端取回签名库」是两条并行路径；
2. 建卡时调用 `_executedSig` 查签名，若此时签名库尚未取回，查询必然落空；
3. 落空的卡片被建成待执行态；
4. 签名库随后取回并合并进内存，但**没有任何环节回头重判已建好的卡片**，
   于是这些卡片一直停在待执行态。

这解释了为什么后端脚本直连验证「签名可存可取」却依然复现——故障不在存取，
在「取回之后没人用」。

修复：新增 `05g_cards.js` 的 `_restoreExecutedCards()`，在 `04_sessions.js`
的存档加载完成处调用，遍历消息树里的卡片按签名库重判一次，只把「未执行」
往「已执行」方向纠正，反向不动（避免覆盖本次会话刚跑完的结果）。

验证：`tests/js/test_card_sig_restore.test.js` 六个用例覆盖命中、未命中、
已执行不重处理、空库、非工具卡、多卡混合六种情况。

实机确认：刷新后日志出现 `loadConversation 签名恢复：后端=142 内存=142`，
页面无待执行卡片，S1 关闭。

## 五、S4 现象（已解决）

S1 修复后，卡片的「已执行态」恢复了，但卡片在界面上退化成普通代码块：
没有「执行 / 跳过 / 重新执行 / 复制结果」按钮，用户无法手动重跑。

结论：已解决（用户确认），S4 关闭。具体修复位置与做法以代码为准。

排查时列入的两种可能：

1. 恢复逻辑把卡片标为已执行后，渲染层据此隐藏了操作按钮——即按钮只在
   待执行态出现，已执行态没有任何入口。若是这种，属渲染设计缺陷，与 S1 无关；
2. 恢复出的卡片缺少某个渲染所需的字段，被当成普通代码块渲染。

排查要点：对比「刚执行完的卡片」与「刷新后恢复的卡片」在 DOM 上的差异，
重点看卡片的 isTool / call / status 三个字段。

## 七、验证方法

1. 执行一张新卡片，日志应出现「[签名诊断] 登记 sig=」，且 `persistConv ... 签名=N` 的 N 大于 0；
2. 刷新页面，日志应出现「loadConversation 签名恢复：后端=N」，N 与上一步一致；
3. 确认该卡片仍显示「已执行」；
4. 确认非末条消息里的卡片不自动执行。

## 八、操作准则

1. 改动前先登记假设与预期，验证后再标记结论。
2. 结论必须有日志或网络记录支撑；静态阅读代码只能得出「代码写成了这样」。
3. 扩展代码改动后，在 `chrome://extensions` 重新加载对应扩展，再刷新页面，确保运行的是当前代码。
4. 先验证数据是否真正落库，再调整判定逻辑。
