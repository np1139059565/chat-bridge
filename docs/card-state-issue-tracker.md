# 卡片状态故障追踪

> 本文档记录「卡片状态异常」的当前状态：故障现象、已提交改动、待查环节。
> 规则：每项结论必须附可复现的证据来源；无证据的推断不写入本文档。

## 一、故障现象

| 编号 | 现象 | 严重程度 | 复现状态 |
|---|---|---|---|
| S1 | 刷新页面（含 `/rall` 重启）后，已执行卡片全部退回待执行 | 严重 | 两次实机验证均复现 |
| S2 | 非末条消息里的卡片抢占自动执行权 | 严重 | 两次实机验证均复现 |
| S3 | 偶发「幽灵卡片」：执行时被判不在镜像中而拒绝 | 中 | 未专项复现 |

## 五、验证方法

1. 执行一张新卡片，日志应出现「[签名诊断] 登记 sig=」，且 `persistConv ... 签名=N` 的 N 大于 0；
2. 刷新页面，日志应出现「loadConversation 签名恢复：后端=N」，N 与上一步一致；
3. 确认该卡片仍显示「已执行」；
4. 确认非末条消息里的卡片不自动执行。

## 六、操作准则

1. 改动前先登记假设与预期，验证后再标记结论。
2. 结论必须有日志或网络记录支撑；静态阅读代码只能得出「代码写成了这样」。
3. 扩展代码改动后，在 `chrome://extensions` 重新加载对应扩展，再刷新页面，确保运行的是当前代码。
4. 先验证数据是否真正落库，再调整判定逻辑。
