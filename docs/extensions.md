# 扩展开发规范（chat-bridge）

> 适用对象：想向宿主注册能力的人——写 skill、加 AI 工具、注册指令、投递任务。
> 本文合并了原先分散在五份文档中的规范，冲突时以本文为准。
> 翻译员与工具服务的拆分期间，相关归属变化见 `docs/split-mirror-and-tools-service.md`。

## 一、四种扩展形态

宿主提供四条扩展路径，各自归属不同、读者不同：

| 形态 | 是什么 | 谁用 | 存哪 |
|---|---|---|---|
| **skill** | 一组能力 + 说明的封装 | 宿主扫描 | `skills/<name>/` |
| **AI 工具** | AI 可调用的能力 | AI | `tool.json` 的 `tools` |
| **指令** | `/` 开头的用户命令 | 用户 | `tool.json` 的 `commands` |
| **投递任务** | 外部工具主动联系网页 AI 的载体 | 网页 AI | 运行时投递 |

**核心判据**：这个条目会被 AI 调用吗？

- 会 → 放 `tools`
- 不会，只作某条指令的执行端 → 放 `command_actions`
- 是用户敲的命令 → 放 `commands`

三者物理分开、互不混放，视图层无需任何过滤。详见第五节「隔离铁律」。

## 二、skill 规范

### 2.1 目录结构

```
skills/<name>/
├── tool.json      # 声明文件：provider、工具、指令执行端、指令、注入说明
├── SKILL.md       # 技能说明文档（供 AI 读取）
├── README.md      # 面向人的简介（可选）
└── extension/     # 扩展代码（若为浏览器扩展，可选）
```

### 2.2 声明文件 tool.json

```json
{
  "provider": "debug_chrome",
  "prompt": "本技能提供……（注入给 AI 的处理要求）",
  "tools": [ /* AI 工具 */ ],
  "command_actions": [ /* 指令执行端 */ ],
  "commands": [ /* 指令声明 */ ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `provider` | 是 | 提供方标识，扩展轮询命令时用它认领 |
| `prompt` | 否 | 注入 System Prompt 的说明 |
| `tools` | 否 | AI 工具数组（进 AI 工具目录与 System Prompt） |
| `command_actions` | 否 | 指令执行端数组（对 AI 透明，执行通道与工具共用） |
| `commands` | 否 | 指令声明数组（供用户使用） |

### 2.3 SKILL.md 写法

`SKILL.md` 是给 AI 读的说明书，建议按以下结构组织：

| 章节 | 内容 |
|---|---|
| 标题 + 一句话简介 | 这是什么 |
| 能力 | 提供哪些工具 / 指令，用表格列 |
| 交互方式 | 被调用、主动对话两条通道怎么走 |
| 处理要求 | AI 必须遵守的步骤与约束 |

要点：

- 处理要求里写清「若本次会话尚未读过本说明，先用 `read_skill` 读取」，避免 AI 凭记忆臆测。
- 需要读写本地文件时，声明「用镜像插件的本地工具，不臆造工具名」。
- 读取 skill 文档统一走 `read_skill`（参数 `skill` + `file` 相对路径），不要用 `read_file` 拼路径。

### 2.4 注册流程

1. 建 `skills/<name>/tool.json` 与 `SKILL.md`。
2. 设置页扫描 → 安装 → 上线。
3. 技能清单由后端扫描 `skills/` 生成，注入 System Prompt 的 SKILL 段。

## 三、AI 工具规范

### 3.1 内置与外部

内置工具跑在 Flask 服务里（`tools_impl.py`）；外部工具由扩展自己轮询、自己执行，服务只负责入队与等结果。判据看 `tool.json` 的 `executor` 字段：`external` 即外部工具。

### 3.2 工具字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 工具名，外部工具须与扩展 `TOOL_HANDLERS` 的键一致 |
| `description` | 是 | 说明，展示给 AI |
| `executor` | 是 | `external`（外部）；内置工具不写此字段 |
| `silent` | 否 | 为 `true` 时不在抽屉生成工具卡片（如 `push_message`） |
| `wakeup` | 否 | 为 `true` 时允许在抽屉关闭时被待命轮询取走（如 `open_drawer`） |
| `parameters` | 是 | 参数数组，每项含 `name` / `type` / `required` / `description` |

参数类型沿用 `string` / `number` / `boolean` / `array`，`required` 缺省为 `false`。

**参数的准确名字以 `get_tool_params` 返回为准**——AI 调用前应先查，不得臆造别名。

### 3.3 执行通道

```
AI 生成工具调用
  → 工具服务解析、生成工具卡片
  → 按 provider 入队
  → 扩展轮询取走、在页面执行
  → 回传结果 → 工具卡片显示
```

关键常量：

| 项 | 值 | 位置 |
|---|---|---|
| 提供方在线判定窗口 | 10 秒 | `external_tools.ONLINE_WINDOW` |
| 命令等待上限 | 10 秒 | `external_tools.FORWARD_TIMEOUT` |

在线判定仅用于界面指示灯，**不参与执行判断**。命令路由依据目标页面的抽屉是否打开；目标页未打开时命令逸散到其他页面代收。

### 3.4 回传约定

- 结果**一律回传**（含 `silent` 工具），让调用方拿到真实执行状态。
- `silent` 仅表示不在抽屉生成工具卡片。
- 是否把结果再发回网页 AI，由插件侧的 `no_reply` 参数决定。

### 3.5 扩展侧约定

扩展用一张表登记工具名 → 处理函数（`05_tool-handlers.js` 的 `A.TOOL_HANDLERS`）：

```js
A.TOOL_HANDLERS = {
  get_element_style: (params) => A._toolGetElementStyle(params),
  // 新增工具：写处理函数并登记，不必改分发逻辑
};
```

未登记的工具名返回 `UNKNOWN_TOOL`。必须遵守：

- **内容脚本只做 DOM 操作，不直接发网络请求**，一律走 `A.proxyFetch`（PNA 会拦截直连）。
- 执行可能长阻塞的工具（如 `exec_js`）必须自行超时，否则卡死轮询循环。
- 参数名与 `tool.json` 声明严格一致。

### 3.6 新增一个外部工具

1. 扩展侧：写处理函数，登记进 `A.TOOL_HANDLERS`。
2. 声明侧：在 `tool.json` 的 `tools` 里加一项，`executor` 填 `external`。
3. 设置页扫描 → 安装 → 上线。
4. 用 `get_tool_params` 核对参数名后调用验证。

## 四、指令规范

### 4.1 现有指令系统

**内置指令**：表驱动，两张表分离。

| 表 | 文件 | 管什么 |
|---|---|---|
| `BUILTIN` | `remote_bridge/command_registry.py` | 命令名 → 说明 / 别名 / 分组 |
| `_BUILTIN_HANDLERS` | `remote_bridge/command_panel.py` | 命令名 → 执行函数 |

两表的键必须一致，导入期由 `_check_handler_table()` 自检。别名由 `resolve_cmd()` 归一为主命令名。执行路径：处理函数调 `_dispatch()` → 创建 `drawer-command` 卡片 → 抽屉轮询取走执行。

**自定义指令**：存在配置的 `commands` 字段，用户可在设置页维护，三类：

| 类型 | 作用 |
|---|---|
| 组合（`steps`） | 按序执行多条子指令，步骤间有间隔 |
| 采集（`collect`） | 点按钮取 Markdown |
| 点击（`selector`） | 点击指定元素 |

`selector` 可为裸选择器、任意 JS 表达式或 `@profile:FIELD` 哨兵。哨兵在执行时取当前站点档案同名字段的值，指令配置对站点无感知；字段未配置的站点会收到指明站点与字段的失败回执。

合法性由 `validate_command()` 校验：命令名须以 `/` 开头、不得与内置或其它自定义指令（含别名）冲突、组合的子指令必须存在。

### 4.2 外部指令注册

**目标**：外部工具像声明工具一样声明指令，宿主只当「目录 + 转接器」，不介入扩展内部。关键判据：**按下指令后，动手的是扩展自己，而不是宿主。**

声明格式见第二节的 `command_actions` 与 `commands` 两个数组。

`command_actions` 的字段与 `tools` 完全一致，解析与执行共用同一套逻辑，仅来源数组不同。

`commands` 字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 主命令名，须以 `/` 开头 |
| `alias` | 否 | 快捷键，须唯一 |
| `desc` | 是 | 说明，进 `/help` 与指令面板 |
| `tool` | 是 | 映射到本 skill 的哪个 `command_action` |
| `params` | 否 | 固定参数，敲指令时原样随命令下发 |

执行通道复用 external 工具通道，不新开管道：

```
用户敲 /dbg-open
  → command_panel 查外部指令注册表
  → 命中 provider=debug_chrome, tool=open_drawer
  → 走 external_tools 通道入队
  → 扩展轮询取走、自己执行
  → 结果按原路回传
```

**命名**：外部指令建议统一前缀（如 `/dbg-`），快捷键两字符为宜。主名与别名都要过 `_check_name_free()`，被占用时注册失败并回执，由扩展换名重报。

**配额**：不硬限元素个数，超出平台上限时截断并记录，保留优先级高者，不阻断注册。

**生命周期**：扩展卸载或下线时，其指令一并注销，不得在 `/help` 或面板里留下按了没反应的死开关。注册表以 `provider` 为键聚合。

### 4.3 示例：debug_chrome

| 主命令 | 快捷键 | 作用 | 映射工具 |
|---|---|---|---|
| `/dbg-open` | `/do` | 打开调试抽屉 | `open_drawer` |
| `/dbg-close` | `/dc` | 关闭调试抽屉 | `close_drawer` |
| `/dbg-side` | `/dl` | 抽屉左右切换 | `switch_drawer_side` |
| `/dbg-settings` | `/dt` | 打开设置页 | `open_settings` |
| `/dbg-back` | `/db` | 从设置页返回 | `close_settings` |

### 4.4 指令回执通道

指令经 external 通道下发后，扩展执行完要把结果送回**发起指令的那条通道**，否则宿主等待方取不到结果，超时后报「指令未在时限内执行」。

| 发起方 | 结果回传地址 |
|---|---|
| 用户指令（`command_hub`） | `/api/command-ext/<provider>` |
| AI 工具调用 | `/api/ext/<provider>` |

回执函数 `postResult(requestId, result, channelPath)` 缺省 `channelPath` 时回落到 AI 工具通道。因此扩展处理指令时，`handleTask` 必须把通道参数透传给 `postResult`。

内置指令不受影响：它们走投递队列，由宿主抽屉直接执行，回执走 `/api/bridge/result`。

**指令回执与消息 id 无关**：对客户端而言，AI 回复与指令回复没有区别，都是「一条要投递的消息」。是否需要 id、用哪种 id，由各通道自己决定。指令层只管把结果交给通道，不参与消息标识的构造。

### 4.5 外部指令参与组合指令

外部指令可作为组合指令的子指令。约束是同一条组合指令内的子指令须来自同一 provider：跨 provider 组合需要执行链支持跨扩展调度，当前 `command_panel` 不具备该能力。

## 五、隔离铁律

> 改动任何涉及「指令」「工具」「回传」的代码前，先读本节。
> 指令与工具**严禁任何形式的互相入侵**。此坑已多次复现。

### 5.1 两个概念，两个归属

| | 指令 | 工具 |
|---|---|---|
| **谁用** | 用户 | AI |
| **声明位置** | `tool.json` 的 `commands` | `tool.json` 的 `tools` |
| **执行端** | `command_actions` 数组 | `tools` 数组 |
| **回执去向** | 发起指令的用户 | 网页 AI（作为工具结果） |
| **能否进 AI 工具目录 / System Prompt** | **否，绝对禁止** | 是 |
| **能否流向 AI** | **否，任何情况都禁止** | 是（这是它的用途） |

一句话：**指令归用户，工具归 AI。指令的任何东西都不得流向 AI。**

### 5.2 铁律

| 编号 | 内容 |
|---|---|
| R1 | 指令不得出现在任何「给 AI 看的」清单里：`/tools`、System Prompt、未知工具提示的 `available` 列表、`get_tool_params` 的可用清单 |
| R2 | 指令自身的信息不得流向 AI：包括指令名、指令回执、指令执行失败的错误堆栈、网络异常、中间状态 |
| R3 | 指令与工具不得混放在同一数据数组：`tools` 只放 AI 工具，`command_actions` 放指令执行端，`commands` 放指令声明 |
| R4 | 不得用标记字段区分指令与工具：靠视图层过滤极易漏过滤，改为源头分开 |
| R5 | 指令执行端与 AI 工具共用执行通道，但不得共用展示通道 |

### 5.3 回传通道的分界

**工具回传**（合法，进 AI）：AI 调用工具 → 工具卡片 → 结果/失败 → 回传网页 AI。失败分两类：AI 能改的（参数错、工具代码缺陷）回传；环境/网络类不传，因为 AI 改不了、只会污染上下文。

**指令回执**（禁止进 AI）：用户发指令 → `drawer-command` 卡片 → 前端执行本地动作 → 回执经 `/api/bridge/result` → QQ / 网页收件箱。**绝不**经 `/tool`、绝不产生工具卡片。

**判别口诀**：先分清「指令的回执」与「指令触发的工具结果」。

| 类型 | 举例 | 去向 |
|---|---|---|
| 指令回执 | `/ls` 的列表、「已切换会话」提示、指令自身的报错 | 只能回用户，**任何情况都不进 AI** |
| 指令触发的工具结果 | `/rr` 重跑、`/sa on` 带起的卡片 | 属工具产物，正常结果照常回传；只有**执行失败时的报错**要拦 |

隔离针对的是「指令本身的信息」，不是「指令顺带跑出来的工具结果」。把工具结果一并拦掉，会让 `/rr` 这类指令完全失效。

### 5.4 所有「指令可能流向 AI」的路径（改动必查）

| # | 路径 | 文件 | 防护 |
|---|---|---|---|
| 1 | 工具目录 `/tools` | `routes/tools.py` | 只取 `kind=tool` |
| 2 | System Prompt 技能清单 | `core/prompt_sections.py` | 只取 `kind=tool` |
| 3 | 未知工具可用清单 | `routes/tools.py`、`tools_impl.py` | 只取 `kind=tool` |
| 4 | 设置页工具列表 | `routes/custom_tools.py` → `meta.all_meta_full` | 只取 `kind=tool` |
| 5 | 指令卡片漏消费 | `dialog/parts/01_backend.js` | `drawer-command` 黑名单拦截 |
| 6 | 指令结果 / 失败回传 | 见 5.3 节 | 指令回执走 `/api/bridge/result`，不进 AI |

### 5.5 新增功能自查

- [ ] 新增的条目是 AI 工具、指令执行端，还是指令声明？放对数组了吗？
- [ ] 新的「给 AI 看的」清单，过滤了 `kind != tool` 吗？
- [ ] 新的回传逻辑，来源是指令还是工具？指令来源绝不进 AI。
- [ ] 指令执行失败时，错误会不会被包装成工具结果回传？
- [ ] 有没有用「标记字段 + 过滤」的旧写法？应改为源头分开。

### 5.6 历史事故

1. `open_drawer` 等 5 个抽屉控制工具混进 `/tools` 与 System Prompt（指令入侵工具目录）。
2. 指令执行端出现在设置页工具列表（用户报「指令入侵工具列表」）。
3. 指令执行产生的网络错误回传给了 AI（指令流向 AI）。

共同根因：缺一份权威的隔离规范，改动时无据可依。

## 六、投递任务规范

> 本节描述的「外部卡片」机制，在翻译员与工具服务拆分中正名为**通用投递队列**，
> 定位为与语音同级的公共服务，任意两端可对接。见 `docs/split-mirror-and-tools-service.md` 第 3.6 节。

### 6.1 什么是投递任务

投递任务是「外部工具主动联系网页 AI」的载体。用户在扩展抽屉里输入需求、附加已选元素，提交后组装成一张卡片，发往网页 AI 处理。

与工具卡片的区别：工具卡片是 AI 调用工具后生成的执行记录；投递任务是用户从扩展侧主动发起、投给 AI 的任务入口。

### 6.2 信封结构

```json
{
  "type": "external-call",
  "nonce": "唯一标记",
  "request": "任务正文",
  "source": "qq",
  "openid": "用户标识",
  "msg_id": "消息标识",
  "page_url": "页面地址"
}
```

| 字段 | 说明 |
|---|---|
| `type` | 固定 `external-call`，用于识别 |
| `nonce` | 本次投递唯一标记 |
| `request` | 任务正文（用户诉求） |
| `source` | 来源渠道，如 `qq` |
| `openid` | 来源用户标识 |
| `msg_id` | 来源消息标识 |
| `page_url` | 关联页面地址 |

### 6.3 角色语义（勿混淆）

会话中存在三类消息来源，判定靠 `msgSource` 字段：

| 来源 | msgSource | 是否算用户发言 |
|---|---|---|
| 用户网页亲口说 | `user` | 是 |
| 工具结果（`bridge-chat-res`） | `tool` | 否，属工具产物 |
| 投递任务（`external-call`） | 归入 `user` | **是** |

要点：

- 工具结果是工具产物，**不计入**用户发言，也不写入工作记忆的「用户关键信息」。
- 投递任务**算用户发言**。来源渠道（如 QQ）不影响该判定。
- 此语义曾出过错（曾擅自认定「投递任务不算用户发言」），改动前必须核对用户原话。

### 6.4 投递语义

- **发送即结束**：投递后即结束，**不等待回传**。
- 登记即返回，卡片入列即确认已展示，此后不再投递。
- 任务进展、结论与方案，由网页 AI 通过 `push_message` 工具**主动推送**给用户。

### 6.5 存储与渲染

- 存 `conv.externalCards`，**按会话隔离**并持久化。
- 带 `anchorKey`（消息树 key）：渲染时按锚点插入到对应消息之后；锚点不在当前列表时放到末尾。
- 镜像区会跳过已处理且无消息本体的卡片，避免与消息本体重复显示。

### 6.6 投递方约定

- 组装信封 → 提交工具服务 → 工具服务渲染卡片并自动发送至网页 AI。
- 内容脚本不直接发网络请求，一律走 `proxyFetch`。
- 投递后不轮询回执，等 AI 用 `push_message` 联系。
