# 私服请求中继技能 · 需求与进度

> 状态：**调研完成，待开发**
> 最后更新：2026-10-29
> 关联工程：嘉立创 AI 巧绘私服（`pro-schematic-ai/ai_schematic_private`）

---

## 一、要解决的问题

私服的模型额度是共享的。当 ARK 总余额耗尽或全部模型不可用时，用户从 AI 巧绘客户端发出的每一次对话都会直接报错，体验是硬中断。

而本地 chat-bridge 通常挂着网页 AI（额度充裕）。这个技能要做的就是：**私服扛不住时，把请求交给本地网页 AI 顶上去。**

## 二、目标行为

```
用户 → AI巧绘客户端 → 私服 /api/ark-chat
                          ├─ 有可用模型 → 正常转发（现有行为不变）
                          └─ 无可用模型 → 请求入队挂起（最多 30 秒）
                                            │
                  本地 chat-bridge 技能主动拉取 ←┘
                          │
                    按用户分配网页会话 → 驱动网页 AI 回答 → 回填结果
                          │
              私服把结果按 Responses API 格式返回给客户端
```

**超时兜底**：入队 30 秒内无人消费，私服照原样返回错误。队列不是永久的，避免请求无限堆积。

## 三、核心设计决策

### 3.1 为何要「按用户分配网页会话」

网页 AI 的上下文是**按会话隔离**的。若多个用户的请求混进同一个会话，会出现两个问题：

1. **上下文污染**——A 用户的问题被 B 用户的对话历史影响，回答跑偏；
2. **回复归属错误**——技能捕获到回复时，无法判断这条回复该回填给哪个请求。

因此：**每个私服用户绑定一个固定的网页会话**，同一用户的多轮对话在同一会话内延续（保留上下文），不同用户互不干扰。

### 3.2 工程里有「两个会话」，必须分清

这是最容易踩错的地方：

| | 抽屉会话 | 网页会话 |
|---|---|---|
| 存哪 | 后端 `memory/conversation` + 抽屉内存 `this.conversations` | DeepSeek 站点自己的存储 |
| 切换方式 | `selectConversation(id)` → `applyConversation` | 点击页面左侧的会话项 |
| 影响范围 | 只影响抽屉展示的历史记录 | 影响网页 AI **实际使用的上下文** |
| 现有指令 | `/ss`（按序号切换） | **无** |

`/ss` 走的是前者：它只重绘抽屉里的历史，**完全不碰网页右侧的会话列表**。
（佐证：`clearAllConversations` 里注释写着「后端唯一权威：逐个删后端会话」。）

本技能要的是驱动**网页 AI** 切换上下文，必须操作网页会话。
**这是全新能力，`/ss` 不可复用**，最多复用它「参数解析 + 分支判断」的写法。

### 3.3 为何需要「按 id 切换」而非按序号

技能在代码里调用，需要**精确、稳定**的锚点：

- 序号依赖列表当前顺序，会话一多、有新会话插入，序号就漂移；
- id 是稳定的唯一标识，代码可以持久化「用户 → 会话 id」的映射并直接定位。

## 四、现状调研结论

### 4.1 可复用的既有实现

**`chat-bridge-v2/skills/eda_bridge/`** —— 曾实现过一次同类对接，思路是「用本地网页 AI 顶替嘉立创私服模型」，与本次需求方向一致。

可复用的部分：

| 文件 | 可复用的内容 |
|---|---|
| v2 工程的 `serve_ark.py` | **Responses API 响应体构造**（`id`/`object`/`status`/`usage` 等必需字段）、**input 解析**（`extract_question` 跳过工具调用条目、`extract_system` 取 system 全文、`summarize_tools` 压缩工具清单）、**工具调用转换**（`callTool` 协议壳封装）、token 估算 |
| v2 的 `SKILL.md` | 技能说明的组织结构、回答格式约定 |
| v2 的 `tool.json` | 端点声明方式 |

不可直接复用的部分：

- 它的等待机制是「轮询卡片状态」，依赖 `_host/cards` 接口——**当前工程没有这套接口**；
- 它是「一请求一卡片」的人工中转模式，本次需要的是**自动消费队列**，机制完全不同。

### 4.2 当前工程已具备的能力

| 能力 | 位置 | 用途 |
|---|---|---|
| 自动写入并发送 | `extend/content/03_bridge.js` → `pasteToWebpageAI(text, autoSend)` | **驱动网页 AI 发言的核心**。用原生 setter 写值 + 派发 input 事件，等发送按钮就绪后回车 |
| 生成结束检测 | `extend/content/04_observer.js` → `scheduleScan` + `waitSendReady` | DOM 静默 N 毫秒后才解析，避免生成中抓取 |
| 回复捕获 | 扩展上报机制 + `web_bridge/web_inbox.py` | AI 回答完成后入库 |
| 卡片投递 | `routes/cards.py` + `card_bus` | 仅「发送即结束」，**不支持等待回填** |
| 远程指令通道 | `remote_bridge/command_dispatch.py` 等 | QQ 侧指令分发，可作技能调用的参考 |
| 抽屉会话切换 | `extend/dialog/parts/04_sessions.js` → `selectConversation` | **仅操作抽屉会话，与网页会话无关** |

### 4.3 缺失的能力

1. **私服侧**：无请求队列、无挂起等待、无管理员可视化列表
2. **chat-bridge 侧**：无「主动拉取队列」的机制、无「用户 ↔ 网页会话」绑定关系存储
3. **网页会话操作**：无法按 id 定位并切换网页左侧的会话项

## 六、待确认事项

1. **超时窗口**：私服侧等 30 秒，但技能从拉取到网页 AI 生成完成通常需要更久。若网页 AI 已经开始生成，私服却已超时返回错误，这次生成的结果就无处回填。
   - 备选：私服在超时后仍保留队列项一段时间，允许「迟到的回填」被丢弃或缓存给用户下次查看。
2. **并发上限**：网页 AI 通常只能同时处理一个会话。若队列里积压多个用户的请求，技能必须串行处理，后面的请求可能等不到 30 秒窗口。
   - 备选：私服侧按到达顺序排队，只把队首交给技能；或技能一次只领取一条。
3. **用户标识**：私服用 `user_uuid` 区分用户，技能侧用它做绑定键。需要私服在队列接口里回传该字段。
4. **新建会话的语义**：`/new` 是新建空会话还是清空当前会话？需先确认再决定「新建」该怎么调。
5. **用户手动干扰**：技能自动切会话时，用户可能同时在网页上手动操作。需要检测并避让，避免两者打架。

## 七、风险提示

- **阶段零可能推翻方案**：如果网页会话 id 不在 DOM 上暴露、或切换有强防护，按 id 切换可能做不成。必须先验证。
- **时序竞态**：请求挂起、技能拉取、网页生成、结果回填是四段异步流程，任何一环超时都会导致「回复找不到主人」。需要明确的租约与超时策略。
- **网页 AI 状态不可控**：用户手动操作与技能自动化会冲突。
- **误伤正常流程**：私服队列只在「无可用模型」时启用，绝不能影响正常转发路径。
