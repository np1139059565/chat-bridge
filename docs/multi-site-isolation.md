# 多网页 AI 并存的隔离机制

一台电脑同时开多个网页 AI（千问 / 元宝 / Kimi / DeepSeek / GLM …）时，
需要保证各路消息与指令不互相串台。本文说明隔离是怎么做的、边界在哪。

## 一、三条隔离线

| 场景 | 隔离键 | 管什么 |
|---|---|---|
| 记忆与存档 | 站点 id | 消息树、会话存档、卡片执行签名 |
| 手机网页端 | 站点 id | 收件箱消息、顶部站点下拉 |
| QQ / 企微等单窗口通道 | 页面地址 | 指令投递与消息推送 |

**为什么手机端用站点、通道用页面**：手机端是你自己主动切着看，按站点分最直观；
单窗口通道是被动接收，必须精确到「那一个标签页」，按页面分才不会串。

## 二、手机端：站点下拉

顶栏有一个下拉框，列出所有已配置站点：

- 有在线页面的站点前面带绿点（●）
- 选中另一个站点 → 整页重载，游标与已渲染内容全部按新站重建

**为什么整页重载**：局部重置要处理游标、已渲染 DOM、去重集合、倒计时状态好几处，
漏一处就是脏数据。整页重载虽粗暴，但不可能漏。选择记在 localStorage。

**站点标识口径**：收件箱消息的 `site_key` 存站点 id（如 `deepseek`），
不是域名。内容脚本上报时用 `profileId`（站点 id），不用 `siteKey`（域名）——
两者混用会导致「消息按域名打标、按 id 查询」，切站后一片空白。

## 三、单窗口通道：/page 绑定

QQ 与企微都是单窗口。不绑定时所有页面的消息都推给它，多个 AI 的回复会混在
同一个聊天窗口。绑定后各看各的。

| 指令 | 说明 |
|---|---|
| `/page`（别名 `/pg`） | 列出在线页面与当前绑定 |
| `/page 1` | 把**当前这条通道**绑到第 1 个页面 |
| `/page deepseek` | 按地址片段绑（唯一命中才算，有歧义报错不猜） |
| `/page off` | 解除当前通道的绑定 |

**绑定作用域是「当前通道」**：在 QQ 里敲就绑 QQ，在企微里敲就绑企微。
这是它与其他指令的关键区别——其他指令作用于全局，这条是分通道的。

绑定持久化在运行时配置的 `channel_bindings` 键（本机偏好，不入库），重启后保持。

### 双向隔离

| 方向 | 行为 |
|---|---|
| 指令下发 | 只投给该通道绑定的页面；未绑定时不限页面（旧行为） |
| 消息推送 | 已绑定通道只收该页面的消息；未绑定全收；消息无页面来源时绑定通道也收（避免丢历史） |

### 在线页面表

抽屉打开时显式上报上线（`POST /api/pages/online`），关闭或卸载时显式上报下线
（`POST /api/pages/offline`）。上下线是事件而非超时推断：页面切到后台被浏览器
节流时仍然是打开的页面，按超时判离线会让它的消息改投到别的站点。

轮询（`/api/cards/pending` 与 `/api/commands/pending` 的 `page` 参数）只作幂等兜底登记，
不决定页面是否在线。

**内存态，重启后清空**——页面在线与否本就随标签页开关变化。

### 站点无在线页面时的投递

指定了站点、但该站点此刻没有打开的抽屉时，投递直接失败并回执
`site_offline`（HTTP 409），消息不入收件箱。此前会退回「不限页面」把它投出去，
结果卡片被任意页面取走，实测曾从 GLM 落到 DeepSeek。回执失败比投错更诚实，
也更好排查。

## 四、已知限制

1. **通道绑定的是页面，页面关了绑定就失效**。重新打开同一站点的新标签页地址会变，
   需要重新 `/page`。这是刻意的：绑定一个已关闭的页面地址没有意义。

2. **同一通道不能同时看多个页面**。`/page` 一次只绑一个，绑新的覆盖旧的。

3. **手机端切换站点看不到别的站的历史**。这是隔离的必然结果——每个站一条独立时间线。

## 五、排查口径

| 现象 | 先看什么 |
|---|---|
| 手机端切站后一片空白 | 消息 `site_key` 是站点 id 还是域名（应为 id） |
| 手机端发消息跑到了别的页面 | 前端发消息是否带了 `site`；后端是否按它解析出目标页面 |
| 指令发了没反应 | 该通道是否绑了别的页面；`/page` 看目标页是否在线 |
| 两个页面消息混在一起 | 通道是否未绑定；`/page` 查看 |
