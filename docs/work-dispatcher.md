# 工作对话 · 需求分发方

> 本文件是需求分发方（下称「分发方」）的职责约定、进度记录与交接说明。
> 任何接手此角色的人或 AI，先完整读一遍本文件，再读 `.\docs\work-board.md`。

## 一、角色定位

分发方**不写业务代码**，只做四件事：

| 职责 | 具体做什么 |
|---|---|
| 定规格 | 维护 `.\docs\split-mirror-and-tools-service.md` 为唯一规格来源 |
| 拆任务 | 把阶段拆成可独立完成的工作单元，写清范围、禁区、验收标准 |
| 审代码 | 执行方交付后，按验收标准逐条核，不看「它说完成了」 |
| 控节奏 | 把控阶段边界、合入时机、分支合并顺序 |

**分发方可以改的文件**：`.\docs\` 下的所有文档、规格文档。

**分发方不改的文件**：`.\flask_server\`、`.\extend\`、`.\skills\` 下的任何代码。

## 二、工作约定（硬约束）

### 2.1 路径写法

- **只用工程内相对路径**，形如 `.\flask_server\routes\tools.py`、`.\docs\work-board.md`
- **禁止出现任何绝对路径**。各工作区根目录不同，绝对路径必然对不上
- 三个执行方文档（`.\docs\work-ai-a.md`、`.\docs\work-ai-b.md`、`.\docs\work-ai-c.md`）与本文件必须遵守同一条

### 2.2 分支与合入

| 角色 | 分支 |
|---|---|
| 分发方 | `main` |
| AI-A | `work/ai-a` |
| AI-B | `work/ai-b` |
| AI-C | `work/ai-c` |

**合入流程**：

1. 执行方推送自己的 `work/ai-*` 分支
2. 用户告知分发方「更新 git」
3. 分发方拉取该分支，逐条核对验收标准
4. 核对通过 → 合并到 `main`，推送
5. 核对不通过 → 在执行方文档的提问区写明哪条不达标，等其修正

**不合并半成品。** 验收不通过就不合。

### 2.3 质量闸的现状与处理

存量欠账已由分发方在 `main` 上统一登记基线（`a493941`），2026-11-10 实测 `quality_rules.py` 统一闸门 exit 0、全部条目为 `[已知]`、新增文件零 `[新增]` 违规，`quality` 恒红问题已消除，提交不再需要跳过。

| 闸门 | 现状 | 处理方式 |
|---|---|---|
| `quality`（结构质量十二项） | 已转绿；存量欠账按基线登记 | 正常提交，不用 `--no-verify` |

**判断归因的方法**：把待提交改动 stash 掉，在干净 HEAD 上复跑闸门。若仍失败，说明是存量问题，非本次引入。

**存量欠账的登记权归分发方**：`scripts\quality_baseline.json` 是全仓共用的一份基线，执行方各自修改会在合并时冲突。存量欠账由分发方在 `main` 上统一登记（`python scripts\quality_rules.py --update-baseline`），登记单独成一次提交，执行方 rebase 后正常提交，不使用 `--no-verify`。

### 2.3.1 提问与答复的权责

执行方文档第四节分两部分，权责不同：

| 部分 | 谁写 | 说明 |
|---|---|---|
| 提问 | 执行方 | 卡住时登记问题、已尝试什么、卡在哪 |
| 答复 | 分发方 | 执行方**不得**自行填写 `[答复]` |

执行方等不到答复时，正确做法是停在该处、保持分支可回退，而不是自行推定答复并继续。自行填写答复视为越权，分发方审核时会在文档中重述真实答复并记录。

### 2.4 提交信息写法

- 只描述改动本身
- 不写对话过程、不写「按某要求」、不写否决过的方案
- 一个任务一次提交

### 2.5 预下发节奏（避免执行方空转）

执行方只有一个「当前任务」槽位，验收期间会空转。为利用这段时间，采用预下发：

**时机**：分发方**开始审核**某个分支时，把下一个任务写进该执行方文档的「排队任务」槽，并标注「审核中，可开工」。不在执行方刚提交时预下发——提交只代表代码写完，形态可能还会变。

**判断标准**：先问一句「若正在审核的任务返工，排队任务会不会被连累」。

| 情况 | 处理 |
|---|---|
| 排队任务依赖正在审核任务的接口或数据结构 | 预下发，但注明「依赖 X 定稿，返工时可能随之调整」 |
| 排队任务与正在审核任务无耦合 | 直接预下发 |
| 排队任务明确依赖正在审核任务验收通过 | 不预下发，等验收 |

**返工时的处理**：分发方在执行方文档提问区写返工意见，同时**撤回或改写**排队任务。执行方以撤回后的内容为准。

**执行方收到预下发任务时**：当前任务未收尾前不得动手写排队任务的代码；可以读规格、做准备。当前任务一收尾，无需再等指令，直接开工排队任务。

## 四、审核清单

每次收到执行方的分支，按此表逐条核。**任一条不通过就不合并。**

### 4.1 通用项（每个任务都查）

| # | 查什么 | 怎么查 |
|---|---|---|
| 1 | 改动是否落在任务范围内 | `git diff main --name-only`，逐个比对任务里「可以碰的文件」 |
| 2 | 有无越界触碰禁区文件 | 同上，比对「不要碰」清单 |
| 3 | 测试是否覆盖新增行为 | 看测试文件，确认新增场景有用例 |
| 4 | 全量测试是否通过 | 在 `.\flask_server` 下跑测试，看通过数与基线对比 |
| 5 | 提交信息是否只描述改动 | 读提交信息，看有无对话痕迹 |
| 6 | 文档是否同步 | 改了接口的，检查 `.\docs\api-reference.md` 是否已补 |

### 4.2 任务专属项

见各执行方文档「验收标准」一节，逐条实测，不采信执行方的自述。

### 4.3 实测而非采信

**关键原则**：执行方说「已完成」，不等于完成。分发方要自己跑一遍验收脚本、自己构造测试数据、自己确认边界行为。

举例：AI-C 的任务要求「自定义配置逐字节一致」，分发方要自己构造一个含中文、嵌套、null 的配置，实际存一遍取一遍做深比较，而不是看它说测过了。

## 五、交接说明

接手此角色时，按顺序做：

1. 读本文件全文
2. 读 `.\docs\work-board.md`，了解三个执行方的实时状态

5. 检查各 `work/ai-*` 分支是否有新提交待审
6. 若有待审分支，按第四节清单审核
7. 若某执行方在提问区留了问题，答复或转交用户决定

**不要做的事**：

- 不写业务代码
- 不因为赶进度放宽验收标准
- 不在执行方未完成时提前合并
- 不把「闸门红」当作拒绝合入的通用理由——先按 2.3 节判断归因
