# 安卓版 AI 接口封装工程 · 详细计划书

> 状态：**待审批**
> 日期：2026-10-30
> 需求提出：用户（QQ 侧下达）
> 关联工程：chat-bridge（复用其网页解析与发送驱动能力）

---

## 一、需求复述

在安卓手机上搭一套「把网页 AI 变成本地 AI 接口」的工具，包含两半：

1. **浏览器插件**（Firefox 扩展）：只做一件事——把网页 AI 的回复抓下来，整理成标准结构（思考内容、正文、token 用量）；
2. **本地服务**（安卓程序）：与插件通过本地 HTTP 通信，对外暴露标准 AI API，其它软件填一个地址和密钥就能用。

明确不做的：不需要原工程那些复杂的本地文件操作（读写文件、跑命令、搜代码等）。

## 二、这东西的本质

打个比方：网页 AI 是个只肯在自家柜台接待客人的老师傅，别的软件想找他办事，得亲自跑到柜台前排队打字。这个工程相当于在老师傅柜台旁开了一个「代办窗口」——别的软件把请求交到窗口，由窗口的人去柜台前替它问、把答案抄回来，再按标准格式递出去。

代办窗口有两个岗位：

- **跑腿的**（Firefox 扩展）：站在网页 AI 页面里，负责「打字提问」和「抄回答案」；
- **柜台**（安卓本地服务）：对外收单、对内派活、把抄回来的答案整理成标准单据。

## 三、整体架构

```
外部软件（任意，支持标准 AI API）
        │  HTTP  POST /v1/chat/completions
        ▼
┌─────────────────────────────┐
│  安卓本地服务（柜台）        │
│  · 鉴权（密钥校验）          │
│  · 请求队列与租约            │
│  · 响应体构造（标准格式）    │
│  · 流式输出（SSE）           │
└──────────┬──────────────────┘
           │  本地 HTTP（127.0.0.1）
           ▼
┌─────────────────────────────┐
│  Firefox 扩展（跑腿的）      │
│  · 轮询取任务                │
│  · 写入提问并触发发送        │
│  · 等生成结束                │
│  · 抓取思考 / 正文 / 用量    │
│  · 回填结果                  │
└──────────┬──────────────────┘
           │  DOM 操作
           ▼
      网页 AI（手机浏览器里打开）
```

**关键约束**：网页 AI 通常一次只能跑一个对话。所以柜台必须串行派活——同一时刻只有一个请求在跑腿，其余排队。这是本方案最硬的物理限制。

## 四、技术难点与对策

### 4.1 token 用量拿不到真实值（必须先说清）

网页 AI 的页面上**不显示 token 用量**，这是产品设计，不是我们能改的。

可选做法：

- **估算**：按字符数折算（中文约 1 字 ≈ 0.6~1 token，英文约 4 字符 ≈ 1 token）。误差通常在 10%~30%。
- **标零**：明确返回 0，并在响应里注明「本接口不提供真实用量」。
- **留字段**：结构里保留字段，值填估算值，另加一个自定义字段标记这是估算。

**我的建议**：填估算值 + 明确标记「estimated」，调用方自己判断要不要用。不假装是真实值。

### 4.2 思考内容能拿到，但要按站点适配

原工程已有成熟实现：GLM 用 `.advance-thinking`，DeepSeek 用 `.ds-think-content`。这部分可以整体搬过来。

**风险**：手机浏览器的页面结构和桌面版可能不同（响应式布局可能改变 DOM 层级）。需要实测。

### 4.3 手机 Firefox 的扩展限制（最大风险）

Firefox for Android 长期只支持一小批「官方推荐」扩展，普通的自建扩展**未必能装**。即使能装，content script 能否注入到 AI 站点页面也需要验证。

三条备选路径（见第六节选项 A/B/C）。

### 4.4 生成结束的判定

原工程的做法是「DOM 静默 N 毫秒后认为生成完毕」。这在手机上要重新调参：手机性能弱、网络慢，静默时间太短会截断，太长会让接口变慢。

### 4.5 流式输出与网页生成的对齐

标准 AI API 支持流式（一个字一个字往外吐），但网页 AI 是整段生成完后我们才抓得到。

**对策**：做不到真流式。可以做成「伪流式」——等生成完毕后，把结果按字符切片、以 SSE 格式分批吐出，让调用方看到打字效果。这是诚实的妥协，要在文档里写清楚。

## 六、需要你拍板的选择

### 选择一：插件形态（最关键，决定整个方案成败）

**1. 坚持 Firefox 扩展**
- 好处：符合你的原始设想，插件独立于服务，用户可自由开关。
- 坏处：**手机 Firefox 对自建扩展极可能不开放**，阶段零大概率卡住；即使能装，后台保活也差。

**2. 安卓应用内嵌 WebView**
- 好处：彻底绕开扩展限制，注入脚本完全自主；服务和页面同进程，通信不走网络，更稳更快；省电策略也好控制。
- 坏处：AI 页面在应用内打开，不是在用户惯用的浏览器里；页面样式和交互可能和正式浏览器有差异。

**3. 双轨：先试扩展，不通过就转 WebView**
- 好处：先花小成本验证你的原始设想，行不通立刻切换，不浪费时间。
- 坏处：阶段零要多花半天到一天做验证。

**我的建议是 3**：先花半天验证 1 是否可行，不行就走 2。这不是骑墙，是因为 1 的可行性真的取决于 Firefox 官方政策，不是我们能决定的。

### 选择二：安卓端技术栈

**1. Termux + Python**
- 好处：几乎能原样复用现有 Flask 代码，开发最快。
- 坏处：需要用户自己装 Termux，不是「装个应用就能用」；后台保活差；不适合交付给普通人。

**2. Python 打包成 APK（Kivy / BeeWare）**
- 好处：复用 Python 代码，又能做成正规 APK。
- 坏处：打包体积大（几十 MB 起），启动慢，安卓上跑 Python 有些坑。

**3. 原生 Kotlin 重写**
- 好处：体积小、启动快、后台稳定、体验最像正规应用。
- 坏处：服务端逻辑要用 Kotlin 重写一遍，工作量最大。

**我的建议是 2**：能复用现有逻辑，又能交付成 APK。如果你只自己用、不介意装 Termux，选 1 最省事。

### 选择三：token 用量怎么处理

**1. 返回估算值并标记为估算**
- 好处：调用方能拿到大致量级做统计。
- 坏处：数值不准，可能误导按量计费的场景。

**2. 固定返回 0，文档注明不支持**
- 好处：绝不误导。
- 坏处：某些客户端可能因用量为 0 而报错或显示异常。

**3. 返回估算值，同时提供开关让用户选择是否启用**
- 好处：两种场景都照顾到。
- 坏处：多一个配置项。

**我的建议是 1**，简单直接，且明确标注了来源。

### 选择四：首期支持哪些 AI 站点

**1. 只做 DeepSeek**
- 好处：聚焦，先把链路跑通。
- 坏处：换站点要再适配。

**2. DeepSeek + 智谱清言（沿用原工程已有的两套规则）**
- 好处：直接复用现有站点配置，成本低。
- 坏处：两套都要在手机上验证。

**我的建议是 2**，因为规则已经写好了，多支持一个几乎不增加成本。

## 七、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 手机 Firefox 不支持自建扩展 | 方案 1 直接失效 | 阶段零先验证，不通过转 WebView |
| 手机端 DOM 与桌面不同 | 抓取失败 | 阶段零实测，按需补选择器 |
| 安卓后台杀进程 | 服务掉线，调用方连不上 | 前台服务 + 电池优化白名单引导 |
| 网页 AI 登录态过期 | 所有请求失败 | 检测到登录页时明确回传错误 |
| 网页 AI 限流或验证码 | 请求被拒 | 识别拦截页，回传明确原因，不静默重试 |
| 用户手动操作页面 | 与自动流程打架 | 检测页面焦点与输入状态，冲突时让路 |
| 生成耗时超过调用方超时 | 调用方先断开 | 队列保留结果一段时间，允许迟到取回 |

## 八、明确不承诺的事

为避免后期扯皮，以下三点先说清楚：

1. **做不到真流式**。网页 AI 生成完才抓得到，所谓流式是事后切片模拟的。
2. **拿不到真实 token 用量**。页面不显示，只能估算。
3. **并发只有 1**。网页 AI 一次只能跑一个对话，多个请求必须排队。这不是实现问题，是物理限制。
