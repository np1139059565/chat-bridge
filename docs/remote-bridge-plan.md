# 远程桥接方案（QQ ↔ 网页 AI）

本文档面向「下一个接手的人 / AI」，描述如何让用户在手机上通过 QQ 与网页 AI 对话，从而在离开电脑时远程查看 AI 回复、远程下达指令。

---

## 一、需求与目标

用户不可能一直守在电脑旁。目标是在手机 QQ 里与一个机器人对话，实现三件事：

1. **看得见**：网页 AI 的回复一产生，就能推到 QQ 上看到。
2. **发得出**：在 QQ 里发的话，能送进网页 AI 对话框，等同于用户自己在电脑上输入。
3. **点得动**：在 QQ 里能点击预设指令（如 `/start`、`/stop`），触发电脑端的预设动作。

配套需要一个统一设置页管理这些能力。

---

## 二、前提与边界

### 前提一：抽屉保持开启

远程桥接的全部能力，以「用户离开前抽屉开着」为前提。

工程的设计是「面板关闭即销毁」：`setDialogVisible(false)` 会停掉观察器与定时器并删除 iframe。面板关闭后，没有人轮询卡片、没有人解析对话，链路自然中断。

这不是缺陷，而是符合用户意图的——**关闭抽屉，就代表用户此刻不需要远程工作。** 因此本方案不改动内容脚本的生命周期，只在设置页给出一句提示：远程功能需保持面板开启。

### 前提二：已有可用的 QQ 机器人

走官方 API，机器人凭证由用户在设置页填入。

### 明确不做

- **不做多页面定向**：不区分「QQ 消息该投给哪个网页 AI 页面」。同时开着多个页面时，按卡片总线既有行为——哪个抽屉打开着谁取走。
- **不做安全白名单**：不限制发送者身份。

---

## 三、核心定位：对网页 AI 完全透明

这是本方案的第一原则，也是架构选型的出发点。

**网页 AI 全程感知不到 QQ 桥接层的存在。**

- 从 AI 的视角看，只有两种东西：用户消息、工具消息。QQ 来的话被包装成一张普通外部卡片，和调试扩展推来的卡片长得一模一样。
- AI 不需要知道自己的回复会被转发到 QQ，也不会在工具列表里看到一个叫 `qq_push` 之类的工具。
- QQ 桥接层不注册 provider、不进工具目录、不写入 System Prompt。

一句话：**桥接层是夹在 QQ 和网页 AI 之间的传声筒，两边都不知道对方存在，更不知道传声筒存在。**

---

## 四、QQ 侧能力约束

QQ 官方在 2025 年 4 月 21 日起不再提供主动推送能力。「AI 随时主动弹一条消息到 QQ」这条路被官方堵死。可行的官方路径有两条：

| 路径 | 能力 | 触发条件 |
|---|---|---|
| 被动回复窗口 | 用户发消息后 **60 分钟内**可无限次回复 | 用户先发过消息 |
| 指令面板 | 点击按钮把命令填入输入框，常驻展示 | 无需用户先发消息 |

本方案主用被动回复窗口。

### 窗口续期机制

被动回复窗口不是固定的 60 分钟，而是**从「最近一条用户消息」起算 60 分钟**。用户每发一条新消息，就获得一个新的 `event_id`，窗口从这条新消息重新计时。因此：

- 用户在窗口内持续发消息 → 窗口不断向后滚动，实际可以无限延长。
- 桥接层始终持有**最新一条用户消息的 `event_id`**，所有推送都用它。
- **机器人无法单方面续期**：不能自己造一条消息来重置窗口。唯一的续期动作来自用户。
- 用户静默超过 60 分钟后，窗口关闭，推送暂停，等待用户再次发消息唤醒。

## 五、桥接层住在哪里

**桥接层作为独立模块住在 Flask 服务进程内，自己维持 QQ 长连接。**

理由：QQ 消息随时可能到来，桥接层必须一直在岗。它不能依赖浏览器——如果它住在 Chrome 扩展里，用户离开电脑、浏览器关掉，功能立即失效，恰恰违背需求。

```
QQ 手机端
   │  ①消息（C2C_MESSAGE_CREATE）      ▲ ④推送（被动回复）
   ▼                                    │
┌─────────────────────────────────────────────────┐
│  flask_server/remote_bridge/                     │
│   ├── qq_client.py      QQ 协议层（鉴权 / 收发）   │
│   ├── qq_gateway.py     WebSocket 长连接 + 事件分发 │
│   ├── message_router.py 消息分类 → 推送（旁听侧）   │
│   ├── command_panel.py  指令注册与回调（指令侧）     │
│   └── bridge_store.py   配置与映射持久化            │
└──────┬───────────────────────────────┬──────────┘
       │ ②POST /api/cards              │ ③上报新增
       ▼                               ▼
  卡片总线（既有）              消息树 / 抽屉（既有）
       │
       ▼
  抽屉轮询 → 发送到网页 AI
```

### 5.1 接入方式：WebSocket 长连接

QQ 消息的接收走**官方 Bot API 的 WebSocket 网关**（与 OpenClaw 的 qqbot 插件同一路径）：用 AppID + AppSecret 建立长连接，机器人主动连出去，**本地服务不需要公网地址**，也不需要内网穿透。

```
qq_gateway.py
   ├─ 用 AppID + AppSecret 换 access_token
   ├─ 建 WebSocket 连接，心跳维持
   ├─ 断线自动重连
   └─ 收到 C2C_MESSAGE_CREATE 事件 → 交给 message_router
```

### 5.2 对外两个口子

桥接层对外只需两个口子：

- **出口**：内部调用 `card_bus.bus.create()`，把 QQ 消息塞进卡片总线（进程内调用，不走 HTTP）。
- **入口**：一个给抽屉用的上报接口（`POST /api/bridge/report`），让抽屉把当前可见切片告诉桥接层。

抽屉关闭期间，这两个口子都静默——不收卡片、不上报，符合「关闭即代表不工作」的前提。

## 六、三类消息的分流与推送

### 6.1 分类规则

消息树里每个节点已有 `role` 字段，但工具调用需要更细的判定：

| 类别 | 判定条件 | 处理 |
|---|---|---|
| 用户消息 | `role === 'user'`，且非 external-call 信封 | 推送到 QQ（标记 `👤`） |
| 工具消息 | `role === 'user'`，且 `parseExternalCall()` 命中 | 推送到 QQ（标记 `🛠`） |
| AI 消息 | `role === 'assistant'` | 推送到 QQ（标记 `🤖`） |

QQ 自己发来的消息同样以 external-call 信封存在，必须通过 `payload` 里的来源标记识别出来，**不再回推 QQ**，否则用户会看到自己刚发的话被机器人复读。

### 6.1.1 推送粒度

一条 assistant 消息内部有多个块（思考 / 正文 / 代码 / 列表 / 表格等），推送到 QQ 时按以下规则取舍：

| 块类型 | 是否推送 | 说明 |
|---|---|---|
| 思考过程 | 默认不推，设置里可开 | 通常冗长，手机上看着累；需要监控 AI 是否跑偏时再开 |
| 正文（段落 / 标题 / 列表 / 引用 / 表格） | 推 | 这是用户最关心的内容 |
| 工具调用代码块 | 推 | 用户在手机上看不到抽屉里的卡片，不推就不知道 AI 正在调工具。只推「调用了什么工具、参数是什么」，不推完整 JSON |
| 普通代码块 | 推 | 同上，按代码原文呈现 |

同一条消息内的块合并为一条 QQ 消息发出（而非逐块拆成多条），避免刷屏。

### 6.2 推送触发点与去重记账

抽屉在 `ingestMessages()` 完成后，把当前的可见切片上报给桥接层。注意：`sendPage` 每次都提取**整个可见切片**全量推送，`upsertTree` 返回的 mode（append / prepend / full）只说明「树怎么长的」，**并不告诉你哪几条是新的**。

因此「哪些消息该推」由桥接层自己记账：

- 桥接层维护一份「已推送消息 id 集合」，按会话隔离、可持久化。
- 每次收到上报，拿全量消息比对集合，差集才是真正要推的新消息。
- 推送后把新 id 写入集合。持久化保证服务重启后不会把历史消息全量复推、刷屏用户手机。

抽屉在这里只是「小喇叭」：把看见的消息喊给桥接层，分类、去重、往 QQ 推全由桥接层完成。抽屉不用懂 QQ，也不管长连接。

### 6.3 推送通道

- 桥接层持有最新一条用户消息的 `event_id`，窗口内的所有 AI 回复都用它作被动回复发出。
- 用户每发一条新消息，`event_id` 更新，窗口自动向后滚动延长。
- 窗口快过期且仍有待推送内容时，回一条提醒：「当前会话窗口即将关闭，请回复任意消息以继续接收」。
- QQ 单聊支持 Markdown（`msg_type=2`），三类消息用不同前缀区分。

## 七、四条链路

### 7.1 QQ → 网页 AI（远程发消息）

```
QQ 用户发消息
   → qq_gateway 收到 C2C_MESSAGE_CREATE
   → message_router 包装成 external-call 卡片
      { type:'external-call', title:'QQ用户', content:'原文',
        payload:{ source:'qq', openid, event_id, ts } }
   → card_bus.bus.create() 登记
   → 抽屉轮询取走 → 渲染 → auto_send → 网页 AI
```

卡片类型沿用既有 `external-call`，与调试扩展推来的卡片同构。`payload` 里带 QQ 来源标记，供推送侧去重。

**自动开关照旧，不为 QQ 卡片破例。** 卡片是否自动发送，仍由抽屉里那个「自动」复选框决定。用户没勾，卡片就停在抽屉里等手动发送——这是用户自己的选择，桥接层不代他决定。

### 7.2 网页 AI → QQ（远程看回复）

```
抽屉 ingestMessages() 完成
   → 上报当前可见切片（全量）给桥接层
   → 桥接层与「已推送 id 集合」比对，取差集
   → message_router 分类（用户 / 工具 / AI）
   → 过滤 QQ 来源（去重）
   → 走被动回复窗口推送到 QQ
   → 新 id 写入集合并持久化
```

### 7.3 QQ 指令 → 预设动作

QQ 官方提供两级交互能力：

- **指令面板**：常驻显示，点击命令按钮自动把命令名填入输入框，用户回车即发送。最多 20 个元素，名称最多 14 字符，描述最多 30 字符。
- **自定义菜单**：仅 C2C 单聊窗口底部展示，通过 `PUT /v2/menu` 注册。菜单项类型有 `send_message`（填入预设消息）、`link`、`switch`（开关）、`menu`（二级菜单）。

电脑端配置、QQ 端展示：在统一设置页里配置指令列表（命令名、显示名、动作、参数），桥接层启动时批量注册到指令面板与自定义菜单。

指令动作按类型分流：

| 类型 | 示例 | 执行方式 |
|---|---|---|
| 控制类 | `/start`、`/stop` | 直接切换桥接层状态开关 |
| 查询类 | `/status` | 桥接层读本地状态直接回复 |
| 转发类 | `/ask 内容` | 包装成外部卡片投给网页 AI（走 7.1） |
| 工具类 | `/run 工具名 参数` | 经外部工具提供方通道下发 |

`send_message` 类型菜单项只填入文本不自动发送，可用来做二次确认，避免误触。

### 7.4 设置页

在现有 `renderSettings` 的区块序列里插一个「远程桥接」区块，位置在「通用配置」与「历史会话」之间。内容：

- QQ 机器人凭证（AppID / ClientSecret，存入后端配置）
- 连接状态指示灯
- 推送开关：三类消息分别控制是否推到 QQ
- 指令列表编辑器：增删改命令，设置显示名与动作
- 推送窗口状态：显示当前被动回复窗口剩余时间
- 提示语：远程功能需保持面板开启

前端改动只涉及 `08_settings.js` 新增一个渲染函数，以及 `00_data.js` 的 `data()` 加几个字段，符合工程「设置页分片渲染」的既有约定。

## 八、落地顺序

按依赖关系分四步，每步都可独立验证：

1. **桥接骨架**：`remote_bridge/` 包 + QQ 鉴权 + WebSocket 收消息 + `bridge_store` 配置持久化。先只做「收到 QQ 消息 → 回复确认」，验证长连接稳定性。
2. **打通 7.1**：QQ 消息 → `card_bus.create()` → 抽屉取走。跑通后，远程发消息能力成立。
3. **打通 7.2**：抽屉上报新增 → 桥接层分类 → 被动回复窗口推送。重点验证去重与窗口续期。
4. **做 7.3 + 7.4**：指令面板注册 + 设置页区块。风险最低，因前三条链路已验证。
