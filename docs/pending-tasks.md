## 一、待处理

### 消息格式标准：内容完整保留，只用代码块包裹（企微 / QQ 共有）

**位置**：`flask_server/remote_bridge/channel/text.py`、`message_parse.py`、`outbound.py`

**现象**（2026-11-05 实机截图）：工具调用在正文里显示成
`[工具调用] search_content 参数={"pattern":...}`，参数明文摊开、未包代码块；
语音文字也以 `[语音] ...` 平铺；工具回传另起一条气泡推送整段 JSON。
**企微与 QQ 两条通道都复现**——QQ 也不例外。

**根因分三层**：

1. **块分类漏认回传**：`_block_category` 只识别 `bridge-chat-call`，
   不识别 `bridge-chat-res`，回传被归为正文整段推出。
2. **抓取漂移**：载荷常以「🛠 工具 + 裸 JSON」的形态落在普通段落块里，
   `_load_json_block` 要求块整体以 `{` 开头，对此完全失效。
3. **原文快捷路径未设防**：`_md_shortcut` 与 `outbound.build_body`
   都优先采用 Markdown 原文，却没检查原文自身是否夹带痕迹。
   采集侧把已渲染的正文又抓了一遍时，原文里就带着参数与语音文字，
   照用即原样推出——这是截图里明文参数的直接来源。

**修复**：

- `message_parse._block_code`：抽出 `_payload_summary` 统一取摘要。
  工具调用只报工具名、工具结果只报成败，两者都用代码块包裹
  （平台无折叠语法，代码块在手机上默认收起，是等效的折叠）；
  语音文字保留但去掉前缀——语音合成可能失败，正文里的字是兜底。
- `message_parse._scrub_traces`：正文块里混入的痕迹就地清洗还原。
- `channel/text.py`：分类同时识别两类载荷并加扫描兜底；
  `_md_shortcut` 增两道检查（块里有痕迹、原文自身脏）。
- `outbound.py`：抽出 `_pick_body`，原文不干净时退回块拼。

**验证**：企微与 QQ 两条通道输出对齐（仅角色前缀差异），
截图形态、代码块形态、纯回传、正常正文、思考开关五种场景实测符合预期；
后端全量 625 项通过，质量闸门新增违规 0。

**仍未覆盖**：同一条回复被拆成多个气泡。
截图里三条气泡的成因已部分消解（回传不再单独推送），
但若仍拆分，需查 `merge_batch` 返回 None 后管线是按消息单元还是按块推送。

**影响面**：企微与 QQ 两条通道的出向推送。

**优先级**：P1（格式部分已完成，拆分部分待实机复验）。

### 网页 AI 触发风控出现「已停止」，需自动重试

**位置**：待定（很可能在 `extend/content/` 的内容脚本，需 DOM 特征探测）

**现象**：网页机器人偶发触发风控，页面出现「已停止」提示，生成链路中断，不再产出回复。

**现状处理**：只能人工在抽屉点 `/reai`（重新生成）恢复，每次都要手动点。

**期望行为**：检测到「已停止」特征后，延迟 5 秒自动触发重新生成，免去人工介入。

**关键难点（暂缓原因）**：一旦生成恢复正常、收到新回复，「已停止」特征就会从 DOM 刷新消失。
因此检测逻辑不能写成「轮询特征是否存在」，而要捕捉「由生成中变为已停止」这一次状态流转——
否则要么漏检（变化太快），要么误触发（在正常完成后也点火）。

**处理方向**：等用户提供「已停止」状态下的 HTML 源码后，据此确定选择器与状态判定方式，再实现。

**优先级**：P2（暂缓，待提供 DOM 源码）。

### 质检拦截与推送的关系：推送侧不介入（已结案）

**结论**：质检是网页工具的事，跟推送机器人没有关系。推送侧不做任何介入——
不扣消息、不加标注、不裁剪内容，收到什么就按标准格式推什么。

**边界**：质检判出问题后由网页工具回传告警、提醒 AI 重做，这是网页侧的业务流程。
推送机器人只负责把消息如实送达。两者职责不交叉。

**曾出现的越界**：一度在推送侧按质检结论给正文加「本条未通过质检」的标注，
并在文案里裁剪质检说明。这属于业务流程入侵，已全部撤销。

### 前端分片层缺行为测试，重构无安全网

**位置**：`extend/dialog/parts/`

**现状**：前端测试只对 4 个分片做专项验证（`05j_card_sig`、`05g_cards`、`05h_memory_bridge`、`05f_parse`）。
`test_dialog_boot` 会按 `dialog.html` 全量加载全部脚本，验证的是「能否跑完、方法是否挂上」；
`test_dialog_contracts` 验证的是脚本挂载契约。**没有测试验证业务行为**——

**影响**：`extend/dialog/parts/` 下业务逻辑改动的安全网只有「语法没错、方法还在」。

**处理方向**：优先补三类行为测试，各挑最有代表性的场景：
1. 卡片构造：给一张后端卡片，断言前端卡片的字段完整性与 key 生成规则；
2. 文件挂载：待处理图片与用户消息的匹配，覆盖命中、不命中、多图对多消息；
3. 孤儿消息兜底：`orphanSlice` 存在与为空两种情形的时间线组装结果。

补完后再评估分片层的重复清理。详见 `quality-debt-tracker.md` 第 4.3 节。

**优先级**：P1。
