### 原生结构工具调用不被识别（P0，已定位并修复，待实机验证）

**现象**（2026-11-08 ChatGLM 实机截图 + 复现）：`open` / `click` / `find` 等原生格式调用
（`{"open": [...]}`，工具名作顶层键、无信封字段）在镜像里被渲染成普通 json 代码块，
不建卡、不执行、不回传，链路静默中断；同一回复里手动补齐信封字段的 `run_command`
却正常，形成「部分工具时好时坏」的表象。修复过程中的 `open` 调用同样未被识别，
由用户人工转告，进一步坐实根因。

**根因**：`05f_parse.js` 的 `parseToolCall` 只认 `{ tool, type: 'bridge-chat-call', parameters }`
信封形态；原生形态（工具名作顶层键）整体落在判定之外，被当普通代码块跳过。
协议提示词（05c_prompt）也只描述了信封写法，未覆盖原生写法。

**修法**：`parseToolCall` 兼容双形态——信封形态优先、协议不变；新增原生单键识别：
唯一顶层键、不带 `tool`/`type` 字段、键名命中本机工具注册表才判为调用；
值为普通对象直接作参数包，数组/原始值包成 `{ 工具名: 值 }`。
注册表守卫防止把普通单键 JSON 示例误判为调用。测试见 `test_parse.test.js` 原生形态用例。

**优先级**：P0。

### 设置页系统级配置改完立即弹回旧值（P1，已定位并修复，2026-11-08，待实机验证）

**现象**：设置页修改「网页图片保留数」「语音临时文件保留数」等系统级配置，输入新值后界面被覆盖回旧值，无法修改。

**根因**（2026-11-08 代码走查）：renderSystemConfig 复用 renderField 时 tool 传 'system'，onChange 走 setToolConfig('system', key, value)；该函数只在 this.toolConfig（对象，键为工具名，system 分组被 all_specs 排除在外）里找声明，查不到 spec，本地乐观更新失效，spec.value 停留旧值。后端保存链其实是通的（CONFIG_SCHEMA 含 system 分组，POST 正常落盘、GET 能读回），但任何重渲染（5 秒状态轮询等触发）时，Vue 按 patch 语义以旧 spec.value 重设输入框 DOM 值，表现为「改完立即弹回」。

**修复**：01_backend.js 的 setToolConfig 兼容 system 分组——tool 为 'system' 时改查 this.systemConfig 数组按 key 匹配更新，乐观更新与失败回滚同口径。

**现象**（2026-11-07 09:39 实机截图）：页面顶部显示「未连接」，发送消息全部失败；
切回前台后不自动恢复，只能手动刷新。

**现状代码**（`flask_server/web_bridge/web_page.js`）：

- 任一次心跳或轮询失败 → 立即停表、中止在途、清 `pollBusy`、重建定时器并补拉；
- 移除 `MIN_RECONNECT_GAP` 与延迟重连这一层；
- 移除回前台的 `location.reload()` 分支，改为重建轮询；
- 看门狗保留为兜底，但正常恢复不再依赖它。

### 风控恢复改为周期检查（已修，待实机验证）

**现状触发条件**：

- 生成态轮询周期 `BUTTON_POLL_MS = 500` 毫秒（`00_state.js`）；
- 风控恢复 `recoverIfStopped` **只在**「生成中 → 空闲」翻转时触发，延迟 800 毫秒，一次性；
- 三种形态（已停止 / 服务器不可用 / 输出为空）在这一次调用里按短路求值依次判定。

**问题所在**：按钮轮询已是 500 毫秒，比「五秒一次」快 10 倍，频率不是缺口。
真正的缺口是：**翻转一旦被错过，就没有第二次检查**。会错过的情形包括——
页面在后台被节流、轮询周期与生成结束错位、生成态判定本身失效。

**定下的方向**：保留翻转触发（快），另加一条**低频兜底检查**（不漏），两者并存。

周期取低频而非高频，理由有二：

1. 风控恢复不紧急——它只是把被掐断的回复重跑一次，晚几秒无实际损失；
2. 查得越勤，扩展自身的 DOM 读取与解析开销越大，既拖慢页面，
   也让「页面持续被脚本扫描」这一特征更明显，反而不利于规避风控。

**执行条件**：仅在生成态为空闲、且自上次兜底以来未发生翻转时执行一次。
生成中完全不检查——那时页面正在输出，既没必要也最费资源。

**周期取值**：10 秒（低频）。翻转触发的快路径不受影响，
用户感知仍是「生成一结束就检查」。

**2026-11-07 二次排查（三项新发现）**：

1. **「服务器暂时不可用」未触发，根因是单次 800ms 检查太早**。
   现场快照 `docs/archive/服务不可用.html` 证实该提示确实存在于 `.ds-message` 内的
   `span._1ce76f5`（不在 `.ds-markdown` 里），按 `isServerUnavailable`
   的判定逻辑本应命中；但它渲染晚于按钮翻转，800ms 的单次检查必然落空，
   之后不再复查，于是整次机会丢失。
   修法：翻转后改为递增间隔多次复查（约 0.8s 起、累计约 10s），命中即止；
   最后一次仍未命中才记「未识别到停止形态」。

2. **跳过策略时序错误**：`isAtBottom` 在检测时判定，动作却在 20 秒后执行。
   这 20 秒内用户可能翻看历史、页面也可能变化，早判无效——
   既会拦住「检测时不在底部、20 秒后已回到底部」的正该恢复场景，
   也放过了「检测时在底部、20 秒后已翻走」的误点场景。
   修法：检测阶段不判底部；动作前一刻（倒计时结束、点击前）再判，
   不在底部则放弃本次并记日志。

**优先级**：P1。

### 手机端漏消息：后台重载后中间段被跳过（已修，待实机验证）

**结论**：不是推送丢失，是回前台整页重载后游标归零，只取最新 10 条而跳过中间段。
已改为游标持久化 + 重载后逐批补齐，详见下文「根因」与「选定修法」两节。

**现象**（2026-11-07 08:39 实机截图）：抽屉「网页对话镜像」显示当前会话已有多轮 AI 回复，
手机端网页版机器人只收到其中两条（时间均为 08:39），更早的若干轮没有出现。

**对比材料**：抽屉镜像区与手机端消息列表的截图，两者同属同一会话。

**初步判断**：抽屉本地有内容、手机端缺内容，说明缺失发生在推送链路上，
不在抓取阶段。需区分两种可能：

1. 推送未发出——`_reportFreshReply` 的判据未命中（例如 `isFreshReply` 判定偏严、
   或消息被判为历史消息而跳过上报）；
2. 推送已发出但投递失败——后端接收后未能送达手机端（通道或去重环节丢弃）。

**推送的唯一开关**（`05_messages.js` 第 280 行）：

```
isFreshReply = !isInitialLoad && !scrollOnly && addedNodes && lastIsAssistant && !tailInTree
```

其中 `scrollOnly = (reason === 'scroll')`。五个条件必须同时成立才会上报，
任一不成立则本轮不推送——包括消息已经入树、界面上看得见的情况。

**日志取证结论**（2026-11-07，扩展日志 + 桥接日志 + 应用日志三方比对）：

推送侧**全部成功**，不是丢推。08:38:19 至 08:39:27 之间共 6 次
`isFreshReply=true`，均以 `reason=generate` 上报：

| 时间 | 末条消息 | 上报 |
|---|---|---|
| 08:38:19 | `m1t5p3e5` | 是 |
| 08:38:38 | `mqs79j2` | 是 |
| 08:38:49 | `m1v5domw` | 是 |
| 08:39:02 | `mbbaqum` | 是 |
| 08:39:18 | `myqd8x1` | 是 |
| 08:39:27 | `m1qay7c3` | 是 |

后端同样收到并处理：桥接日志在上述每次上报后 1 秒内都有一次
`语音合成成功：引擎=sapi`，说明消息确实进了后端并走完了处理链路。

**真正的断点在手机端轮询**：

- 08:38:39 取走 2 条（游标 6719 → 6721）后，`[web][poll]` **彻底消失**；
- 下一条轮询出现在 **08:49:40**，中间断开 **11 分 1 秒**；
- 断档期间的 `client_log` 心跳仍在发（46 次），但密度从每几秒一次
  衰减为 08:42:49、08:47:49 两条，间隔恰为 5 分钟；
- 这是浏览器把后台页面的定时器节流到「一分钟甚至五分钟一次」的典型形态，
  即**页面被切到后台或锁屏**。

**恢复时的行为**：08:49:40 出现 `cursor=0 返回=10 条 新游标=6728`，
属页面回前台后重建游标、补拉一批。

**残留疑点（下一步）**：截图时间为 08:56，晚于 08:49:40 的补拉，
但手机端仍只显示最后两轮（`myqd8x1` / `m1qay7c3`，正是 08:39:18 与 08:39:27 两次）。
说明补拉拿到的 10 条没有全部渲染出来，缺口发生在**补拉之后的渲染/去重环节**，
而非推送环节。

**代码走查补充**：

- 消费端 `web_page.js` 的 `onPollOk` 逐条 `renderMessage`，**没有任何按角色或内容的过滤**，
  拿到多少条就渲染多少条。故「只显示两条」不可能来自渲染环节的主动丢弃。
- 收件箱 `web_inbox.list_since(cursor, limit)`：取 `seq > cursor` 的全部消息，
  超出上限时取**最旧**一批（`fresh[:limit]`），游标推进到本批末条，
  逐批追平，不会跳过中间消息。
- 收件箱另有内容级判重：`ai` / `tool` 角色下 `(role, text)` 完全相同会被跳过。
  若某轮 AI 回复正文与此前某条完全相同，该条不会入库——这是一条潜在的吞消息路径，
  但要求正文逐字相同，与本例（各轮内容不同）不符。

**矛盾已解开**（`routes/web.py` 第 292-301 行）：`/api/web/messages` 有两个分支，
由 `history` 参数决定，与 `cursor` 无关：

- `history=1` → `web_inbox.recent(hlimit)`，取**最新** N 条（默认 10），
  返回的 `seq` 是全局最新值。首屏铺屏走这条。
- 否则 → `web_inbox.list_since(cursor, limit)`，按游标取增量。

日志里 `cursor=0 返回=10 条 新游标=6728` 正是 `history=1` 分支：
游标 0 是客户端带上的默认值，实际返回的是最新 10 条，故新游标直接是 6728。
两条路径语义清楚，无矛盾。

**根因（已确认）**：`web_page.js` 的 `visibilitychange` 处理里有一条策略——
页面在后台停留超过 `RELOAD_AFTER_HIDDEN_MS`（30 秒）时，回前台直接 `location.reload()`，
理由是「长期后台后 DOM 陈旧、继续复用容易长时间无响应」。

`cursor` 只是内存变量，整页重载后必然归零，于是首次加载走 `history=1` 分支，
**只取最新 10 条，并把游标一步设为全局最新**。

完整时序：

1. 08:38:39 最后一次增量轮询，游标 6721；
2. 页面进入后台；
3. 08:49:40 回前台，距切后台约 11 分钟 > 30 秒 → 整页重载；
4. 重载后游标归零 → `history=1` 取最新 10 条（seq 6719-6728）→ 游标跳到 6728；
5. 后台期间积压的消息（seq 6729 起）既不在最近 10 条内，也不会被增量取到。

**为什么不是「推送丢了」**：收件箱 `data/web/inbox.json` 中 seq 6729 至 6806 全部在库，
当前 seq 已到 6806、共 500 条。数据一条不少，缺的是客户端没取。

**选定修法**：游标持久化。把 `cursor` 同步写入 `localStorage`，
页面加载时先读回，非零则走增量追赶而非 `history=1`。
整页重载是既定的健壮性策略，不改；改的是重载后不再丢弃已知进度。

**取证方向**：

- 核对 `/api/web/messages` 路由：`cursor=0` 与 `cursor>0` 分别走哪个函数；
- 取 08:49:40 那批 10 条的具体 seq 与 text，确认是否包含 08:39:27 之后的内容；
- 确认截图那台设备与 08:49:40 发起请求的是否为同一客户端
  （另有一台设备或另开一个标签页也会产生同形的 `cursor=0` 请求）。

**优先级**：P1。


### 页面断连后无法自愈，只能刷新（根因已修，待实机验证）

**现象**（用户实机反馈）：发送失败弹出提示后，即使立刻点掉，
页面状态仍一直停在「未连接」，必须刷新页面才能恢复。

**根因**：轮询停掉之后，能把它重新拉起的只有两条路径——
`onPollFail` 里的 `reconnectNow()`、以及页面切回前台的 `visibilitychange` 回调。
**没有任何兜底**：若这两条路径都没走到（例如失败时 `pollBusy` 仍为真导致
`fetchMessages` 在入口被跳过、或请求收尾没执行到使 `pollBusy` 永久为真），
轮询就永久死亡。而「未连接」状态的恢复唯一途径是轮询成功，
于是界面永久卡在未连接，只能刷新。

**修复**：新增 `web_watchdog.js`，**每 1 秒**自检三种卡死形态，命中即强制复活：

1. 定时器丢失（`pollOn` 为假）——浏览器可能在后台丢弃定时器；
2. 久未成功轮询（超过 **8 秒**，约连丢三轮）——网络恢复后本该自动重连；
3. 在途标记泄漏（`busy` 持续超过 **10 秒**）——单次请求 6 秒必超时，
   超过 10 秒仍为忙即说明收尾没执行到，后续所有轮询都在入口被跳过。

自检间隔取 1 秒而非 5 秒：轮询本身 2.5 秒一轮，自检必须比它密，
才能在断连后一轮之内发现，而不是等用户察觉「一直转圈」再修。
另监听 `online` 事件，网络恢复瞬间立即自检一次，不等下一个周期。

**自愈时效**：断连后最迟约 8 秒内自动恢复，网络恢复时可近乎立即恢复。

复活动作 = 重建定时器 + 强制复位在途标记 + 立即补拉一次。
页面在后台时跳过自检，避免把浏览器节流误判为卡死。

**配套改动**：两处 `alert()` 改为 `WebToast.show()`（非阻塞），
原因是 alert 虽被用户立刻点掉，但它在此期间冻结主线程，
放大了失败后的无响应感受；`web_perf.js` 的 `tickgap` 增加
`document.hidden` 判断，不再把后台节流误记为卡顿。

**测试**：`tests/js/test_web_watchdog.test.js` 10 项，覆盖三种卡死形态的识别、
正常状态不误伤、防抖、首次加载不误判、复活异常不穿透。

**待验证**：实机上再遇断连，页面应在 5~30 秒内自行恢复「已连接」，无需刷新。

**优先级**：P0（已修，待验证）。



### 前端卡顿：alert 同步阻塞（已改，待实机验证）

**根因**：`web_page.js` 的发送失败处理里调用了 `alert()`。
`alert()` 是**同步阻塞 API**：弹出期间主线程完全冻结，定时器不走、渲染停摆，
直到用户点「确定」。手机上该框常被忽略或挂在后台，一挂数分钟，
用户感知即「页面卡死」。`web_upload.js` 的文件发送失败处有同样问题。

**证据链**（按内层时间戳排序后统计，2026-11-04 ~ 11-07 共 13 条 800ms 以上长任务）：

- **每一条**大卡顿前 1~3 秒内都有一次 `[send] fail kind=neterr`——
  正是 fetch 失败进入 `finish()`、弹出 alert 的时刻；
- 长任务时长（899 / 1110 / 1593 / 1620 ms）与 alert 弹出瞬间的同步阻塞吻合；
- 更早统计「断网失败与大卡顿无关联」是错的：日志为断网后批量补发，
  文件中的行序不等于事件发生的时间序（补发时延最大 1264 秒），
  按物理行相邻判断会得出相反结论。按内层时间戳重排后规律完全一致。

**同时修正的误报**：`web_perf.js` 的 `tickgap` 用 `Date.now()` 算间隔，
页面切后台时浏览器节流定时器、时间照常走，回前台补触发的间隔等于后台停留时长，
被误记为「事件循环被卡」（388 / 210 / 177 秒那些）。已加 `document.hidden` 判断，
后台期间不再记录。真实卡顿由 `longtask` 反映，量级为秒。

**已改**：新增 `web_toast.js`（页面内非阻塞提示条，4 秒自动消失、可点掉），
两处 `alert()` 改为 `WebToast.show()`；`web_perf.js` 增加后台判断。

**待验证**：实机上再遇发送失败，应弹出底部提示条、页面不再冻结；
`tickgap` 不再出现数百秒的假记录。

**优先级**：P0（已修，待验证）。



### 卡片偶发双执行（已实现，待实机验证）

**状态**：代码已提交（`aa28285`），**尚未在真实复现场景下验证**。

**根因**（2026-11-06 实机截图确认）：网页端把同一次工具调用在**相邻两条消息**里各输出一遍，
两条 `msgId` 不同、工具名与参数完全相同。执行签名由「会话 + 消息指纹 + 工具 + 参数」组成，
含消息指纹，故两次都判为「未执行过」，各自排一次倒计时——
表现为相差几秒执行两次、AI 收到上一张卡片的结果。

**修复**：建卡时只与紧邻的上一条消息比对「工具名 + 参数」，相同则标记 `duplicate`。
标记的卡片保留在界面上供手动查看，但不进入自动执行候选；
滚动复检（`_maybeAutoExecOnScroll`）与开自动开关（`setAutoSendEnabled`）两处路径同步排除。

**为什么只比相邻**：长会话里同参数调用反复出现属正常业务（实测单会话七八百轮，重复率极高），
跨消息全局查重会误杀真实调用。

**待验证**：

1. 网页端再次出现相邻重复输出时，第二张卡片是否被标记为重复、只有第一张执行。
2. 正常场景（相邻两条调用参数不同）不受影响，两张都照常执行。
3. 长会话中相隔多轮的同参数调用不被误判为重复。

**已知边界**：只覆盖相邻一条。若网页端把同一调用输出在隔一条消息的位置
（如中间插入系统提示），仍会执行两次。暂按观察处理，复发再议是否扩到相邻三条。

**生效前提**：内容脚本与抽屉脚本均须「扩展重载 + 页面刷新」才更新。

**优先级**：P1。


### 风控自动恢复（已实现，v11 起真正生效，待实机验证）

**状态**：代码已实现并提交（`f1e15d8`），**尚未在真实风控场景下验证**。
实现要点：挂在「生成中 → 空闲」翻转点上判定，不轮询特征存在性；
只读思考区标题栏、排除思考内容内部，避免 AI 自己讲到该词时误判；
检测到后延迟 20 秒点一次「重新生成」，点击交主世界执行。

**待验证**：真触发风控时能否正确识别并自动恢复；正常生成结束时不得误触发。

**覆盖三种风控形态**，共用同一套恢复动作，只是判定条件不同：

1. **页面显示「已停止」** —— 读思考区标题栏文字，排除思考内容内部。
2. **页面显示「服务器暂时不可用」** —— 该提示在消息下方状态区，不在正文里；
   判定时须排除 `.ds-markdown` 正文区，否则 AI 自己讲到这个词会误判。
3. **AI 输出为空** —— 生成中断但不显示任何提示，末条 AI 消息只有思考内容。
   判定复用现有解析：除思考块外没有任何内容块即为空。

**生效前提**：内容脚本必须「扩展重载 + 页面刷新」才更新，`/rf` 只刷页面不够。
此前十几轮改动均因扩展未重载而未生效，2026-11-06 19:25 日志首次出现
`build=2026-11-06-risk-recover-v11`，确认链路打通。
已加 `ping_content`/`pong_content` 探测，抽屉启动时核对内容脚本版本并上报后端。

**生效条件**：须在设置页打开「风控自动恢复」开关（默认关闭）；
且视口停在对话底部（往上翻看历史时不打扰，避免替用户重跑主动停止的回复）；
检测到后等待 20 秒再点重新生成，留出人工介入时间。

**形态可重叠**：三种形态可能同时出现（实测「服务器暂时不可用」与「已停止」并存）。
判定按短路求值，任一成立即止，末尾统一走一次恢复——保证同一次停止只点一次，
不会因多个形态同时命中而重复触发。

**已修的两个缺陷**（2026-11-06 实机发现）：

1. **滚动守卫误伤**：`isAtBottom` 原先「选择器命中即视为不在底部」，
   但其中一条选择器偏宽（`div[role=button].ds-button--floating`），
   会把「继续生成」这类浮动按钮一并命中，于是风控停止时反而被判成「用户不在底部」，
   恢复永不触发。

   **修正过程**：最初在调用处加了「只认无文字命中项」的过滤，这是绕过问题而非解决问题。
   核查确认全工程 `isAtBottom` 仅此一处实现、无其它成熟判定可复用后，
   改为**收紧选择器**——删掉宽泛的那条，只留三条类名同时命中的精确选择器。

   **取舍**：精确选择器若因页面改版失效，`isAtBottom` 会恒返回 true（查不到按钮即认为在底部），
   导致滚动轮次可能误执行历史卡片。相比原先的误判（风控恢复永不触发），
   这个方向的失效更容易被察觉，且影响面更小。
2. **全链路无日志**：各判断分支原先都是静默 return，出问题时无从排查。
   现「不在底部」「未识别到形态」两条路径均记日志。
