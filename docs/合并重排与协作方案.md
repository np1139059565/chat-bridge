## 二、合并方向（用户指定，单向）

master → old → main，每一步都必须逐文件阅读代码，不能简单拷贝。

- master → old：两边都没有大改，重复的 bug 修复按代码优劣自由取舍，逐文件裁定，不整分支搬。
- old → main：main 是破坏性大改，必须服从新结构，先做接口与目录适配再同步修复。
- 两笔都禁止整分支照搬；哪边实现更优、哪边已失效，由执行方给出逐文件理由，分发方复核。

- **git log 才是历史**：提交历史已完整留痕，文档里再抄一遍时间线属重复存储。
  历史内容在文档里最多留「一行结论 + commit 短号」，不存过程全文。
- **唯一入口瘦身为速读版**：START_HERE.md 压到 ≤150 行，只留身份判定、当前队列、

## 五、并发调度方案

复用 2026-11-14 已验证的教训：a/c 曾空闲数小时、B-7 单笔过大，责任在分发侧漏派与单笔过大，
不是执行方问题；小片化后收到活即半天内甚至 40 分钟交付。

规则：

- 单笔 ≤1 个可验收面、自带实测口径、半天内可交付。
- 分发方维持各方在途队列；任一方完成回监听，下一轮立即续派下一片，不等、不堆单。
- 不自找活仍有效（避免乱改），但等不到活算分发侧责任。
- 任务按层 / 按仓切，不按文件切，互不撞车；依赖面串行，无依赖面并行。
- 验收期间预下发下一片进排队槽，当前任务收尾即开工，不再等指令。

分片预览（**仅预览，审批前不下发**）：

| 片 | 执行方 | 面 | 依赖 | 形态 |
|---|---|---|---|---|
| R0 | a | 配置八跳有效性核查 | 无 | 只读取证 + 矩阵 + 夹具 |
| R1 | b | master → old 逐文件移植 | 无 | 改 old 实现，一次提交 |
| R2 | c | 三仓差异矩阵 + 协作长文精简落地 | 无 | 文档改写与删除 + 行数对比清单 |
| R3 | R1 收口后最先空闲方 | old → main 服从新结构适配 | R1 合入 | 改 main 实现，一次提交 |
| R4 | 分发方 | 逐笔独立 worktree 走查、串行合入、回归、解冻真机 | 各片交付 | 不写实现 |

R0 / R1 / R2 起始三方同时有活，互不撞车（a 只读配置链、b 改 old、c 只改 docs/ 下文档，不碰实现）；
R3 与 R1 是依赖串行，不会让 a/c 干等，因为 R0 / R2 收口即续派。
G-A / G-B / G-C 三笔大改验收任务不作废，整体顺延到本轮合并走查之后。
