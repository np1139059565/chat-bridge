# 拆分方案：镜像插件 与 本地工具服务

> 状态：**待审批**。本文件只记录需求、耦合现状与拆分候选条目，未做任何代码改动。
> 需求提出：2026-11-05。

## 一、需求原文

> 理论上网页 AI 插件（会话记录 / 指令等，可能要给网页 AI 保留一个轻量级的服务端，
> 可以存储一些界面的会话数据即可）和本地工具服务（企微 / QQ / 微信 / 网页版等机器人通道，
> 工具 / skill 列表 / 规则 / 语音等，可能要给工具服务保留一个轻量级的配置页面，
> 可以对一些配置进行管理）应该可以拆开。
>
> 因为网页 AI 实际上也只是通过抽屉将对话转成标准 API 回复，
> 所以本地工具服务应该做得更通用一点：可以配置其他通用 API 地址，
> 也可以配置网页 AI 的服务地址，提供公共工具的调用。
>
> 不过两者深深耦合，具体拆分细节需要阅读相关文档和代码后，列出详细拆分条目，
> 并且经过用户详细审批才能真正分开。

## 二、规模现状（实测）

| 目录 | 文件数 | 行数 | 定位 |
|---|---|---|---|
| `extend/` | 70 | 14078 | 镜像插件（MV3 扩展 + 抽屉界面） |
| `flask_server/remote_bridge/` | 54 | 11824 | 远程桥接：三通道机器人 |
| `flask_server/core/` | 44 | 7206 | 核心支撑（含记忆系统） |
| `flask_server/web_bridge/` | 18 | 3650 | 网页版机器人 |
| `flask_server/routes/` | 20 | 3177 | HTTP 接口层 |
| `flask_server/tools/` | 15 | 2920 | 内置工具 |
| `flask_server/custom_tools/` | 9 | 1346 | skill 解析与执行 |

两侧体量相当（14k : 30k），不存在「一边薄一边厚」的天然切点。

## 三、耦合现状盘点

### 3.1 依赖方向

```
抽屉（浏览器）  ──50 个 HTTP 接口──▶  本地工具服务
                                        │
外部提供方      ──POST /api/cards──▶  card_bus ──轮询──▶ 抽屉
```

抽屉调用 50 个接口，跨 8 个领域：工具、规则、技能、配置、桥接、通道、记忆、卡片。
**依赖是单向的**：抽屉依赖后端，后端不主动调抽屉（外部卡片靠抽屉轮询取走）。

### 3.2 六处实质耦合

| # | 耦合点 | 现状 | 拆分难点 |
|---|---|---|---|
| C1 | `/api/bridge/report` | 抽屉把消息切片 POST 给后端，后端分发到三通道机器人 | 这是「网页侧数据 → 工具侧」的唯一主通道，格式必须稳定 |
| C2 | 记忆系统 | 抽屉存会话，后端存蒸馏/事件/检索；两边各有一份会话数据 | 会话数据归属未定：存网页侧则后端检索不到，存工具侧则网页侧依赖变重 |
| C3 | 外部卡片 | 后端登记 → 抽屉轮询取走 → 渲染成消息发给网页 AI | 工具侧产出、网页侧消费，跨服务需保留「发送即结束」语义 |
| C4 | 配置界面 | 抽屉是唯一配置入口，同时管工具配置与网页侧配置 | 拆开后配置页要一分为二，或保留一个跨服务聚合页 |
| C5 | 消息树 / 卡片状态 | 抽屉持有完整消息树与卡片状态，后端只做去重记账 | 状态权威方在抽屉，后端记忆库是副本，两者需对账 |
| C6 | 语音链路 | 抽屉上报消息 → 后端合成 → 推回通道 | 合成属工具侧能力，但触发源是网页侧消息 |

### 3.3 边界比预想的清楚

一个关键发现：**抽屉与后端之间的 50 个接口，本身就已经是一条边界**。
后端不清楚抽屉内部怎么渲染，抽屉也不需要知道后端怎么推送。
真正纠缠的不是「代码互相引用」，而是三件事：

1. **会话数据存哪边**（C2/C5）
2. **配置界面归谁**（C4）
3. **外部卡片的方向语义**（C3）

## 四、拆分候选条目

以下条目独立可评估，可只做其中几条。每条标注代价与风险。

### 条目 A：抽出「对话后端」抽象层

**做什么**：把「AI 从哪来」抽象成一个可配置的端点。现在抽屉固定对接当前网页 AI（靠内容脚本抓 DOM），
改为支持两种模式：
- 模式一：本地镜像插件（现状，抓网页 DOM）
- 模式二：HTTP 端点（配置一个通用 API 地址，按约定格式收发）

**价值**：这是「工具服务通用化」的前提。没有它，工具服务只能配当前这套网页 AI。

**代价**：需定义一套对话消息的交换格式（消息块、卡片、语音标记），
并在抽屉里实现「DOM 模式」与「HTTP 模式」两条适配路径。预计 800~1200 行新增。

**风险**：格式一旦定型就难改，后续接其他模型可能要打补丁。

### 条目 B：会话数据归属明确定义

**做什么**：明确会话数据的**唯一权威**在哪边，另一边只存缓存。

两个选项：
- B1：权威在网页侧（抽屉本地存储 / 轻量服务端），工具侧只在推送时读取快照
- B2：权威在工具侧（现有记忆库），网页侧启动时拉取

**代价**：B1 需要网页侧有持久化能力（现在靠浏览器 localStorage + 可选后端）；
B2 会让网页侧的「离线可用」能力退化。

**风险**：选错方向后迁移成本高——历史会话可能要搬家。

### 条目 C：配置界面拆分

**做什么**：现在抽屉是唯一配置入口。拆成：
- 网页侧配置（网页 AI 地址、抓取规则、站点适配）留在抽屉
- 工具侧配置（通道凭证、工具上下线、语音引擎）移到工具服务自带的配置页

**代价**：需为工具服务做一个配置页面（预计 1500~2000 行）。
当前抽屉的 `08*` 系列分片（约 1200 行）中，大部分是工具侧配置。

**风险**：用户要开两个页面配置，日常操作变繁琐。需要聚合入口缓解。

### 条目 D：外部卡片通道独立

**做什么**：把 `/api/cards` 系列从「抽屉轮询」改为可配置的投递目标，
支持投递到任意注册的客户端（抽屉、HTTP 端点、其他）。

**代价**：中等，主要是把「全局 claim」改成「按客户端注册」（顺带解决已搁置的 M3）。

**风险**：低。这条相对独立，可先做。

### 条目 E：语音链路解耦

**做什么**：把语音合成从「被上报触发」改为「独立服务」。
网页侧通过 API 请求合成，工具侧返回音频。

**代价**：中等。现有 `voice_tts` 已是独立模块，主要是加一层 HTTP 封装。

**风险**：低-中。合成有并发闸门与超时，改成 HTTP 后需重新评估。

### 条目 F：真正拆成两个服务进程

**做什么**：`extend/` 配一个轻量服务端（只存会话），`flask_server/` 保留工具能力。

**前提**：A~E 全部完成，且 C2/C4 的归属已定。

**代价**：高。需要拆分 `core/` 与 `routes/`，明确每个接口归属，
并处理跨服务调用（会话同步、卡片投递、配置读取）。

**风险**：高。这是终点，不是起点。**强烈建议放在最后。**

## 五、建议的推进顺序

推荐先做 D（低风险、独立、顺带解决 M3），再做 A（通用化前提），
然后 B（定数据归属），C 与 E 视情况，F 最后。

**不推荐**跳过 A 直接做 F：没有抽象层就拆服务，等于把耦合从进程内搬到网络调用，更难维护。
