# 拆分方案：镜像插件 与 工具工程

> 状态：**待审批**。本文件只记录需求、数据归属、耦合现状与拆分条目，未做任何代码改动。
> 需求提出：2026-11-05；方向调整：同日，插件要抽得更彻底，工具工程要有自己的聊天界面。

## 一、需求（调整后）

### 1.1 插件侧

- **不再依赖后端存数据**。卡片状态、会话记录存浏览器本地。
- **抽得像 debug_chrome**：只做「抓网页 AI 对话 → 转成标准格式 → 交给别人干活」，
  自身不承担业务能力，依赖另一个服务完成实际工作。
- 指令列表中依赖后端的操作，逐条评估能否转成操作浏览器内存；
  没有价值的直接删除。

### 1.2 工具工程侧

- **要有自己的聊天界面**。拆分的目的是让工具工程脱离网页 AI 独立运转，
  其它功能（工具、技能、规则、语音、推送通道、记忆）本就在这边。
- **要有自己的配置页面**。推送通道、工具上下线、语音引擎等配置从抽屉搬过来。
- 推送通道 / 工具 / 技能 / 规则 / 语音，数据与能力全部属于工具工程。

### 1.3 一句话概括

> 工具工程从「给插件打辅助的后端」变成「主产品」；
> 插件从「带完整业务的前端」变成「网页 AI 的适配器」。

## 二、目标形态

```
┌─────────────────────────────┐
│  工具工程（主产品）           │
│  · 自己的聊天界面             │
│  · 配置页面                   │
│  · 工具 / 技能 / 规则         │
│  · 推送通道（QQ/微信/企微）    │
│  · 语音合成与识别             │
│  · 记忆系统                   │
│  · 对话后端可配置（见 2.1）    │
└──────────┬──────────────────┘
           │ 标准消息格式
┌──────────┴──────────────────┐
│  浏览器插件（适配器）         │
│  · 抓网页 AI 对话 → 交给工具工程 │
│  · 接收回复 → 粘贴回网页 AI    │
│  · 会话与卡片状态存本地        │
└─────────────────────────────┘
```

### 2.1 工具工程的对话后端（三种来源）

| 来源 | 说明 | 现状 |
|---|---|---|
| 本地聊天界面 | 工具工程自己的聊天页，直接对话 | 待建 |
| 网页 AI（经插件） | 插件抓网页对话送过来，工具工程回话由插件粘贴回去 | 现状主路径 |
| 任意 HTTP 端点 | 配置一个通用 API 地址，按约定格式收发 | 待建 |

三者对工具工程而言是同一件事：**一个能收消息、能出消息的对话来源**。

## 三、数据归属（核心表）

这张表是本次拆分的核心。每一行都要你确认。

| 数据 | 归属 | 理由 | 现状 |
|---|---|---|---|
| 网页 AI 会话镜像 | **浏览器** | 插件的私有数据，工具工程不需要知道网页上聊了什么 | 现在抽屉本地 + 后端记忆库各一份 |
| 卡片状态（网页侧） | **浏览器** | 卡片挂在消息树上，消息树在浏览器 | 现状已在本地，但卡片回传要经后端 |
| 工具工程会话 | **工具工程** | 自己的聊天记录 | 现有记忆库 |
| 工具 / 技能 / 规则 | **工具工程** | 能力归属工具侧 | 现状如此 |
| 推送通道配置与凭证 | **工具工程** | 通道是工具侧能力 | 现状如此，但界面在抽屉 |
| 语音成品与缓存 | **工具工程** | 合成在工具侧 | 现状如此 |
| 记忆（蒸馏/事件/检索） | **工具工程** | 服务于工具侧的对话 | 现状如此 |
| 外部卡片 | 工具工程产出 → 插件消费 | 产出方在工具侧，消费方在浏览器 | 现状如此 |
| 配置（全局） | **工具工程** | 单一真源 | 现状如此，但界面在抽屉 |

**关键变化**：网页 AI 会话镜像不再进后端记忆库。这需要确认——现有记忆系统里存的是什么？
若存的是网页 AI 的对话，拆分后它该只服务工具工程自己的聊天。

## 五、耦合点重新盘点

按新方向，耦合点变少了，但有几处变重了。

| # | 耦合点 | 新方向下的处理 |
|---|---|---|
| C1 | `/api/bridge/report` 上报切片 | **保留**。这是插件向工具工程送对话的唯一通道 |
| C2 | 记忆系统两份会话 | **拆开**。网页镜像只存浏览器；记忆库只服务工具工程自己的聊天 |
| C3 | 外部卡片投递 | **保留但简化**。工具工程登记，插件轮询取走 |
| C4 | 配置界面 | **拆开**。工具工程自建配置页，插件只留「连哪个工具工程」这类连接配置 |
| C5 | 消息树与卡片状态 | **归浏览器**。工具工程只读快照用于推送，不写回 |
| C6 | 语音链路 | **归工具工程**。插件不再触发合成，由工具工程自己决定 |

### 5.1 新出现的问题

**问题一：网页 AI 的回话怎么粘贴回去？**
现在抽屉是「抓对话 → 上报 → 后端回话 → 抽屉自动粘贴」。拆开后抽屉仍是这个角色，
但它不再需要理解工具、卡片、技能，只需知道「有回复就粘」。

**问题二：卡片谁来执行？**
网页 AI 输出的 `bridge-chat-call` 代码块，现在由抽屉建卡并调 `/tool` 执行。
拆开后有两个选项：
- 选项一：抽屉仍在本地建卡、仍调工具工程 `/tool` 执行（改动小）
- 选项二：抽屉只把代码块原样转给工具工程，由工具工程解析并执行（插件更薄）

**选项二更彻底，但要重新设计「执行结果怎么回到网页 AI」这条回路。**

## 六、拆分候选条目（重做）

### 条目 1：工具工程自建聊天界面

**做什么**：工具工程里加一个聊天页面，能直接对话、渲染卡片、执行工具、显示记忆。

**价值**：这是「主产品」的标志。没有它，工具工程永远是插件的外挂。

**代价**：高。相当于把抽屉的核心界面在工具工程里重做一遍。
现有抽屉 70 个文件、14078 行，其中界面与渲染部分（`07*`、`08*` 系列）约 5000 行需要重做。

**风险**：中。技术栈可沿用（Vue），但需要重新处理与后端的交互方式（同源，不再跨域）。

### 条目 2：对话后端抽象层

**做什么**：定义「对话来源」的统一接口，支持本地界面、网页 AI（经插件）、任意 HTTP 端点三种。

**价值**：条目 1 的前置。没有它，聊天界面只能接一种来源。

**代价**：中。约 800~1200 行，主要是一套消息格式与三个适配器。

**风险**：中。格式定型后难改。

### 条目 3：插件剥离后端数据依赖

**做什么**：
- 会话与卡片状态只存本地（现在已经在存，但要确认没有后端写入路径）
- 删除或改造 50 个接口调用中不必要的那部分
- 插件设置页只留「连接哪个工具工程」

**价值**：插件变薄的关键。

**代价**：中。主要是梳理 50 个调用点，逐个判断去留。

**风险**：低-中。需要确认哪些功能移除后不影响现有使用。

### 条目 4：指令体系整改

**做什么**：按第四节分类执行——13 条搬本地、5 条转发、5 条删除。

**价值**：直接呼应你的要求「评估能否转成浏览器内存，没价值的删除」。

**代价**：低。指令表本身就是配置数据，改动集中。

**风险**：低。

### 条目 5：工具工程自建配置页面

**做什么**：把抽屉里 `08*` 系列的配置区块搬到工具工程。

**代价**：中-高。约 1500~2000 行。

**风险**：低。

### 条目 6：卡片执行归属重新设计

**做什么**：按 5.1 的问题二，决定卡片由谁执行。

**这是需要你拍板的方向性选择**，详见第八节。

## 七、分阶段计划

### 阶段一：独立数据（不动界面）

- 条目 3（插件剥离后端数据依赖）
- 条目 4（指令体系整改）

**产出**：插件不再需要后端存数据。此阶段完成后，即使工具工程关掉，插件仍能抓对话、存会话、显示历史。

### 阶段二：工具工程长出界面

- 条目 2（对话后端抽象层）
- 条目 1（聊天界面）
- 条目 5（配置页面）

**产出**：工具工程能独立对话。插件变成可选的适配器。

### 阶段三：收缩插件

- 条目 6（卡片执行归属）
- 把插件里已经不需要的代码删掉

**产出**：插件只剩「抓对话、贴回复」两件事，如 debug_chrome 一般。

**为什么这个顺序**：先让插件独立，再让工具工程独立，最后收缩插件。
任何一步做完都可以停下来，不会出现「两边都不完整」的中间态。
