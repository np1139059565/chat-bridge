# 拆分方案：镜像插件 与 工具工程

> 状态：**已审批，待实施**。四条决策均已确认，可进入实施阶段。
> 需求提出：2026-11-05。同日经四轮澄清定稿方向与决策。

## 一、核心定位

> 工具工程对外提供**标准 AI 接口**（chat completions + tool calling）。
> 插件是安装在工具工程里的**一个轻量 skill**，负责把网页版的流量翻译成标准 API 调用。
> 不装这个 skill，配任何一个标准 AI 端点也能正常用。

```
工具工程 = AI 网关 + 工具执行器 + 推送通道 + 记忆 + 网页聊天界面
插件     = 一个可选的对话来源适配器（skill）
```

**插件不是必需品**。它与「工具工程自带的网页聊天页」「任意标准 HTTP 端点」并列，
三者对工具工程而言是同一件事：一个能收消息、能出消息的对话来源。

### 1.1 根本原则：工具服务回归标准，插件承担适配（第六轮确立）

**这是本次拆分最核心的一条，其余决策都由它推出。**

现有版本之所以处处别扭，根因是**把网页 AI 的特殊性写进了工具服务**：
System Prompt 由插件拼、工具结果带一堆网页专用的字段、语音约定塞在提示词里……
这些在标准 API 场景下全是畸形的适配。

正确划分：

```
工具服务  —— 只提供标准形态：标准 system prompt、标准工具列表、标准工具结果、
             标准会话记录。它不知道「网页 AI」这种生物存在。
插件      —— 拿到标准数据后，自己拼成网页 AI 能懂的形态（代码块、卡片、语音约定）。
```

**判断标准**：任何只在网页 AI 场景成立的概念（卡片、bridge-chat-call 标记、
bridge-voice 约定、多卡片检查），一律归插件，不得出现在工具服务的数据结构里。

## 二、对话接口标准（第一轮澄清）

### 2.1 能力边界

| 能力 | 是否支持 | 说明 |
|---|---|---|
| 多轮对话 | **是** | 工具工程记录完整会话，按标准模型项目对待 |
| 并行工具调用 | **是** | 一次回复可含多个 `tool_calls` |
| 流式输出 | **否** | 明确不做，降低复杂度 |
| 工具调用 | **是** | `tools` 声明 + `tool_calls` 返回 + `tool` 角色回灌 |

### 2.2 为什么接口要定标准

现有网页聊天页 `/web-bot` 已经是一个可用的聊天界面，**不需要新增界面**。
但接口必须定义得标准，因为：

- 后续可能增加别的界面（群聊窗口、移动端、第三方客户端）；
- 界面与接口解耦后，每个界面都只是标准接口的一个客户端。

### 2.3 插件要做的翻译

| 网页上的形态 | 翻译成 |
|---|---|
| AI 输出的 `bridge-chat-call` 代码块 | `tool_calls` 数组 |
| 用户消息 | `messages` 里的 `user` 角色 |
| AI 正文回复 | `messages` 里的 `assistant` 角色 |
| 工具执行结果 | `messages` 里的 `tool` 角色，回灌给网页 AI |

**卡片由工具工程解析执行**，插件不再理解「卡片」「工具」这些概念。

## 三、指令体系（第三轮澄清，重要调整）

### 3.1 上一版的错误判断

上一版按「插件不再是业务前端」把 13 条指令移出或删除。**这个判断是错的。**

用户指出的关键场景：**很多时候用户不在电脑旁，无法手动控制工具服务的启停、清空会话等操作。**
这些能力必须能通过指令远程触发。

### 3.2 正确做法：工具工程提供公共指令能力

指令不由插件自己定义，而是：

```
工具工程提供指令规范与接口（与 skill 规范同级）
    ↓
插件安装时按规范注册界面指令
    ↓
与 debug_chrome 提供外部指令是同一套机制
```

**具体形态**：

| 类别 | 归属 | 注册方式 |
|---|---|---|
| 内置指令（`/side` `/settings` 等） | 工具工程定义规范 | 插件安装时注册执行端 |
| 工具服务控制指令（`/rs` `/css` `/cms`） | 工具工程提供能力 | 插件注册执行端，实际由工具工程执行 |
| 自定义指令 | **工具工程存储** | 通过接口提供获取与调用 |
| 组合指令 | 工具工程存储 | 同上 |
| 外部指令 | 由各 skill 声明 | 现有机制不变 |

### 3.3 指令规范：复用既有机制，不新建

**已澄清（第五轮）**：工具工程提供「可注册的接口」，其它插件
（`debug_chrome`、本次拆出的镜像插件）按这套接口标准定义自己的配置，
**安装时对接**。这套机制 `docs/external-command.md` 已经实现并上线，
拆分不新建另一套。

因此本条目的实际工作是：

1. 镜像插件按 `external-command.md` 的既有格式，在 `tool.json` 里声明
   自己能执行的指令（`command_actions` + `commands`）。
2. 补充一类现有规范未覆盖的：**界面自身指令**（`/side`、`/settings`、`/back`、
   `/sessions`、`/reparse`、`/help`），它们是纯前端行为，不经过工具工程，
   只需在规范里登记归属，不需要注册到工具工程。
3. 工具工程侧新增指令时，界面下次加载自然看到（与决策 1 一致）。

### 3.4 指令可能还要扩展

用户提到「甚至可能还要扩展指令列表，例如更新 git 的」。
这意味着指令规范要支持**工具工程侧新增指令**，插件不需要改代码就能用上。

### 3.5 保留的清单

不再有「删除」这一类。所有指令按上述三类归属重新登记：

| 指令 | 归属 | 说明 |
|---|---|---|
| `/side` `/settings` `/back` | 界面自身 | 抽屉外观，纯前端 |
| `/sessions` `/ss` `/cj` `/reparse` | 界面自身 | 会话操作，纯前端 |
| `/css` `/cms` | 工具工程能力 | 清空会话，界面注册执行端 |
| `/rr` `/cp` `/sk` | 工具工程能力 | 卡片操作，界面注册执行端 |
| `/sa` `/rt` | 工具工程能力 | 自动回传策略 |
| `/sp` `/rs` `/vo` `/mem` `/csp` | 工具工程能力 | 截图、重启、语音、记忆、Prompt |
| `/md` | 工具工程能力 | 采集原文，界面注册执行端 |
| `/help` | 界面自身 | 显示指令列表 |
| 自定义 / 组合 / 外部指令 | 工具工程存储 + 各 skill | 现有机制不变 |

## 四、数据归属

| 数据 | 归属 | 说明 |
|---|---|---|
| 网页 AI 原始会话记录 | **浏览器 localStorage** | 插件私有。保存网页上的原始形态（消息文本、代码块、DOM 摘要） |
| 卡片状态（含已执行记录） | **浏览器 localStorage** | 必须持久保存，见下方「持久化与清理」 |
| 网页会话的标准格式副本 | **工具工程** | 由插件翻译后送入，按标准 message 历史存 |
| 工具 / 技能 / 规则 | **工具工程** | 能力归属 |
| 指令定义（含自定义） | **工具工程** | 插件按规范注册执行端 |
| 推送通道配置与凭证 | **工具工程** | |
| 语音成品与缓存 | **工具工程** | |
| 记忆 | **工具工程** | 只服务工具工程自己的对话 |
| 全局配置 | **工具工程** | 单一真源 |

**两份记录的关系**：网页对话有两条并存的数据，各管各的——

- **浏览器里的原始记录**：网页上长什么样就存什么样，含卡片状态。插件自用，用于刷新恢复与界面呈现。
- **工具工程里的标准记录**：插件把同一段对话翻译成标准 `messages` 后送入，供标准接口与记忆使用。

同一段对话在两处形态不同、职责不同，**不是冗余副本**，也不是二选一。
原始记录不可翻译成标准格式后即丢弃：卡片状态在标准格式里没有对应概念，丢了就无法恢复刷新后的界面。

### 4.1 持久化与清理

**卡片状态与原始会话记录必须持久化到浏览器 localStorage**，刷新不丢、关标签页不丢。

- **为什么不能只放内存**：刷新后若丢失，已执行卡片会退回待执行，重抓网页时再跑一遍工具（此问题历史上已出现过，见 `pending-tasks.md` 已关闭表的「刷新后已执行卡片退回待执行」）。
- **唯一的清理入口是抽屉设置页**：用户手动清空会话或删除会话时，同步清掉对应的原始记录与卡片状态。
- **不得自动清理**：不设过期时间、不设条数上限自动淘汰。用户没在设置页里删，就一直留着。

### 4.2 工具与指令必须严格分离

两者看着都是「调用本地能力」，但归属、触发方、结果流向完全不同，**禁止合并成一套机制**：

| | 工具 | 指令 |
|---|---|---|
| 是什么 | AI 操作本地的能力 | 用户远程控制工具服务与抽屉的能力 |
| 谁发起 | AI（经插件翻译为标准 `tool_calls`） | 用户（在网页、手机、QQ 等任意通道敲 `/xxx`） |
| 结果去哪 | 回到 AI 对话流，供 AI 继续推理 | 回到发起指令的用户 |
| 存哪 | 工具工程（工具定义与执行） | 工具工程（指令定义与注册） |
| 界面角色 | 翻译与呈现 | 注册执行端 |

**推论**：

1. 标准 chat completions 接口的 `tool` 角色消息，只承载**工具结果**，不得承载指令回执。
2. 指令回执走独立的回传通道，不进 AI 对话流。指令的执行结果**绝不流向 AI**。
3. 条目的 1 与条目 2 虽然都涉及「回传」，但实现上是两条通道，不能因为名字像就复用同一套逻辑。

## 六、拆分条目

### 条目 1：工具工程实现标准 AI 接口

**做什么**：
- `POST /v1/chat/completions`，接受标准 `messages` 数组
- 支持 `tools` 参数；返回 `tool_calls`（支持并行）
- 接受 `tool` 角色消息回灌
- **不做流式**
- 工具工程侧记录完整会话历史，支持多轮

**代价**：中-高，约 600~900 行。现有 `/tool` 执行逻辑可复用，主要是包标准格式。

**风险**：中。多轮与并行的细节需仔细对齐。

### 条目 2：指令规范与注册机制

**做什么**：
- 编写界面指令规范文档（参照 `external-command.md`）
- 提供注册 / 注销 / 查询 / 回执接口
- 自定义指令迁到工具工程存储，提供获取与调用接口
- 支持工具工程侧新增指令，界面无需改代码

**价值**：解决「用户不在电脑旁无法操作」的场景，这是刚需。

**代价**：中。现有外部指令机制可复用大部分，约 500~800 行。

**风险**：中。指令是高频操作路径，改坏了直接影响日常使用。

### 条目 3：插件改为翻译器

**做什么**：
- 不再建卡、不再调 `/tool`
- 抓网页消息 → 转标准 `messages` → 调 `/v1/chat/completions` → 拿 `tool_calls` → 翻译成网页可执行形式 → 取结果 → 作为 `tool` 消息回灌
- 原始会话记录与卡片状态持久化到 localStorage（见 4.1）
- 按规范注册界面指令

**代价**：中-高，翻译层约 800~1200 行。

**风险**：中-高。行为改动最大，需充分测试。

**本阶段不删旧代码**：旧的建卡与 `/tool` 调用路径先保留，新旧两套并存。
由配置开关切换走哪条路，新链路跑稳并经过实机验证后再删。
删旧代码的动作移入阶段三（见下），避免「旧的已删、新的未稳」的裸奔窗口。

### 条目 4：接口标准化收口（为多界面预留）

**做什么**：把现有 `/web-bot` 的收发接口对齐到标准接口，
使网页聊天页成为标准接口的一个客户端而非特例。

**代价**：低-中。主要是接口适配层。

**风险**：低。

### 条目 5：清理网页侧遗留

**做什么**：`remote_bridge/` 里为「抽屉上报 → 后端推送」写的代码，
改成标准接口后部分要重写或删除。

**代价**：中。

**风险**：中。推送链路线上在用。

## 七、分阶段计划（第四轮澄清：顺序已认可，按调整重排）

### 阶段一：标准接口 + 指令规范

- 条目 1（标准 AI 接口）
- 条目 2（指令规范与注册机制）

**为什么合并**：两者都是「工具工程对外提供规范」的一部分，且都不动插件现有链路。

**注意：两条通道相互独立**。标准接口的 `tool` 角色消息只承载工具结果，
指令回执走另一条通道（见 4.2）。两者在同一阶段做，但实现上不共用逻辑、
不互相依赖——不是为了「共用回传能力」才合并的。

**产出**：任何标准 AI 客户端能连上；指令有规范可循。现有链路照常工作。

**本阶段必须一并完成：接口失败与降级策略**（详见条目 6）。
没有它，后续阶段二一旦切换链路，服务不可达时插件行为未定义。

### 阶段二：插件切换为翻译器

- 条目 3（插件改翻译器）
- 条目 4（接口标准化收口）

**产出**：插件变薄，网页 AI 仍可用。风险最高的一步。

### 阶段三：清理遗留

- 条目 5（清理网页侧遗留）
- **删除旧的建卡与 `/tool` 调用路径**（原属条目 3，移到这里）

**为什么这个顺序**：
- 阶段一不碰现有链路，安全；
- 阶段二插件切换后，新旧两套并存，旧链路仍有调用方（配置开关可切回）；
- 阶段三此时新链路已经过实机验证，删旧的才安全。

**删旧代码的前置条件**（三条同时满足才动手）：

1. 新翻译链路在真实使用中跑满一段时间，未出现工具执行错乱或结果丢失；
2. 配置开关切回旧链路的次数降至零，说明新链路已可信；
3. 刷新恢复、卡片去重、自动回传三项在新链路上逐一验证通过。

**相比上一版的调整**：原「阶段三：工具工程长出界面」取消，因为 `/web-bot` 已经是可用的聊天界面。
原四阶段收缩为三阶段。

## 八、需要你拍板的决策

### 决策 5：指令机制 —— 已确认（第五轮）

**原理解偏差**：曾以为是「新建一套运行时注册接口」。
**实际含义**：工具工程提供可注册的接口，其它插件按接口标准定义自己的配置，
**安装时对接**。这套机制 `external-command.md` 已实现并上线，拆分后沿用。

### 决策 7：工具参数体系 —— 选 2（彻底重写）（第五轮）

**决定**：把 `tool_meta.py` 的自定义参数格式彻底改写为正统 JSON Schema，
不做转换层、不维护两份声明。

**影响面（必须建立进度文档逐项跟踪）**：
- `flask_server/tools/tool_meta.py` — 13 个内置工具的参数声明
- `flask_server/tools/tool_param_check.py` — 参数名校验，依赖旧格式
- `flask_server/routes/tools.py` — `/tools`、`/tools/all` 的输出结构
- `flask_server/custom_tools/loader.py` — skill 工具声明解析
- 前端 `03_custom_tools.js`、`07b_params.js` — 卡片参数渲染与编辑
- 前端 `08e_toolconf.js` — 设置页工具配置渲染
- 所有测试中构造工具声明的地方

**风险**：中-高。牵动前端渲染，且 `"string | array"` 这类联合类型
在标准 schema 里没有直接对应，需逐个决定退化策略。

**要求**：建立 `docs/tool-schema-migration.md` 进度文档，逐项登记
「已改 / 未改 / 验证方式」，避免漏改。

### 决策 6：网页 AI 与标准 API 的关系 —— 已确认（第五轮）

**要彻底消除两者差异**。不管流量从哪来，对工具服务而言都是同一件事。

唯一差别：网页 AI 有自己的会话存储功能，插件收到工具服务的接口数据后
再改造成网页 AI 能理解的形式即可。

### 决策 8：数据分层 —— 已确认（第六轮）

**工具服务存标准，插件做适配**：

| 数据 | 工具服务侧的形态 | 插件侧的处理 |
|---|---|---|
| System Prompt | 标准形态（身份 + 规则 + 技能，不含网页 AI 专有约定） | 拼上调用格式说明、语音约定，交给网页 AI |
| 工具列表 | 标准 JSON Schema | 转成文字列表塞进提示词 |
| 规则 / 技能 | 标准清单与内容接口 | 按需读取并注入 |
| 工具结果 | 标准结构，富信息放 `content` 的 JSON 字符串 | 转成 `bridge-chat-res` 代码块 |
| 会话记录 | **工具服务存完整标准会话** | 抽屉另存一份更细致的（含卡片状态）自用 |

### 决策 9：状态与职责边界 —— 已确认（第六轮）

**工具服务并非无状态**：它存完整会话记录（标准 messages 历史），
但**没有卡片状态这类概念**——卡片是网页 AI 场景的产物，属插件私有。

抽屉因为自己有工具列表、卡片执行、自动回传等业务，
必须在本地再存一份更细致的记录，与工具服务的标准会话**各管各的**。

### 决策 10：工具结果的富信息 —— 已确认（第六轮）

标准 `tool` 消息只有一个 `content` 字符串，但现有错误体系
（`errorType` / `origin` / `hint` / `available`）必须保留。

**决定**：`content` 里放 JSON 字符串，把整套结构原样保留。
**该约定必须写进接口文档**，客户端解析时按约定还原，不得省略。

### 决策 11：并行调用 —— 已确认（第六轮）

- **标准 API**：支持并行，一次可返回多个 `tool_calls`、产出多个工具结果。
- **网页 AI 通道**：天然单线程——网页 AI 若吐出多个调用块，
  抽屉的多卡片检查会直接拦截告警，**不会进入工具服务**。
  故插件侧拿到的结果只可能是单条，无需处理并行。

### 决策 12：语音能力 —— 已确认（第六轮）

**前提澄清**：标准 Chat Completions 接口**不能**返回语音，它只输出文本。
要语音必须单独调 TTS 接口（传文字、拿二进制音频），音频按字符单独计费，
不占对话 token。

**决定**：把 TTS 做成工具服务的一个**标准能力**（一个标准接口），
而不是把朗读约定写死在某个 System Prompt 里。

**链路**：

1. 抽屉拿到标准 System Prompt 后，自行注入「请另用一个代码块返回朗读文本」的约定。
2. 网页 AI 返回朗读文本。
3. 抽屉调工具服务的 TTS 接口，拿到音频。
4. 音频随标准结果一起回传，由推送通道发给用户。

**在工具服务看来**：网页 AI 返回的结果与标准 API 没有任何区别——
都是「一段文本 + 一次 TTS 调用」。语音是插件侧的外挂能力，不是协议的一部分。

### 决策 13：规则与技能的归属 —— 已确认（第六轮）

**规则与技能是工具服务对外服务的一部分**，不是网页 AI 的内部管理规定。

因此：
- 进标准 System Prompt，任何接进来的客户端都受同一套约束；
- 工具服务提供标准的清单与内容接口；
- 插件只是把标准内容转成网页 AI 能读的形态。

**这意味着**：第三方标准客户端接入后，AI 同样被约束成诚实、敢反驳、
遵守项目规则——这是有意为之，不是副作用。

### 决策 14：`/tool` 接口去留 —— 已确认（第六轮）

**保留**。两个接口职责不同：

| 接口 | 输入 | 谁决定调什么 |
|---|---|---|
| `POST /tool` | 工具名 + 参数 | 调用方决定，纯执行器 |
| `POST /v1/chat/completions` | messages + tools | 模型决定 |

`/tool` 是低层执行器，标准接口内部也会复用它。
插件改走标准接口后不再需要它，但它作为「直接执行单个工具」的调试入口仍有价值。

### 决策 1：指令规范的具体形态 —— 已确认

- **声明位置**：与 skill 保持一致，用 `tool.json` 声明，不另立 `commands.json`。
- **更新机制**：界面刷新即可更新，不做推送。工具工程新增指令后，
  界面下一次加载时自然看到。

### 决策 2：`/web-bot` 与标准接口的关系 —— 已确认

采用**选项 B**：`/web-bot` 改为标准接口的客户端。

**附加约束（用户明确）**：界面原型尽量不动。若实现过程中确有必要调整界面，
须先提交调整计划经用户审批，不得自行改动。

### 决策 3：自定义指令迁移 —— 前提不成立（已查证）

**查证结果**：自定义指令本来就存在工具工程里——`bridge_store` 的 `commands` 字段，
写入 `definition.yaml` 入库。抽屉只是通过 `/api/bridge/commands` 接口读写它，
指令本体从未存在浏览器。因此**不需要迁移**，原列的两个选项作废。

### 决策 4：是否接受三阶段顺序 —— 已认可

## 九、System Prompt 分层设计（第六轮补充）

**现状问题**：`extend/dialog/parts/05c_prompt.js` 里把五样东西拼成一个字符串，
但它们归属完全不同：

| 内容 | 现状 | 应归属 |
|---|---|---|
| 工具调用格式说明（`bridge-chat-call` 那段） | 拼在 prompt 里 | **插件**（网页 AI 专有） |
| 语音朗读约定（`bridge-voice`） | 拼在 prompt 里 | **插件**（网页 AI 专有） |
| 工具列表（名称 + 描述） | 拼在 prompt 里 | **工具服务**给标准 schema，插件转文字 |
| 规则清单与读取说明 | 拼在 prompt 里 | **工具服务**给标准清单，插件转文字 |
| 技能清单与读取说明 | 拼在 prompt 里 | 同上 |

### 9.1 分层

```
工具服务 → 标准 System Prompt（身份 + 规则 + 技能，纯标准形态）
              ↓
插件     → 拼上「调用格式说明 + 语音约定」→ 交给网页 AI
              ↓
标准客户端 → 直接用标准 System Prompt + tools 参数，不需要插件那层
```

**判断依据**：网页 AI 认不了 `tools` 参数，只能读文字，所以工具列表、
规则、技能都得转成文字塞进提示词；标准客户端有 `tools` 参数，
工具列表走结构化，只有规则与技能需要进标准 System Prompt。

### 9.2 待定：标准 System Prompt 的内容边界

需要确认：标准 System Prompt 里放什么？候选：

1. 只有「身份 + 规则 + 技能清单」三段
2. 再加「工具使用通则」（如先查参数再调用）——但这条对标准客户端也成立吗？
3. 完全不含工具相关内容，工具说明只走 `tools` 参数

**我倾向 1 + 第 2 条里的「先查参数」**，因为它对两类客户端都成立。
