# 拆分方案：镜像插件 与 工具工程

> 状态：**待审批**。本文件只记录需求、定位、数据归属与拆分条目，未做任何代码改动。
> 需求提出：2026-11-05。同日两次澄清：插件要抽彻底；工具工程要有自己的聊天界面；
> 工具服务对外就是标准 AI 接口，插件是它的一个可选 skill。

## 一、核心定位（本次澄清后确定）

> 工具服务对外提供**标准 AI 接口**（chat completions + tool calling）。
> 插件是安装在工具服务里的**一个轻量 skill**，负责把网页版的流量翻译成标准 API 调用。
> 不装这个 skill，配任何一个标准 AI 端点也能正常用。

由此，两边的关系不是「前端 + 后端」，而是：

```
工具服务 = AI 网关 + 工具执行器 + 推送通道 + 记忆
插件     = 一个可选的对话来源适配器（skill）
```

**关键推论**：插件不是必需品。它只是「对话来源」的一种实现，与「本地聊天界面」
「任意标准 HTTP 端点」并列，三者对工具服务而言是同一件事。

## 二、目标形态

```
  对话来源（三选一    │        工具服务              │
  或并存）           │                              │
┌──────────────┐    │  · 标准 AI 接口               │
│ 本地聊天界面  │───▶│    （chat completions        │
└──────────────┘    │     + tool calling）          │

└──────────────┘    │  · 记忆系统                   │

└──────────────┘    └──────────────────────────────┘
```

### 2.1 标准接口的边界

工具服务对外暴露的，就是标准 AI 接口的形状：

| 能力 | 标准形态 | 工具服务的职责 |
|---|---|---|
| 对话 | `POST /v1/chat/completions` | 接收消息列表，返回回复 |
| 工具调用 | `tools` 参数 + `tool_calls` 返回 | 声明可用工具；接收调用请求；执行；把结果作为 `tool` 角色消息回灌 |
| 流式 | `stream: true` | 可选，视实现成本 |

插件这一侧要做的翻译：

| 网页上的形态 | 翻译成 |
|---|---|
| AI 输出的 `bridge-chat-call` 代码块 | `tool_calls` 数组 |
| 用户消息 | `messages` 里的 `user` 角色 |
| AI 正文回复 | `messages` 里的 `assistant` 角色 |
| 工具执行结果 | `messages` 里的 `tool` 角色，回灌给网页 AI |

**这意味着决策 1 已有答案**：卡片由**工具服务**解析执行，插件只负责把代码块翻译成标准调用、
再把结果翻译回网页可粘贴的文本。插件不再理解「卡片」「工具」这些概念。

## 三、数据归属

| 数据 | 归属 | 说明 |
|---|---|---|
| 网页 AI 会话镜像 | **浏览器** | 插件的私有数据，工具服务不需要知道网页上聊了什么 |
| 卡片状态（网页侧） | **浏览器** | 只在翻译层用，翻译完即可丢弃 |
| 工具服务会话 | **工具服务** | 自己的聊天记录，含标准 API 的 message 历史 |
| 工具 / 技能 / 规则 | **工具服务** | 能力归属 |
| 推送通道配置与凭证 | **工具服务** | 通道是工具服务能力 |
| 语音成品与缓存 | **工具服务** | 合成在工具服务侧 |
| 记忆（蒸馏/事件/检索） | **工具服务** | 只服务工具服务自己的对话 |
| 全局配置 | **工具服务** | 单一真源 |

**关键**：网页 AI 的会话镜像不进工具服务。记忆库里只存工具服务自己的对话。

## 四、插件的新角色：一个 skill

按你的说法，插件等价于「工具服务里安装的一个轻量 skill」。对照现有 skill 机制：

| skill 需要提供 | 插件对应实现 |
|---|---|
| 声明自己能做什么 | 声明「我能对接网页 AI，提供对话来源」 |
| 接收指令 | 接收「把这条消息发给网页 AI」 |
| 执行并回传结果 | 抓取网页 AI 的回复，回传标准格式 |
| 可安装 / 卸载 | 装与不装，不影响工具服务其它功能 |

**这带来一个设计上的好处**：插件不需要自己定义 API，它复用 skill 的既有机制。
工具服务不需要为插件开特例接口。

## 六、拆分条目

### 条目 1：工具服务实现标准 AI 接口

**做什么**：
- `POST /v1/chat/completions`，接受标准 `messages` 数组
- 支持 `tools` 参数声明可用工具（工具列表由工具服务从已注册工具生成）
- 返回 `tool_calls` 或普通 `assistant` 回复
- 接受 `tool` 角色消息作为工具结果回灌

**价值**：这是整个拆分的地基。做不成这个，其它都是空谈。

**代价**：中-高。核心是接口层与工具声明格式的转换，约 600~900 行。
现有 `/tool` 接口的执行逻辑可复用，主要是外面包一层标准格式。

**风险**：中。标准接口的细节多（多轮工具调用、并行调用、错误格式），需要仔细对齐。

### 条目 2：工具服务自建聊天界面

**做什么**：工具服务里的对话页面，直接调自己的标准接口。

**价值**：让工具服务脱离网页 AI 独立可用。

**代价**：高。相当于重做抽屉的核心界面（消息列表、卡片渲染、执行入口），
约 3000~5000 行。可复用现有抽屉的部分渲染逻辑，但数据流要改成同源调用。

**风险**：中。

### 条目 3：插件改为 skill 形态

**做什么**：
- 插件不再建卡、不再调 `/tool`
- 改为：抓网页消息 → 转成标准 `messages` → 调 `/v1/chat/completions` → 拿 `tool_calls` → 翻译成网页可执行的形式 → 取结果 → 作为 `tool` 消息回灌
- 会话与卡片状态只存本地

**价值**：插件变薄的根本。

**代价**：中-高。翻译层是新写的，约 800~1200 行；同时要删掉大量现有业务代码。

**风险**：中-高。这是行为改动最大的一步，需要充分测试。

### 条目 4：工具服务自建配置页面

**做什么**：把抽屉里 `08*` 系列的配置区块搬过来。

**代价**：中-高，约 1500~2000 行。

**风险**：低。

### 条目 5：指令体系整改

**做什么**：按第五节执行——保留 10 条、移除 8 条、删除 5 条。

**代价**：低。指令表是配置数据，改动集中。

**风险**：低。

### 条目 6：清理工具服务里的网页侧遗留

**做什么**：`remote_bridge/` 里大量代码是为「抽屉上报 → 后端推送」写的，
改成标准接口后部分要重写。逐项评估：
- `message_parse` / `outbound`：消息组装，标准接口下由 `messages` 数组替代
- `bridge_store` 的会话去重：标准接口下由 `messages` 历史天然去重
- `channel/*`：推送通道保留，但要接的是标准回复而非抽屉上报

**代价**：中。主要是删与改，新增少。

**风险**：中。推送链路是线上在用的，改坏了直接收不到消息。

## 七、分阶段计划

### 阶段一：工具服务长出标准接口

- 条目 1（标准 AI 接口）

**产出**：任何标准 AI 客户端都能连上工具服务，工具调用能跑通。
此阶段不动插件，现有链路照常工作。

### 阶段二：插件切换为翻译器

- 条目 3（插件改 skill 形态）
- 条目 5（指令整改）

**产出**：插件变薄，但网页 AI 仍能用。这一步风险最高，需要灰度验证。

### 阶段三：工具服务长出界面

- 条目 2（聊天界面）
- 条目 4（配置页面）

**产出**：工具服务能独立使用，插件成为可选项。

### 阶段四：清理遗留

- 条目 6（清理网页侧遗留）

**为什么这个顺序**：
- 先做接口，因为它是地基，且不影响现有链路；
- 再切插件，此时工具服务已能独立承接，出问题可回退；
- 然后补界面，此时工具服务已完全独立，界面是增强；
- 最后清理，因为前面几步会让很多旧代码自然失去调用方，此时删最安全。

## 八、需要你拍板的决策

### 决策 1：已确定

插件只做翻译，卡片由工具服务解析执行。见第二节。

### 决策 2：标准接口的完整度

- **选项 A（最小）**：只支持单轮工具调用，不支持流式。够用，实现快。
- **选项 B（完整）**：支持多轮工具调用、并行调用、流式输出。与主流 SDK 完全兼容。

### 决策 3：工具服务聊天界面的数据来源

自己的聊天界面对话，是否也要走同一条标准接口？
- 走：一套逻辑，界面只是客户端之一
- 不走：界面直接内部调用，省一次 HTTP 往返

**我建议走**，因为能顺带验证标准接口的正确性。
